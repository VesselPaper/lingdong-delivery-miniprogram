## 4. 订单列表/接单（pages/orders/list.js）★核心链路

- **列表**：`api.orders?scope/stage/status` → `/merchant/orders` server.js:1184
  - stage 过滤：accept(status=1) / load(status=2 且批次0/1) / deliver(status=2 且批次2) / pickup(status=3)
  - scope：active(1,2,3) / history(4,5,6,7)
  - 每条附带：items（order_items）、batch 信息（delivery_batches 读 batch_no/daily_seq/route 文本）、contact_phone 脱敏（maskPhone）、landmark_name 清洗（batch.landmarkNameOf）
- **接单按钮**：「接单」→ `request.post(api.orderConfirm, {id})`（key `orderConfirm='/merchant/order/confirm'` server.js:1248）
  - 后端：店铺歇业拦截 → 订单 status=1 校验 → `batch.addOrderToBatch(store, order)`（services/batch.js:92）：
    1. `orderItemCount`（SUM order_items.quantity）
    2. `getOrCreateOpenBatch`：best-fit 找能容纳且最满的组单中批次（实时件数 HAVING items+n≤12），无则新建（batch_no=BD+时间戳、daily_seq、status=0）
    3. orders.status→2 + batch_id（清 batch_removed_at）；delivery_batches.total_orders+1、total_items+n
  - audit 落 audit_logs
- **表**：orders、order_items(读)、delivery_batches(读写)、audit_logs
- **自动接单**：/api/order/pay（用户支付）与 /api/pay/notify（微信回调）中 `maybeAutoAccept`（server.js:348）—— shops.auto_accept=1 且营业中 → 同样调 batch.addOrderToBatch（派车由批次自动派车扫描统一处理）

## 6. 上货配单（pages/device/loading.js）★核心链路

- **列表**：「配单上货」页 → `api.devicePending` → `/merchant/device/pending` server.js:1987：
  - open_batches（status=0 组单中，LIMIT 5）+ ready_batches（status=1 待上货，LIMIT 10）+ active_batches（status=2 配送中）
  - 每个批次 `batch.getBatchDetail`（services/batch.js:227：订单+商品明细+路线文本+已取计数）
  - pending_orders = 组单中+待上货批次内订单数（红点）
- **表**：delivery_batches、orders、order_items、delivery_tasks、landmarks（全部读）

**「选择该批次上货」按钮**（loading.js:90 selectBatch）：
- 批次 status=0（组单中）→ 先 `request.post(api.batchDispatch, {batch_id})`（key `batchDispatch='/merchant/delivery/batch/dispatch'` server.js:1436 → doDispatchBatch，见 §7）
- 然后 `wx.navigateTo('/pages/device/batchDetail?id='+id)`

**「扫无人车二维码」按钮**（loading.js:115 scanRobot）：
- `wx.scanCode` → `scan.parseDeviceSn` → `request.post(api.deviceScan, {deviceSn})`（key `deviceScan='/merchant/device/scan'` server.js:2001）
- 后端：PLATFORM_MOCK 时取最早待上货/组单批次；真实档按 device_sn 精确匹配 status=1 批次（防错车上货）
  - 写 delivery_batches.device_sn、delivery_tasks.device_sn
  - `platform.grantControl(deviceSn)`（获取控制权）+ `platform.robotAtLoadingPoint`（是否在上货点/距离）
  - 返回 batch_id/orders/control_ok/at_loading_point/distance_m
- 前端带参跳转 batchDetail：`?batch_id&sn&at&dist&lmsg`

## 7. 批次派车/上货详情（pages/device/batchDetail.js）★核心链路

**页面加载**：`api.batchDetail` → `/merchant/delivery/batch/detail?batch_id=` server.js:1359 → `batch.getBatchDetail`；前端 `inferPhase`（scanned 可开舱 / open 已开舱 / loaded 可开始配送 / dispatched 已派发），按任务状态 0/10/20/30→scanned、40→open、50→loaded 恢复。

**「打开舱门」按钮**（batchDetail.js:114 openBin）：
- MOCK 分支：直接模拟成功
- 真实分支：`request.post(api.batchOpenBin, {batch_id})`（key `batchOpenBin='/merchant/device/batch/open-bin'` server.js:1451）
- 后端逻辑：
  1. 门禁：`platform.robotAtLoadingPoint`（任务状态 30/40 才放行；未到返回 `reason:'not_at_loading_point'`，前端弹友好 modal）
  2. 真实档：`platform.grantControl(sn, 600)` → ctrlId 写入 `delivery_batches.ctrl_id`（持久化）+ 内存 Map `batchCtrl`
  3. `platform.verifyBatchLoading(store, batch_id)`（platform.js:746）：逐任务 `loadingVerify(device_sn, platform_task_id, {anyCode: pickup_code})`（两段式：先 verify/match 再 loading/verify，否则 DLV_CTRL_0011）
  4. 批次 status→1 待上货
- **表**：delivery_batches（device_sn、ctrl_id、status）、delivery_tasks（读 platform_task_id/device_sn）、orders（读 pickup_code）、audit_logs
- **平台**：deviceCtrl/grantControl、deviceCtrl/verify/match、deviceCtrl/loading/verify

**「关舱」按钮**（batchDetail.js:150 closeBin）：
- 真实分支：`request.post(api.batchCloseBin, {batch_id})`（key `batchCloseBin='/merchant/device/batch/close-bin'` server.js:1490）→ `platform.drawerCtrl(sn, 0)`（独立关舱，不受任务状态限制）
- 前端弹「是否立即配送」→ 确认则 dispatchAll()，取消则 180s 倒计时
- **表**：delivery_batches（读 device_sn）、audit_logs

**「开始配送」按钮**（batchDetail.js:198 dispatchAll，phase=loaded 才允许，舱门开着禁移动）：
- MOCK 分支：`request.post(api.batchMockDispatch, {batch_id})`（key `/merchant/device/batch/mock-dispatch` server.js:1553）：批次→2 配送中 + mock_arrive_at=now+10s；任务→50 已上货（模拟）；到点由自动派车扫描置已送达
- 真实分支：`request.post(api.batchDispatchAll, {batch_id})`（key `/merchant/device/batch/dispatch` server.js:1502）：
  1. `batch.planRoute(store, orders)`（services/batch.js:180 贪心最近邻）→ 写 delivery_batches.route（JSON）
  2. `platform.confirmBatchLoading`（platform.js:762）：逐任务 `loadingConfirm`（→任务 50 已上货，关舱并开始配送）
  3. 释放控制权：`platform.releaseControl(device_sn, ctrl_id)`（ctrlId 取批次行 ctrl_id 优先）→ 清 batchCtrl、ctrl_id=''
  4. 批次 status→2 配送中
- **表**：delivery_batches（route、status、ctrl_id）、delivery_tasks、audit_logs
- **平台**：deviceCtrl/loading/confirm、deviceCtrl/releaseControl

**「派车定型」按钮**（loading.js 内 selectBatch → batchDispatch；也可在批次列表直接触发）：
- `request.post(api.batchDispatch, {batch_id, device_sn?})` → server.js:1436 → `doDispatchBatch`（server.js:1369）：
  1. 真实档：`platform.pickAvailableRobot`（无指定时选空闲车）→ `platform.isRobotBusy` 校验
  2. CAS 抢占：delivery_batches.status 0→1（防并发双派车）
  3. 读批次内订单（status 1/2）→ `platform.createTasksForBatch`（platform.js:431）：真实档**不再 queue/create**，只建本地 delivery_tasks 行（status_text='待开舱上货'），任务在开舱后由 Route B 直接下发；MOCK 档 queue/create
  4. 订单 status→2
  5. 失败回滚：任务作废(110+void_at) + 批次回组单中
- **表**：delivery_batches、orders、delivery_tasks、audit_logs；平台（device list、createTasksForBatch）

## 8. 配送异常处理（pages/orders/exception.js）

- **列表**：`api.orderExceptionList?tab=` → `/merchant/orders/exception` server.js:1306（status=6 或 exception_handled≠''，附批次/商品/脱敏）
- **重新配送**：「重新配送」→ `request.post(api.orderExceptionRetry, {order_id})`（key `/merchant/order/exception/retry` server.js:1265）：
  - 作废本单旧任务（按 order_id 精确作废，task_status<80 → 110+void_at）→ `batch.removeOrderFromBatch` → `batch.addOrderToBatch`（并入新组单中批次）→ exception_handled='retry …'
- **取消并退款**：「退款」→ `request.post(api.orderExceptionRefund, {order_id})`（key `/merchant/order/exception/refund` server.js:1284）：
  - `realRefundOrLocal`（真实微信退款或本地标记）→ `applyOrderCancelled(finalStatus:7)` → 写 refunds（status=3）+ exception_handled='refund …'
- **表**：orders、delivery_tasks、delivery_batches、refunds、audit_logs；平台（cancelQueueTask/closeTask）
