# 05 · 分层改造方案（按数据项拆分 server.js）

> 依据：01 数据项地图（域边界）+ 02/03/04 链路追踪（每个路由落点）。
> 目标：`backend/server.js` 2530 行 → ~200 行装配层；每个域一个目录，域内三件套。
> ⚠️ 铁律：每次对配送流程做代码修改后，必须先清理旧的测试订单/批次再让用户测试。

---

## 1. 目标目录结构

```
backend/
├─ server.js              # 装配层：env加载 → 中间件 → 挂载各域 routes → 静态托管 → 定时器 → listen
├─ db.js                  # 不动（建表/迁移/种子）
├─ services/              # 公共能力，保持现状（platform/wxpay/runtime 归公共，batch/goodsStats/orderCancel 归域）
└─ domains/
   ├─ user/
   │  ├─ routes.js        # express.Router()
   │  ├─ service.js       # 登录、资料、地址、购物车业务
   │  └─ queries.js       # users/addresses/cart 专属 SQL
   ├─ goods/
   │  ├─ routes.js
   │  ├─ service.js       # 商品、店铺、活动、库存、销量结算
   │  └─ queries.js
   ├─ order/
   │  ├─ routes.js
   │  ├─ service.js       # 下单拆单、支付、取消、退款、订单状态机
   │  └─ queries.js
   ├─ delivery/
   │  ├─ routes.js
   │  ├─ service.js       # 批次、任务、追踪、定时器逻辑
   │  ├─ queries.js
   │  └─ timers.js        # 轮询兜底 / 超时扫描 / 取餐超时 / 自动派车（可选独立文件）
   └─ admin/
      ├─ routes.js
      └─ service.js       # 状态聚合、雷达、工具操作、大屏聚合
```

## 2. 每域路由归属清单（从 server.js 行号映射）

> ⚠️ 归属判定**只看数据项**：路由读写哪张/哪些表的主数据，就归哪个域——即使它被某个端（用户端/商家端/管理员）的页面使用。
> 例：`/api/merchant/orders`（商家端订单列表）读 orders/order_items → **归 order 域**，不因它在商家端任务页展示而归 delivery。
> 跨域数据一律通过调对方 service 解决，不作为归属依据。

## 3. 装配方式（server.js 瘦身）

```js
// server.js（示意）
const { init } = require('./db')
const runtime = require('./services/runtime')
runtime.assertBootable()
const platform = require('./services/platform')
platform.setDispatchHook(runtime.warnIfUnsafeDispatch)
const store = init()

const app = express()
// 中间件、静态托管（/uploads /dashboard /admin）、根重定向 同现状
app.use('/api/auth', require('./domains/user/routes')(store, { runtime, platform }))
app.use('/api', require('./domains/goods/routes')(store, { runtime, platform }))
app.use('/api', require('./domains/order/routes')(store, { runtime, platform, wxpay }))
app.use('/api', require('./domains/delivery/routes')(store, { runtime, platform, batch, orderCancel }))
app.use('/api/admin', require('./domains/admin/routes')(store, { runtime, platform }))
app.use('/api/dashboard', require('./domains/admin/routes').dashboard(store, { runtime, platform }))
// 定时器：require('./domains/delivery/timers').start(store, ...)
app.listen(PORT, ...)
```

要点：
- 路由工厂模式：`module.exports = (store, deps) => { const router = express.Router(); …; return router }`
- store 由 server.js 注入（与现有 services 一致：显式传 store，不持有全局实例）
- 公共中间件（auth/merchantGuard/adminGuard）、audit、maskPhone、toStock、ok() 挪到 `backend/lib/` 或 `domains/_shared.js`
- 状态字典/常量按域归位（ORDER_STATUS → order；TASK_STATUS → delivery；ADMIN_TASK_STATUS → admin）
- 域名路由统一挂 `/api` 前缀下（保持 URL 不变，前端零改动）

## 4. 跨域调用契约（05 关键定案）

| 调用 | 实现 |
|---|---|
| order 下单扣库存 | order.service → `goods.service.deductStock(goodsId, qty)`（goodsStats 归 goods 域） |
| order 下单删购物车 | order.service → `user.service.removeCartItems(userId, goodsIds)` |
| order 取消/退款落账 | order.service/orderCancel → `goods.service.restoreStock` + `delivery.service.removeFromBatch` |
| order 接单并入批次 | order.route → `delivery.service.addToBatch(store, order)`（batch.js 函数包一层） |
| 订单状态机 | `canMoveOrderStatus` 迁到 order.service；delivery 域 platform.applyStatus 通过 order.service.moveOrderStatus 推进 |
| delivery 回调写订单 | delivery → order.service（applyStatus 内部调） |
| delivery 取餐超时驳回 | delivery.timers → order.service.cancelAndRefund(order) |
| admin reset/清理 | admin.service → order.service.cancelAll + delivery.service.cleanupBatch + platform.* |
| admin state 聚合 | admin.queries 直接只读 SQL（跨域只读豁免） |

## 5. 迁移步骤（分 4 步，每步回归）

### 步骤 1（试点）：user + goods 域
1. 建 `domains/user/`、`domains/goods/`，把 01 表归属的查询抽成 queries.js
2. 把对应路由回调改为调 service + queries（**URL 不变**）
3. server.js 中删除已搬走的路由，改为 `app.use('/api', userRoutes)` / `app.use('/api', goodsRoutes)`
4. 回归：`node test_batch_flow.js` 全绿 + 手动跑用户端下单前链路（登录/商品/购物车/地址）
5. 提交点：确认后可 commit

### 步骤 2：order 域
1. 抽 order.queries（orders/order_items/refunds/cancel_requests/pay_notifications）
2. 把订单状态字典、applyOrderCancelled、realRefundOrLocal、splitOrderChunks、maybeAutoAccept 搬入 order.service
3. orderCancel.js 归入 order 域（或保留 services/ 作为 order 域实现）
4. 跨域：maybeAutoAccept 调 delivery.service.addToBatch（此时 delivery 尚未拆 → 先调 services/batch.js，保持兼容）
5. 回归 + 真机下单/支付/取消/退款流程

### 步骤 3：delivery 域（最大）
1. 抽 delivery.queries（delivery_batches/delivery_tasks/landmarks）
2. batch.js 逻辑并入 delivery.service（getOrCreateOpenBatch/addOrderToBatch/planRoute/getBatchDetail 等）
3. 平台回调/轮询/超时/自动派车 4 个定时器迁入 timers.js
4. applyStatus 迁移：delivery 域负责任务状态，订单推进调 order.service
5. 回归：test_batch_flow + 真机全流程（下单→接单→派车→上货→配送→取餐）+ 异常路径

### 步骤 4：admin + dashboard 域
1. admin.routes 收编 /api/admin/* 与 /api/dashboard/*
2. admin.service 调各域 service + platform
3. audit()/adminGuard 迁公共模块
4. 回归：管理员页功能 + 大屏

## 6. 风险与注意

1. **真机测试期**：每次配送代码改动后先清理旧订单/批次（铁律），再让用户下单
2. **URL 必须不变**：小程序已发布/开发版引用的接口路径不能动（前端零改动目标）
3. **store 注入**：所有函数保持显式传 store，避免模块级单例（test_batch_flow 依赖）
4. **require 环**：batch.js 延迟 require platform 的模式（orderCancel.stopMock）要保持；域间互相 require 时注意环
5. **canMoveOrderStatus / applyStatus 归属**：订单状态机是跨域热点，拆 delivery 时把「任务状态→订单状态」映射留在 delivery 内，但调用 order.service 的状态校验函数
6. **computeStats**：商家 stats 与大屏共用，归 order 域（主要读 orders），admin/goods 域调用
7. **定时器**：全部在 server.js 末尾装配（与现在一致），但逻辑进 delivery/timers.js；MOCK/真实档差异（runtime.realPlatform 分支）原样保留
8. **不做**：不改 db.js 表结构、不改 URL、不改前端页面（除非后续单独提出）
