## 2. 分层目标

1. **按数据项（业务实体）分层**，不是按 HTTP 路由分层：每个业务域 = 一组专属数据表 + 自己的 service + 自己的路由。
2. server.js 瘦身到 ~200 行：只做 环境加载 → 中间件 → 挂载各域 routes → 静态托管 → 定时器装配 → listen。
3. 每个域内三件套：`queries.js`（只碰本域表）+ `service.js`（业务逻辑）+ `routes.js`（薄路由壳）。
4. 跨域数据只通过「调用对方 service」访问，禁止直接查对方表（例外：admin 域只读聚合、delivery 域读 orders）。

## 3. 已确认的决策（勿轻易推翻）

- ✅ 按数据项分 5 个域：**user / goods / order / delivery / admin**（划分依据见 01 文档）
- ✅ 迁移顺序：**先试点 user + goods（无跨域依赖）→ order → delivery → admin/dashboard**
- ✅ 真机测试期间**分步迁移**，每步跑 `node test_batch_flow.js` 全绿 + 管理员页状态核对后再继续
- ✅ 定时器（轮询兜底/超时扫描/自动派车）属于 delivery 域，最后随 delivery 一起搬
- ✅ 中间件（auth/merchantGuard/adminGuard）、状态字典、公共常量留在 server.js 或挪到公共模块
- ⚠️ 铁律：**每次对配送流程做代码修改后，必须先清理旧的测试订单/批次**（取消活跃订单 + 关闭平台任务 + 批次置已取消），再让用户重新下单测试

## 4. 三层链路追踪法（本组文档的整理方法）

用户要求按「按钮 → 前端 → 后端 → 数据库」逐层追踪，每层看完即可放下：

```
[前端] 按钮/页面事件 → 页面 js 函数（文件:行号）
  → utils/api.js 里的 key（如 orderCreate）→ request.get/post 拼成完整 URL
[后端] server.js 对应路由（行号）→ 参数校验 → 调 service / 直接 SQL
  → services/*.js 函数（文件:行号）
[数据库] 被读写的表 + 字段 + 写入/迁移规则（db.js 定义）
```

02/03/04 三份文档按此格式穷尽全部链路；05 依据它们做模块拆分。

> ⚠️ **重要区分（务必读）**：
> - **02/03/04 链路追踪文档按「端」分文件**（用户端 / 商家端 / 管理员）——这只是**方便按按钮找链路**的组织方式，**不是**代码分层方式。
> - **05 的代码分层严格按「数据项（表）」**：路由归属判定只看它读写哪张/哪些表的主数据，归哪个域——即使它被某个端/页面使用。
>   例：`/api/merchant/orders`（商家端订单列表）读 orders/order_items → **归 order 域**，不因它在商家端页面展示而归商家/页面域。
>   例：`/api/merchant/device/batch/*`（商家端上货页按钮）写 delivery_batches/delivery_tasks → **归 delivery 域**。
> - 不存在「商家端域」「用户端域」「页面域」——端只是入口，数据项才是边界。
