## 二、为什么又要顺延一次（这是本提交要留下的教训）

上一个提交（`6afe8e9`）顺延的是 `git交接文档`，本提交顺延的是 `会话交接文档`。
**同一类撞号，一次合并里遇到两批**，说明这不是偶发失误，而是**并行开发的编号机制本身有洞**。

具体对照（两份文档在两条分支上同号但内容完全不同）：

| 编号 | `origin/main`（成员那条线） | 本地（我方这条线） |
| --- | --- | --- |
| 会话 20 | 2026-10-12 承接《交接文档19》后端上云，60 行 | 2026-10-12 同一时段的本地增量，119 行 |
| 会话 21 | **远端没有 21**（成员侧跳号） | 2026-10-12 傍晚一段，84 行 |
| 会话 22 | 商品删除（除 Excel 之外的测试商品），103 行 | 大屏显示真车定位收尾，69 行 |
| 会话 23 | 补齐所有商品图片，111 行 | 我方无 23 |

两边都是从同一基线（`72cb732`）之后**各自独立往下编号**，所以必然撞。远端已推送、不能改号，
因此本地这批（未被推送）顺延为 **24 / 25 / 26**，本次会话的新文档顺位取 **27**。

**根因**：`AGENTS.md` §8.5 只要求"追加新一份、编号递增"，**没有说"取号前先 fetch 远端，按远端最新号 +1 取号"**。
在当前"成员直接推 main、并行开发"的协作方式下（§8.7，2026-10-12 定），这条不补上就会持续撞号。

> **这条规范该不该写进 `AGENTS.md`，需要负责人拍板，本次未改 `AGENTS.md`。**
> 建议补一句：「提交交接文档前先 `git fetch`，编号 = **远端已存在的最大编号 + 1**（不要只看本地）」。
> 若负责人同意，我另开一次提交改（按 §11，仓库记忆的修改须先经负责人同意）。

## 三、遇到的问题 / 踩的坑

1. **撞号是"语义冲突"不是"文件冲突"，只看 diff 会丢历史。**
   `git merge-tree` 报 `交接文档20.md`、`22.md` 冲突时，很容易误判成"两边都改过这个文件，取一边即可"。
   实际上 merge-base 里**根本不存在这些路径**（两侧各自新增），内容记录的是**不同会话的不同工作**。
   取任何一边都等于直接删掉另一条线的项目历史。

2. **顺延后编号不连续是正常的，不要去"补洞"。**
   远端没有会话 21；我方顺延后占 24/25/26。全局编号序列变成
   `1..20, 22, 23, 24, 25, 26`（缺 21）。这个 21 是成员侧跳号造成的，**不是我们的错，也不该补**——
   补一个空的 21 只会让后来人以为丢了一份文档。

3. **同一个合并里顺延两批文档，说明"一次只看一类"的思路不成立。**
   我第一轮只顺延了 `git交接文档`（因为 `merge-tree` 那一次只报了那 4 个），
   顺延完再跑 `merge-tree` 才发现 `会话交接文档` 也撞号。**教训：顺延类改动要"改完重跑一次
   冲突预演"，不能只按第一次的冲突清单收工。**
