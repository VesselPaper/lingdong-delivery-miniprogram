## 一、这次为什么改（负责人 2026-10-12 的明确口径）

原话（大意）：**"这个召唤任务判定失败，你不影响。任务判定失败之后不是直接回充电桩，而是有条件的话尽量继续执行，而不是直接停止回充电桩。"**

也就是说 13 号那次做的"连续失败 3 次就停手"方向错了：

- 停手 = 车那边没有任务了 = 它按自己的分组策略（`returnStrategy=standby`）**回充电桩**，业务就停在「待上货」不动了；
- 平台把召唤判失败**不归我们管**（也不该由我们"认输"），我们的职责是**只要还有单要上货，就继续把车叫过去**。

所以这次把默认口径翻过来：**失败也持续重试；失败次数只用来在管理端亮告警**。

## 三、当前行为的完整口径（一张表看懂）

| 情况 | 行为 |
| --- | --- |
| 批次「组单中/待上货」且有单、已指派车 | 守住该车在上货点的召唤任务 |
| 召唤任务活着（0/10/20） | **不重发**（不刷平台、不打断导航）；距上次召唤超过 `SUMMON_LOADING_KEEP_MS`（默认 4 分钟）才在 5 分钟窗口到期前续一次 |
| 任务到达过 30（到达） | 健康：清失败计数与告警，不重发 |
| 任务没到过 30 就进终态（40/50/60） | 计一次连续失败 → **继续重发**（节流默认 15 秒）——**默认永不停手**；连续失败到 `SUMMON_LOADING_KEEP_ALERT_FAILS`（默认 3）→ 管理端亮红字告警（只提示） |
| 显式设 `SUMMON_LOADING_KEEP_MAX_FAILS>0` | 才在连续失败该次数后停手（=1 即"只发一次"，排查隔离用） |
| 批次进入配送中(2) / 完成 / 取消 | 不再守候，计数与告警自动清掉 |

## 四、遇到的问题 / 踩的坑

1. **口径反转要连文档一起翻**：13 号把"停手"写进了 `doc/02`、`doc/07`、`.env.example` 三处文案，这次逐处改回，避免文档与代码打架（本文档与 13 号并存，读的时候以 14 号为准）。
2. **"停手"和"告警"必须解耦**：一开始用一个阈值同时干两件事（到 3 就停手且告警），口径一变就得推翻整个逻辑。现在拆成 `..._ALERT_FAILS`（只告警）与 `..._MAX_FAILS`（才停手，默认 0=不停），两个开关互不影响，日志里同一轮只在**跨阈值那一刻**打印一次（否则每 5 秒刷屏）。
3. **节流默认值的取舍**：实测任务失败发生在创建后 6~16 秒，而车在任务结束后几秒内就开始往充电桩走。原来 30 秒节流意味着车有 15~25 秒"没任务"的时间窗（足够它往回走一截）；改成 15 秒后这个窗口明显变短，仍只相当于每分钟最多 4 次召唤请求，对平台没有压力。可随时用 `SUMMON_LOADING_KEEP_TRY_MS` 调。
4. **"有条件的话尽量继续执行"里的"条件"**：目前是「该批次还有单要上货 + 车没在配送中 + 车未离线」（前两条已有判断，离线/异常由平台召唤本身返回失败兜底）。还有一个可做的候选条件：**批次已经开过舱（`bin_opened_at` 有值）时不再重发召唤**——那说明车已到位、商家正在上货，此时再发召唤反而会把车拽走。本次**没做**，留作待办（需要确认开舱后的时序）。
5. 本轮与另一个 agent 并行：它先提交了 `247ea85`（大屏 EVIZ 定位兜底，用掉 12 号文档），本提交用 14 号；提交前照例断言索引里只有本提交的文件。

## 七、遗留待办

1. **让越凡答复**（根因仍在平台/机器人侧，我们只是不再被它拖回充电桩）：①车在充电桩/充电中时轻任务召唤是否生效、`returnStrategy=standby` 会不会让它接受后立刻放弃；②新上货点(17.168,-3.435)是否在可通行路网内；③要平台给出任务失败原因（接口不返回）。
2. **可选条件**：批次已开舱（`bin_opened_at` 非空）后不再重发召唤（见 §四.4）。
3. **观察成本**：默认不停手意味着失败期间车会在上货点附近来回跑。若长时间失败，建议看电量与里程，必要时用 `SUMMON_LOADING_KEEP_MAX_FAILS` 临时设一个上限（配合"只发一次"排查档定位责任方）。
