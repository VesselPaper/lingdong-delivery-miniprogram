## 2. 逐文件改动说明

### 2.1 后端（优惠券）

#### 新增 `backend/services/coupon.js`（券算法核心）

优惠券「怎么算」全部收在这一个文件里，域服务只负责取数与落库。

| 函数 | 作用 |
| --- | --- |
| `computeReduce(coupon, rows)` | 抵扣计算。满减（`base ≥ threshold` 才减，且不超过 base）、折扣（`base × (1-discount)`，封顶 `max_reduce`）、无门槛（直接减，不超过 base） |
| `evaluate(coupon, userCoupon, rows, now)` | 可用性判定 + **不可用原因**。原因码：`disabled` / `used` / `expired` / `scope` / `threshold` / `no_benefit` |
| `rankFor(rows, candidates)` | **最优券推荐**：抵扣最多者优先，同额取门槛更高者 |
| `allocate(rows, totalReduce, coupon)` | **优惠分摊**：返回 `Map<行下标, 分摊(分)>` |
| `describe(coupon)` | 给用户看的一行券文案，如「满¥30减¥5」「8.5折（最高减¥3）」「无门槛减¥2」 |
| `calcExpireAt(coupon, receivedAt)` | 相对有效期的到期时间（领取后 N 天，当天 23:59:59 止），随人而异 |
| `inValidWindow` / `parseScope` / `goodsInScope` | 有效期与适用范围判定 |

**关键口径（与美团/淘宝一致）**：

- **券作用于「活动后金额」**：活动先打折/满减，券再对折后金额抵扣。这样券不会把活动价再打一遍折（否则商家亏两遍）。
- **分摊基数同为「活动后金额」**（这是对需求原文「按商品原价比例分摊」的一处**有意偏离**，见 §3 P-5）。

**分摊算法的三条硬约束**：

1. 各分摊之和**恰好**等于总优惠（余数归最后一行，避免逐行四舍五入对不上账）；
2. 单行分摊**不超过**该行金额（实付不会变负数）；
3. **只分摊给券适用范围内的商品**。

## 3. 遇到的问题 / 踩的坑

### P-1（最坑，排查最久）小程序报「请求失败」，真实原因是**后端没重启**，接口 404

现象：商家端新建优惠券后提示「请求失败」，看起来像网络故障或接口报错。

排查：直接用 `node -e "fetch(...)"` 探本机 3000 端口，发现——

```
/shop/status          HTTP 200  ← 服务在跑
/merchant/coupons     HTTP 404  ← 路由根本不存在
/merchant/activities  HTTP 401  ← 路由存在（只是没带 token）
```

根因：3000 端口上跑的是**加优惠券之前**启动的进程。Express 对未知路由返回的是 **HTML 404 页面**，
里面**没有 `msg` 字段**，小程序的 `utils/request.js` 取不到提示语就兜底成了那句「请求失败」——
提示语把「接口不存在」说成了「请求失败」，误导了整个排查方向。

- **处理**：停掉旧进程、重启后端；重启时 `db.js` 的迁移自动建好 `coupons` / `user_coupons` 表。
- **教训**：以后看到「请求失败」这种**没有具体信息**的报错，先用 `fetch` 直接探接口看 HTTP 状态码，
  不要在小程序侧猜。**后端改完必须重启**（本次提交的改动全部需要重启才生效）。

### P-2（真实 bug）`per_user_limit = 0`（不限领）被 `|| 1` 吞掉，变成「限领 1 张」

`coupon/queries.js` 的 `insert` 原本写 `Number(f.per_user_limit) || 1`。而 `0` 是「不限领」的**合法取值**，
被 `||` 吞掉后落库成 1 —— 商家设了不限领，实际每人只能领 1 张，且界面上看不出来。

- **修法**：只有字段**缺失**时才回落默认值 1（不限领是危险默认，不能拿来兜底）：
  `f.per_user_limit === undefined || null ? 1 : (Number(f.per_user_limit) || 0)`。
- 已在测试 [8] 加断言锁死：`per_user_limit=0` 落库仍是不限领，且同一人能领第二张。

### P-3（反复踩）`scroll-view` 只给 `max-height` 是**不会滚动**的

券弹窗的券列表一开始只写 `max-height`，结果内容被压扁。这是本项目**第二次**踩同一个坑
（第一次是购物车弹层 `cart-panel`）。

- **根因**：`scroll-view` 需要**确定高度**才会滚动；父容器只设 `max-height` 时，`flex:1` 也拿不到高度。
- **修法**：JS 按内容算出像素高度写在内联 `style` 上；购物车弹层用的是 `computeSheetHeight(count)`，
  券弹窗用的是 `popupBodyHeight(list)`。券弹窗还额外用图片 `bindload` 拿到真实宽高比重算一次
  （图还没加载完时先按 4:3 估），并加了**兜底下限**防止算成 0 把图压没。

### P-4（产品闭环）券必须配图才能启用，否则用户端根本没有它的形态

用户端首页与活动页都是**图片列表**，券和折扣/满减活动一样靠图片呈现。没配图的券在用户端等于不存在。

- **修法**：`normalizeCoupon` 里 **`status===1`（启用）必须有 `image`**；停用可以先没图（便于先存后补图）。
  与活动的「发布强制配图」同一条规矩，两处口径一致。
- 老库补 `coupons.image` 列（`PRAGMA table_info` 守卫），已用「没有该列的老库」实测迁移：
  列补上、老数据没丢、默认 `''`。

### P-5（有意偏离需求原文，需负责人确认）分摊基数用「活动后金额」而不是「商品原价」

需求原文写的是「优惠金额按**商品原价**比例分摊到每个商品」。

实际实现按**活动后金额**比例分摊，原因：券抵扣的基数本身就是活动后金额，
按同一基数分摊才能同时满足「分摊之和恰好等于券抵扣」且「不出现某件商品的券分摊大于它自己的活动后金额」——
后者在部分退款时会把钱退多。测试实测 `5.00 vs 5.00` 精确相等。

> **这是本文件中唯一一处对需求原文的有意偏离，已在该次会话中向负责人说明。**
