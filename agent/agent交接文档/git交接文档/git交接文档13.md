## 二、遇到的问题 / 踩的坑

1. **「删商品」必须先问「小程序里到底有没有删除这个动作」**：`商家端` 商品列表只有「下架/上架」，后端也只有
   `PUT /merchant/goods/status`。用户说的「删除」在系统里其实**做不到**，只能下架（下架后商家端仍占一行、
   批量录入还会按条码当「已存在」跳过）。所以本次是**补能力**，不是改数据 —— 直接去改库会绕开审计和商家端入口。
2. **同一个项目里两套库，差点在错的库上动手**：本机库（PID 2948 / 3000）已经是 216 条门店商品，云端才是 226 条。
   做法：两边都用接口/直读各拉一次全量，按 `条码 + 名称` 双向比对集合差异，确认「多出来的 10 条」只存在于云端且
   与 `db.js: seed()` 名单逐条对上，再动手。
3. **`cart` 的 `LEFT JOIN` 让「删商品」看起来会留脏数据，实际不会**：`cartList` 是 `LEFT JOIN goods`，删掉商品后
   那一行的 `g.status` 为 NULL；用户端 `cart.js:20` 有 `.filter(it => it.goods_status === 1)`，所以残留行既不显示、
   也进不了结算（下单前还会再查商品是否存在）。先把这条链路读出来，才敢按用户的选择「购物车引用保留不动」。
4. **清理工具读 DB 路径的坑（差点埋雷）**：`db.js` 在**模块加载期**就把 `DB_PATH` 定死，而生产 `.env` 里的 `LINGDONG_DB`
   并不在进程环境里。如果工具先 `require('../db')` 再读 `.env`，就会在默认路径上**新建一个空库**（还会写入那 10 条演示种子），
   然后在错的库上删得干干净净、报「完成」，真库一点没动。所以工具第一步先解析 `backend/.env` 的 `LINGDONG_DB`，再 require。
   另外加了安全闸：命中数 == 库内总数时直接拒绝（明说"这看起来是空库/新库"）。
5. **「无图」有两种，只查字段为空会漏报**：本机 33 条 `image` 为空，但另有 3 条**字段有图、文件不存在**
   （`外星人电解质水荔枝海盐950ml` / `汤达人韩式（杯）` 库里写 `.png` 而 `seed_images/` 里是 `.jpg`；
   `Anemon3,118g比利时风味焦糖饼干` 没有对应种子图）。云端那 182 条有图的 URL 逐个 HEAD 全是 200、没有挂图。
   统计口径写进交接文档 22，工具的输出则以「字段为空」为准（那 3 条属于数据修正，见遗留待办）。
6. **测试里「批量删除」的期望条数算错过一次**：前两个用例各删了 1 条门店商品，我却按「只少 10 条」断言总数，
   第一次跑出 3 个 ✘。修正为如实按「10 条种子 + 2 条用例删除 = 少 12 条」，并把已删 id 塞进 `ids` 专门验证 `missing`。
   —— 断言要跟着用例自身的副作用走，别只对着「业务上应该少多少」写。
7. **`Select-Object -First N` 会把上游 node 掐死**：用管道截取测试输出前 45 行时，PowerShell 提前关闭管道导致
   node 以 `exit code 1` 收场，一度误判「测试失败」。改成输出到日志文件再看 `$LASTEXITCODE`。
