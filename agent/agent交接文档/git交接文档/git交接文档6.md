## 二、为什么改

线上后端 2026-10-12 部署到阿里云 ECS（`http://47.108.151.96:3000`）后，根目录三个 `.bat` 的定位发生了变化：`启动服务器.bat` 从"方便"变成"风险"，两个"打开"脚本则应该指向云端才有用（它们的连通性探测与 `服务器地址.txt` 机制本来就是为远程后端设计的）。

## 三、遇到的问题 / 踩的坑

1. **两个 `.bat` 是 GBK 编码 + `chcp 936`**，不是 UTF-8：`read` 工具直接报 "invalid UTF-8"。改它们必须按 GBK 写、并保持 CRLF（仓库根的 `.gitattributes` 对 `*.bat` 指定了 `eol=crlf`，已在提交前用 `git ls-files --eol` 确认新文件是 `w/crlf`）。
2. 写入做法：先用 `write` 工具写 UTF-8 源到工作区 `_tmp4\probes\tools\bats-src\`，再用 PowerShell 的 .NET 接口**显式指定编码**转成 GBK 落到仓库，全程不让 shell 正文接触中文（避免历史上"中文文件走 shell 被 GBK 转码"的事故）。
3. **验证时踩到显示陷阱**：`cmd /c 脚本` 的输出被 PowerShell 按 UTF-8 解码，GBK 中文在**捕获输出里**必然显示成乱码，但文件字节是对的（用 `Encoding.GetEncoding(936)` 解回来中文正常）。这与之前 `tar -tzf` 显示中文乱码是同一类问题：显示乱码 ≠ 文件坏。
4. 真实"双击"没法自动验证（会弹出浏览器并 `pause`），改用**干跑副本**：把 `start ""` 换成 `echo [DRY-RUN]-would-open`、把 `pause` 注释掉，跑一遍确认地址拼接与连通性探测分支都正确。
