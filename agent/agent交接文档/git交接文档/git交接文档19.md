## 二、为什么改（2026-10-12 实测踩到）

- 18:11 老代码（`56a71fb`，停手版）写入 `meta.summon_keep_alert:R110A2603AUEQC00 = {fails:3,…}`。
- 18:17 批次 #2 完成、不再有车等上货；但**告警一直留在 meta 里**。到 19:16 部署新版本后仍然在 —— 因为新进程内存 `keepFail` 是空的，原清理逻辑 `for (sn of keepFail.keys())` 一次都不执行，清不掉。
- 后果：管理端总览会一直亮着「上货点召唤连续失败」的红字告警，明明问题已不存在，误导运营。
- 修法：清理的**依据从"内存"改成"meta 告警行本身"** —— 有没有这行，就删不删。内存 `keepFail` 的清理照旧（负责计数即时归零）。

## 三、遇到的问题 / 踩的坑

1. 一开始只想到"批次离开待上货集合就清"，但实现成按内存 `keepFail` 遍历，漏了"重启后内存为空"这个场景。换成按 meta 行遍历后，两个场景（重启残留 / 正常运行）都覆盖，且天然幂等（没批次等货 → 全删）。
2. 判断"这辆车还在不在等货"用 `byDev`（从 `status IN (0,1) AND total_orders>0 AND device_sn!=''` 的批次聚合），与守候主体同源，不会误删正在失败重试的车（测试 [8] 锁定）。
3. 告警行的 key 固定是 `summon_keep_alert:<device_sn>`，旧格式行（`564e610` 之前写的、没有 `device_sn` 字段）也靠 key 后缀解析出车号，能正常清理。
