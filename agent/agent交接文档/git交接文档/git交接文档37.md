## 二、为什么要做这个（实测证据）

2026-10-12 负责人真机实测时发现"**有订单，车却总想回充电桩**"。云端只读采样（2.5 分钟）拿到 6 条召唤任务的完整状态序列，模式完全一致：

```
任务创建 → 10 已接受 → 20 前往中 → 50 失败（6~16 秒后）→ 车立刻 returnChargingPile
约 30 秒后守候逻辑又续一条 → 再失败 → 再回充电桩 …… 循环（电量 99% → 98%）
```

- **没有一条走到 30（到达）**，所以不是"到达后等超时自动返程"（那才是平台轻任务的正常语义：`expireTime` 到点自动返程，我们给的窗口是 5 分钟）。
- 失败原因**平台不返回**：`GET /open-api/v1/lightTask/{id}` 报文里只有 `status`，没有错误码/原因字段。
- 我们代码里**原本没有**"30 秒回充电"这种东西：所有会让车回去的窗口都是分钟级（上货点 5 分钟、无单释放 3 分钟、配送停靠站 20 分钟）。唯一的 30 秒是**重发节流**。
- 于是循环由两半组成：**平台/机器人侧把任务判失败**（真问题）+ **我们的守候每 30 秒重发**（把问题放大：车来回跑耗电、真问题被循环掩盖，且每次重发都会新建 lightTask、重置导航，车更难到位）。这次改的是后半截 —— 止血，不是根治。

## 三、遇到的问题 / 踩的坑

1. **"在途不重发"与"到点续一次"是两条路**：旧代码只看"任务是不是终态"，`40/50/60` 一律当"该续"，于是"判失败"和"正常结束"被混为一谈，失败会被无限重试。新代码用「**这个任务 id 有没有被观测到过 status=30**」区分二者：到过 30 = 健康周期（照旧续，保证守候不中断）；没到过 = 叫不过去（计数、达阈值停手）。`keepArrived` 是内存 Set，加了 500 条上限避免长期运行无限增长。
2. **测试里必须能关掉 30 秒重发节流**：否则连续调用会被节流挡住，测不出"续→续→停"的序列。做法是把节流值改成读 `SUMMON_LOADING_KEEP_TRY_MS`（默认 30000），测试设 0 —— 顺带让这个节流也变成可配项。
3. **模块级 Map 在测试里的隔离**：`keepFail`/`keepAt`/`keepTryAt` 都在模块作用域，测试用例之间会互相污染。**不加 reset 钩子**，改为每个用例用**不同的 device_sn**（SN-A…SN-F），干净且不动生产代码。
4. **第一版实现有个真 bug，被单测抓住**：到达(30) 分支写成 `if (keepFail.delete(sn)) clearKeepAlert(...)` —— 内存里没有计数时（刚重启、或只有告警没有计数）就**不会清告警**。单测 [2] 直接红。改成无条件清。
5. **`status=50` 的含义必须看对表**：`doc/07` 里有两套状态字典，别混：**配送任务**（`delivery_tasks`）的 50 = 已上货；**轻任务**（lightTask/召唤）的 50 = **失败**。判据取自 §3.3 那一行（0/10/20/30/40/50/60）。
6. **采样期间车被负责人停在禁行线上**（为阻止它乱跑），这本身也可能让机器人接受召唤后立刻失败 —— 所以"失败原因在平台/机器人侧"这个结论要等把车挪回正常可行驶位置后再复核。
7. **和另一个 agent 并行**：`git交接文档12.md` 是它为大屏 EVIZ 兜底写的，本次改用 13 号，并在提交前断言索引里只有本提交的文件（避免把它的暂存内容卷进来，见《git交接文档11》§三.3 的教训）。它同时改 `platform-http.js`（未暂存）。
