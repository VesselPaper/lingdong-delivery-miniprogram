## 2. 为什么改造成「召唤配送」（用户已定方向）

之前的"多单 union 连投"方案（同批次多任务挂同一 `unionTaskId` 共享货仓、一次装货多点连投）已**放弃**，实测结论：

1. `unionTaskId` 平台按**数字(int64)**解析，字符串格式（如 `U-BD...`）报 `For input string`；数字格式可通过校验。
2. 但在**单货仓（一车一单）**机型下，同一舱存在多个任务被平台拒绝：`DLV_MGR_0009 操作舱位已存在任务`，机器人不动。
3. 多单连投需要平台机型货仓为**多料（≥2 货仓）**类型，当前机型（保温/大仓/双仓）均不满足用户"装更多商品"的需求；
   即便换也装不了"每一个点位更多订单/更多商品"，用户决定**不再依赖越凡的配货/配送任务接口**。

## 3. 召唤配送的目标流程（用户口述原话整理）

完全不使用越凡的配送任务接口（不创建 deliveryTask），仅用两个底层原语：**召唤(lightTask) 移动** + **drawerCtrl 开关舱门**。

完整流程：
1. 商家接单后点「上货」→ 机器人被**直接召唤到上货点**（`summonToLoadingPoint`）。
2. 商家点「打开舱门」→ 直接打开舱门（`drawerCtrl(deviceSn, 1)`）。
3. 商家点「关闭舱门」→ 关闭舱门（`drawerCtrl(deviceSn, 0)`）。
4. 关闭舱门后点「立即配送」→ **不用越凡接口**，用**我们现在新写的算法**召唤配送：
   - 用 `batch.planRoute` 按最近邻把点位排成顺序（第一个点位如「灵动库房」）。
   - 直接 `summonToPoint(store, deviceSn, 第一个点位)` 把机器人召唤到该点位并等待。
5. 小程序内同步更新：**该点位对应订单 → 状态置为「待取货(3)」**。
6. 用户来取：校验取餐码（`pickup_code` 归属校验，保留）→ `drawerCtrl(1)` 开舱 → 取走 → `drawerCtrl(0)` 关舱
   → 该单 `markOrderPicked`（置 4 已完成）。
7. **如果此楼栋没有该批次的订单了** → 等待 5 秒 → `summonToPoint` 到**下一个算法规划的楼栋/点位**。
8. 批次所有订单都取完 → `summonToLoadingPoint` 召回上货点等待。

> 关键点：机器人层面是**单次取货、无法排队送餐**；由小程序/后端算法在**首点任务下发 → 用户取完反馈 → 再下发下一点**之间推进，
> 不依赖机器人自身排队。中间**完全没有使用越凡的配送任务代码**。

## 5. 待实测的未知点（动工前必须先实锤，新对话第一步）

> 这是新的「DLV_MGR 级」风险，必须真机试探一轮才能动整个配送链路。

1. **`drawerCtrl(deviceSn, 1)` 在「机器人处于 lightTask（召唤停到配送点）、但没有任何配送任务」状态下，平台是否允许直接开舱？**
   —— 现有代码里 drawerCtrl 只在有关任务的开舱/关舱场景用过（close-bin、loadingConfirm 前的关舱）。需要真机确认纯召唤停点时能开舱。
2. **`summonToPoint` 到「取货点(deliverPoint)」是否稳定到达并保持等待**（lightTask 的 `wait` action、5 分钟 `expireTime`）——
   召唤会中断正在执行的配送任务，但召唤配送下没有配送任务，无冲突；5 分钟窗口对多单逐点是否够用需验证（可能需调长/重召唤）。
3. **"机器人已到点位"如何判定**（召唤模式下无任务状态可依赖）：需用 `getDevicePosition` 测距（点到 landmark 坐标距离）
   或机态变化，实现一个**点位到达门禁**（类似现有 `robotAtLoadingPoint`，但改为通用 `robotAtPoint(store, deviceSn, landmark)`）。

## 6. 实施方案建议（新对话可据此推进）

建议**保留批次模型**（仍按商品件数≤12组批、批次列表/上货页/配送监控/路线展示沿用），但把配送执行从
「创建 per-order 配送任务」改为「**批次 = 一组订单；机器人按路线逐点召唤 + 逐点开舱**」。

前置：先真机试探 §5 的 drawerCtrl 可达性，再动代码。

改动范围预估：
1. **platform.js**：
   - 新增 `summonDelivery(store, batch, nextStop)`（内部调 `summonToPoint`）与调度推进逻辑；
   - 新增点位到达门禁 `robotAtPoint(store, deviceSn, landmarkId)`（用 getDevicePosition + landmark pos 测距）；
   - `drawerCtrl` 确认/暴露开、关两个语义。
2. **backend/domains/delivery/routes.js + service.js**：重写 `/merchant/device/batch/*`（open-bin/close-bin/dispatch）
   和 `/delivery/pickup-*` 的取餐流程，改为「召唤 + drawerCtrl」驱动，并在到达某点位时把该点位订单置「待取货(3)」。
3. **次序推进**：`markOrderPicked` 后检查该点位是否还有本批次未取订单；若无 → `setTimeout(5000)` → 召唤下一点位。
4. **批次完成**：全部取完 → `summonToLoadingPoint` 召回 → 批次 3 已完成。
5. 前端：商家端上货页/批次详情、用户端取餐页/追踪页的状态文案与按钮，按"召唤配送"语义微调。
6. 保留取餐码校验（用户已确认要保留）。
