## 二、本段做了什么

1. **后端补齐删除能力**（`goods` 域，店主专属，落审计）：
   - `DELETE /merchant/goods`（入 `{id}`，404=商品不存在；也接受 `?id=` 兜底）
   - `POST /merchant/goods/batch-delete`（入 `{ids:[…]}`，上限 200 = 批量录入同一常量 `BATCH_MAX`；不存在的 id 只计入 `missing`）
   - 只删 `goods` 行：`order_items` 是下单快照（名称/图/价格都在行内），历史订单明细照常显示；
     `cart` 残留行不动 —— 用户端购物车 `cart.js` 按 `goods_status === 1` 过滤（LEFT JOIN 后为 NULL），既不显示也进不了结算。
2. **商家端商品列表页加「删除」**（仅店主可见，红色二次确认，文案说明不可恢复/历史订单不受影响）+ `utils/api.js` 两个接口定义。
3. **`backend/tools/goods_cleanup.js`**：给部署的人一条命令清演示种子商品。默认**只预览**，`--apply` 才真删；
   删前 `VACUUM INTO` 备份到 `data/lingdong.db.bak_before_goods_cleanup_<时间戳>`；删后直接打印
   **「删除后商品总数 + 还有多少商品没有图片 + 逐个列出」**（正好是用户要的统计）。带安全闸：命中数 == 库内总数时拒绝执行（说明是空库/路径不对）。
4. **`db.js` 抽出 `DEMO_GOODS` 常量**并导出，`seed()` 与清理工具共用同一份名单（避免两处各写一份）。
5. **新增回归测试 `backend/tests/test_goods_delete.js`**（第 12 个），覆盖：店主删除、店员 403、缺参 400、不存在 404、
   订单快照不受影响、购物车残留行 `goods_status=null`、批量删除 + `missing`、审计留痕、总数与无图统计。
6. **文档同步 6 处**：`doc/06_接口与数据协议/04_商家接口.md`、`01_用户与商品接口.md`、
   `doc/05_页面与交互详解/商家端/15_商品管理-goods-list.md`、`doc/01_产品与页面总览.md`（两处）。

## 五、被否决 / 明确不动的方案

- **「你给我 SSH 密码，我直接改云端库」**：用户没选这条，改走 git 交付；我没再尝试其它远程改库的路子（也没有可用凭据）。
- **只「下架」那 10 条**：用户要的是删除；下架商品在商家端仍占一行、还会被批量录入按条码当「已存在」跳过，等于没清干净。
- **连购物车残留行一起删**：用户明确选「只删 goods 行，历史订单/购物车引用保留不动」。实测残留行在用户端确实不会显示
  （`goods_status=1` 过滤），所以保留是安全的。
- **店员也能删商品**：删除商品保持**店主专属**（与新增/编辑/批量录入同权限），店员误删整店商品的代价太大。
