## 二、核心设计（后面看代码先看这几条）

1. **`shop_id DEFAULT 1` 的透明兼容**：所有存量商品/订单/活动/券默认归 1 号店；老接口、老小程序不传店铺参数时自然落到 1 号店。所以"多店能力是加出来的，不是换掉的"——迁移前后老客户端行为完全不变。
2. **一个账号一家店**：`shop_members(shop_id, user_id, role)` 是权威归属，`users.merchant_role` 保留为兜底（只插了 merchant_role 的老测试账号仍落到 1 号店）。`merchantGuard` 统一把 `req.shopId` / `req.shopRole` 塞进请求，各域只读这两项。
3. **跨店一律 404，不是 403**：不告诉对方"这东西存在但你没权限"，避免用 id 试号探测别人家的订单/批次。
4. **跨店结算在三个入口统一拦**：`用户端/utils/shop.js` 的 `toConfirm()` 是唯一入口（首页底部栏、商城底部栏、购物车页都走它），弹窗明说哪两家店不能一起结算。后端 `createOrder` 还会再校验一次商品归属（防绕过）。
5. **一家店一趟车**：`delivery_batches.shop_id`；批次列表、详情、派车、开/关舱、删除、待上货列表、监控全部按店收口。`stops` 列只是预埋，多点停靠没实现（平台也没有该能力）。
6. **大屏单店时"看起来没变"**：店铺概览、分店小字、批次店名后缀、事件店名前缀，全部只在 >1 家店时出现。

## 四、本机环境上的两个坑（下一轮必看）

1. **3000 端口被占**：本机 `gitfox.exe`（跑在 Session 0 的系统服务，`CreationDate 2026-10-23 08:10`）监听 3000，后端 `node server.js` 会直接 `EACCES: permission denied` 退出。这一轮跑大屏探针时后端改起在 **3010**（`$env:PORT='3010'`）。
   - 为此给 `verify_keys / verify_layout / verify_touch / verify_fix` 加了 `DASH_BASE` 环境变量支持（不设时仍是 3000，行为不变）。
   - 用法：`$env:DASH_BASE='http://127.0.0.1:3010'` 再跑探针。
   - **要不要把那个服务停掉、或者换端口，需要负责人决定**，我没动它。
2. **别用 pilot 真平台档做探针**：第一次起后端用的是 `.env` 原样（pilot + 真平台），启动就把点位同步打到生产平台，还对着真车 `R110A2603AUEQC00` 反复重试召唤（卡在 9 月 25 日的老批次 `BD-260925-003`，状态"待上货"）。后来改成 `PLATFORM_MOCK=true` 才跑探针。
   - 附带发现：**只要库里存在"待上货"的老批次，后端每次启动都会持续重试召唤**。那个批次建议清理掉，否则每次本机起后端都会打平台。
