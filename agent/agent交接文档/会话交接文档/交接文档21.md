## 二、已核实的结论（都有实测证据）

### 2. "想回充电桩"的真正机制：**平台把我们的召唤判成失败(50)，失败后车按分组策略回桩**

只读采样（2.5 分钟，6 条召唤）模式完全一致：

```
创建 → 10 已接受 → 20 前往中 → 50 失败（6~16 秒）→ 车 = returnChargingPile
约 30 秒后我们的守候又续一条 → 再失败 → 再回桩 ……（电量 99% → 98%）
```

- 轻任务状态字典（`doc/07` §3.3）：0 排队 / 10 已接受 / 20 前往中 / **30 到达** / 40 完成 / **50 失败** / 60 删除。**没有一条走到 30**。
  （注意别和配送任务的状态字典混：配送任务 50 = 已上货。）
- 所以**不是**"到达后等超时自动返程"（那才是平台轻任务的正常语义：`expireTime` 到点自动返程）。
- **平台不返回失败原因**：`GET /open-api/v1/lightTask/{id}` 报文里只有 `status`，没有错误码/原因字段（已把整份 JSON 打出来核对）。
- 我们代码里**原本没有**"30 秒回充电"这种东西：所有回桩窗口都是分钟级 —— 上货点待命 5 分钟（`expireTime` 与 `action.waitTime` 必须一致，即 issue2 的修法）、无单释放 3 分钟（`SUMMON_RELEASE_WAIT_MIN`）、配送停靠站 20 分钟（`SUMMON_STOP_EXPIRE_MIN`）。唯一的 30 秒是**重发节流**。
- 机器人分组配置（平台侧，`extInfo`）：`returnStrategy=standby`、`lowPowerThreshold=20`、`loadingWaitingTime=1200`、工作时段 05:00–23:00。**回桩是"任务结束+分组策略"的结果，不是越凡偷偷加的 30 秒定时器。**

### 3. "手动召唤能待住、自动召唤待不住"的差别不在时间窗口

管理员网页「召唤」走 `summonToPoint`（`admin/routes.js:355`），**没传窗口 → 也是默认 5 分钟**，和自动召唤（`summonToLoadingPoint`）**同一口径**。所以差别只可能在：①目标点不同；②我们每 30 秒重发一次（平台语义：新建召唤会打断当前任务、重置导航）。

### 4. 已上线的止血改动（提交 `56a71fb`，部署版本 `20261012-181106`）

- `timers.js` 守候逻辑抽成 `keepLoadingSummon`（可单测）+ **连续失败熔断**：召唤任务"没到过 30 就进终态"算一次失败，连续 `SUMMON_LOADING_KEEP_MAX_FAILS`（默认 3）次 → **停止自动重发** + 写 `meta.summon_keep_alert:<车号>`；车真到达过(30) 或批次不再等上货 → 自动清零清告警。重发节流改为可配 `SUMMON_LOADING_KEEP_TRY_MS`（默认 30s；**设 1 = 只发一次**，排查隔离档）。
- `admin/queries.js` + `admin/service.js`：总览 alerts 增加"上货点召唤连续失败"红字告警。
- 新增 `tests/test_summon_keep_breaker.js`（19 项断言）+ 既有 11 个测试，**全绿**。
- **线上核对（18:11:32）**：日志出现`上货点召唤连续失败 3 次，已停止自动重发`；`meta` 出现 `summon_keep_alert:R110A2603AUEQC00 = {"fails":3,…,"batch_no":"BD-261012-002"}`；此后**再无新召唤**（18:11:35 之后 `保持在上货点` 0 条），批次 `light_task_id` 停在 18:11:12 不再变 → **车不再来回跑、空耗电**。
