## 4. 关键架构：配送流程（本次重构核心，接替者必须理解）

```
用户下单 → 商家接单（自动/手动）→ 订单并入开放批次（组单，多单合并，12 件上限）
  → 扫描(15s)检测到订单 → 召唤机器人到上货点待命（lightTask，不创建任务、不锁批次）
  → 商家端「配单上货」红点 = 待配单订单数（非批次数）
  → 商家进配单上货页，点批次「上货(N件)」→ 组单中批次此刻才定型（doDispatchBatch 创建平台任务）
  → 上货页：开舱 → 上货 → 关舱 → 弹「是否立即配送」
      ├─ 是：舱门关闭后立即配送（loadingConfirm）
      └─ 否：显示圆形「开始配送」按钮
  → 机器人规划多单路线 → 配送 → 送达 → 用户扫码取餐
```

### 关键代码位置

- **召唤**：`platform.summonToLoadingPoint(store)`（platform.js，POST `/open-api/v1/lightTask`，选空闲车；扫描调用在 server.js `setInterval`，BATCH_SCAN_MS 默认 15s）
- **上货定型**：商家端 `loading.js selectBatch`（status=0 批次先 POST `/merchant/delivery/batch/dispatch` 再进 batchDetail）；后端 `doDispatchBatch`（server.js ~1226，CAS 抢占 status 0→1）
- **关舱配送**：`batchDetail.js closeBin/dispatchAll`；`dispatchAll` 前置校验 `phase==='loaded'`（**舱门开着禁止移动**，安全逻辑勿删）
- **红点**：`orders/list.js loadPendingCount` + `device/pending` 返回 `pending_orders`；`shop/home.js` 底部角标同源
- **自动拆单**：`server.js /api/order/create` + `splitOrderChunks`；前端 `order/confirm.js`（超 12 件提示 + 逐个支付 + 跳订单列表）

## 5. 平台实测结论（写进逻辑树图四，接替者勿违背）

1. **排队任务 queue/create**：完整上货流程，但**机器人充电中不拉取**（机器人待机自动回充电桩 → 排队任务永远等不到车）
2. **直接下发 create/direct**：充电中能执行，但**语义 = 货已在舱**（busyStocks 占用）→ loadingVerify 报「机器人当前不在取货阶段」；且机器人去上货点会**卡住转圈**（已紧急关闭过）
3. **drawerCtrl 可独立开关舱门**（不受任务状态限制）
4. 结论：派车走 **queue/create（排队）+ lightTask 召唤待命 + 商家点上货按钮定型**。**不要改回 create/direct**

## 8. 工具与坑（重要）

- **临时脚本模式**：写 `backend\_xxx.js` 用 node 跑，**跑完必删**（保持工作区干净）。不要用 pwsh 内联 `node -e` 跑含 `IN (1,2)` 这类 SQL（pwsh 引号会吃括号）——必须用临时 .js 文件
- **pwsh 的 workdir**：每次新进程，cwd 不保留，务必传 `workdir`；git 路径相对仓库根
- **git 约定**：**默认不 push**（用户明说才推）；GitHub 网络慢，push 可能超时/要 GCM 认证，前台重试会弹认证框
- **回归测试教训**：**不要多次 edit `test_batch_flow.js`**——曾因多次编辑破坏文件导致"运行无输出但静默 exit 0"（语法检查通过、require 正常，但 IIFE 不执行）；恢复 git 版本后正常。改它务必一次性整体改 + 立即试跑
- **数据库**：node:sqlite **无 transaction**，多步骤写入不会自动回滚；扣库存等用条件更新（`WHERE stock>=?`）防超卖
- **日志已精简**：派车/召唤/轮询忽略日志已静默，启动摘要保留；不要加回刷屏日志
- **后端端口**：3000（生产）；回归 3100；临时验证 3200/3201
