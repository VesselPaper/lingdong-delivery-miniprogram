## 一、这份方案要解决什么

现在的小程序在用户眼里是"一家店"：首页就是「零栋铺子」，商品是这家店的，活动是这家店的，下单就送到楼栋点位，一辆车从唯一的商铺上货点出发。这套东西跑通了一单到底的全链路，但它的形状是**单店自营**。

要往美团靠拢、要接校外商家，真正要改的不是"多加几个页面"，而是三件事：数据得能按店归属、车得能服务多个取货点、钱得能合规地分给不同主体。这三件事里前两件是技术，第三件是资质与资金，后者比前者贵得多，且不可绕。

本方案给出的判断是：**分三期做，一期只做"多店地基"（数据归属 + 按店分批发车），不做跨店购物车、不做自助入驻、不做分账**。一期做完，接第二家校内店不需要再改表；二、三期再把体验和平台能力补上。

## 二、现状：七条"单店假设"

以下每条都在代码里核过，不是推测。这七条是扩容时必须逐条拆掉的东西。

| 编号 | 现状假设 | 代码出处 | 卡住哪个方向 |
| --- | --- | --- | --- |
| S1 | 全库只有一家店 | `shops` 表存在但只有一行；`backend/domains/goods/queries.js:45` 固定 `SELECT * FROM shops WHERE id=1`，`:46` 更新也写死 `id=1` | 多商家 |
| S2 | 商品 / 活动 / 券没有店铺归属 | `goods`、`activities`、`coupons` 三张表都没有 `shop_id`（`backend/db.js:56`、`:143`、`:162`）；商家端列表 `merchantList` 直接 `SELECT * FROM goods` 全表返回 | 商家隔离、按店对账 |
| S3 | 订单不记店铺，也不记取货点 | `orders` 表无 `shop_id`、无 `pickup_landmark_id`（`backend/db.js:79-99`）；下单只校验商品存在与库存 | 拆单、按店退款、结算 |
| S4 | 一个批次只有一个取货点 | `delivery_batches.loading_landmark_id` 是单值字段（`backend/db.js:115`）；`backend/services/points.js:58 loadingPointRow()` 全库取第一条上货点，`batch.js` 四处（`:331`、`:503`、`:713`、`:919`）都调它 | 多商家多取货点 |
| S5 | 只有一个收款商户号 | `backend/services/wxpay.js:11` 全局 `WXPAY_MCHID`，请求体无 `settle_info`、无分账接收方 | 校外商家资金合规 |
| S6 | 没有校区实体 | `landmarks.building` 里存的是字符串「四川师范大学成龙校区」（`backend/db.js:633-642`）；表结构里没有任何 `campus_id` | 多校区（后期） |
| S7 | 商家账号可以多开，但数据不隔离 | `users` 表用 `role='merchant'` + `merchant_role='owner'/'staff'` 表示商家（`backend/db.js:29`），管理员网页能建任意多个（`domains/admin/routes.js:748`），但它们操作的是同一份商品、同一份订单 | 最容易误判的一条 |

**S7 要单独强调**：现在管理员网页确实能建多个商家账号，看起来像"已经支持多商家了"。实际只是"多个人共管一家店"——所有账号看到的商品和订单完全一样。接第二家店时，这条会立刻暴露成"B 店能改 A 店的商品"。

**结论**：扩容的工作量不在页面，在"给已有四张表补归属列"以及"让所有商家视角的查询都带上归属条件"。

## 三、扩容要跨过的三道门槛

**第一道 · 数据归属（技术，可控）**
给 `goods` / `orders` / `activities` / `coupons` 补 `shop_id`，把"全表"查询改成"按店"查询。听起来是加一列，实际难点在存量数据迁移和"漏改一处就串店"——全后端涉及 `orders` 的 SQL 约 120 处（`domains/` 下 75 处），不可能全局替换，必须按"这是谁在看、在看谁的数据"逐处判断。

**第二道 · 履约（技术 + 供应商依赖）**
一辆车现在的行程是固定的：从唯一上货点装货 → 依次送楼栋。多家店意味着多个上货点，车要"先去 A 店装、再去 B 店装、然后送"。而现在的平台**不支持多点停靠**（《交接文档 29》§三已核实：一批订单 = N 个独立任务，`priority` 仅提示、不影响目的地）。

所以一期只能用**按店分批发车**来绕开：一车只服务一家店，算法不动，只把"上货点"从"全库一条"改成"按店取"。代价是车次变多、装载率下降——在只有 1～2 台车的阶段，这是可接受的；真要多点取货，得等新供应商的底盘能力，这条已经写进《03_给下家公司的要求清单》。

**第三道 · 资金与资质（业务/法务，最贵）**
校外商家如果是**独立主体**，钱就不能"全部收到我们商户号再转给商家"——这是二清（二次清分），监管和支付机构都会查，最坏的结果是资金被冻结、账户被停。合规路径只有两条：微信支付**服务商模式 + 分账**（我们做服务商，商家做二级商户），或者让商家自己进件、各自收款。这两条都需要资质与时间，不能用代码绕过去。

同时，变成"多商家平台"会改变小程序的类目属性：自营外卖和多商户平台在微信侧的资质要求不同，餐饮类还要逐店核《食品经营许可证》。这件事必须在上线前问清楚，不是开发能决定的。

## 四、对照美团，我们缺的是哪几层

把美团拆成六层能力，逐层对照现状，能看清"靠拢"到底要做多少、先做哪个。

| 能力层 | 美团有 | 我们现在 | 差距 | 排期 |
| --- | --- | --- | --- | --- |
| 供给 | 多店、店内分类、SKU 规格、库存、营业时间、配送范围 | 一家店、商品有 `category` 字符串、有库存、有营业状态 | 店铺实体、规格、配送范围 | 一期 / 二期 |
| 交易 | 按店购物车、跨店结算、拆单、起送价、打包费、配送费、优惠叠加 | 单店购物车、有优惠券与活动、有配送费（`shops.delivery_fee`） | 拆单、按店计费、优惠叠加规则 | 一期（地基）/ 二期（规则） |
| 履约 | 骑手抢单、多点取送、超时补偿 | 机器人固定路线、单取货点、单批次 12 件、超时二段驳回退款 | 多取货点（受供应商限制） | 一期（按店分批）/ 三期（多点） |
| 用户 | 首页推荐、分类导航、搜索、店铺页、评价、收藏、客服 | 首页单店、搜索、活动页、订单、售后、地址 | 店铺列表/详情、评价、收藏 | 二期 |
| 商家 | 自助入驻、资质审核、经营数据、结算对账 | 管理员手工建账号、有商品/订单/活动管理 | 入驻流程、结算单、经营看板 | 二期 / 三期 |
| 平台 | 多城市、分账、佣金、风控 | 单校区、单商户号、无佣金 | 校区、分账、佣金 | 三期 |

**判断**：三期里真正决定"能不能接第二家店"的只有"供给 + 交易"的前半段，也就是一期的数据归属。其余都是"接了店之后好不好用"，可以慢慢补。

## 五、三期路线图

### 一期 · 多店地基（目标：能接第二家校内店，业务形态不变）

不新增页面功能，只把数据从"单店"变成"多店"，并且**老版本小程序不传店铺参数时默认落到 1 号店**，避免线上白屏。

验收标准（缺一不可）：

1. 新增 `test_shop_isolation.js`：A 店账号看不到、改不了 B 店的商品/活动/订单/批次，测试全绿。
2. 既有 19 个回归测试全绿（`backend/tests/test_*.js`，2026-10-23 实测 19 个）。
3. 迁移脚本在**本地库副本**上演练通过：迁移前后行数、金额合计一致，可回滚。
4. 用户端、商家端在微信开发者工具真机各跑一遍完整下单链路。
5. 可视化大屏同步改完：`verify_keys.mjs` + `verify_layout.mjs`（+ `verify_touch.mjs` / `verify_fix.mjs`）在真实浏览器跑通、0 console 报错、服务器地图数据校验一致（见 §八）。
6. 云上部署仍可用 `rollback.sh` 退回 `20261019-233008`（现网版本）。

### 二期 · 对齐美团体验（目标：用户能"逛店"，商家能自助）

- 用户端：店铺列表页、店铺详情页、按店搜索、评价与晒单、收藏、客服入口、分包加载
- 交易规则：起送价、打包费、按店配送费、平台券与店铺券的叠加与互斥顺序（**这一条必须先定规则再写代码**，否则后期每个活动都要打补丁）
- 商家端：资质上传与审核、经营数据（单量/客单/退款率）、结算单（`settlements`）
- 履约：多取货点路径（取决于新供应商是否支持多点停靠）

### 三期 · 平台化与多校区（目标：复制到第二所学校）

- `campuses` 表与全链路校区维度（这一期才做，不提前预埋字段）
- 分账、佣金、提现
- 混合运力：校外商家 → 校门口中转点 → 机器人接驳，或骑手直送
- 新业务线：快递代取、跑腿（见 §九 关于 `biz_type` 的说明）

## 六、一期的数据模型与改动清单

### 6.1 表结构（一次性改完，避免二次迁移）

```sql
-- shops 从"一行"变成"多行"
ALTER TABLE shops ADD COLUMN code TEXT DEFAULT '';              -- 店铺短标识（用于分享、二维码）
ALTER TABLE shops ADD COLUMN logo TEXT DEFAULT '';
ALTER TABLE shops ADD COLUMN category TEXT DEFAULT '';          -- 餐饮/超市/水果/快递代取
ALTER TABLE shops ADD COLUMN address TEXT DEFAULT '';
ALTER TABLE shops ADD COLUMN pickup_landmark_id TEXT DEFAULT ''; -- 本店取货点（landmarks.id），替代全局唯一上货点
ALTER TABLE shops ADD COLUMN min_order REAL DEFAULT 0;          -- 起送价
ALTER TABLE shops ADD COLUMN pack_fee REAL DEFAULT 0;           -- 打包费
ALTER TABLE shops ADD COLUMN owner_user_id INTEGER DEFAULT 0;   -- 店主账号（users.id）

-- 四张表补归属
ALTER TABLE goods      ADD COLUMN shop_id INTEGER DEFAULT 1;
ALTER TABLE orders     ADD COLUMN shop_id INTEGER DEFAULT 1;
ALTER TABLE orders     ADD COLUMN pickup_landmark_id TEXT DEFAULT ''; -- 下单时快照，避免店改了取货点导致历史单错乱
ALTER TABLE activities ADD COLUMN shop_id INTEGER DEFAULT 1;         -- 0 = 平台级活动
ALTER TABLE coupons    ADD COLUMN shop_id INTEGER DEFAULT 1;         -- 0 = 平台券

CREATE INDEX IF NOT EXISTS idx_goods_shop  ON goods(shop_id, status);
CREATE INDEX IF NOT EXISTS idx_orders_shop ON orders(shop_id, status, created_at);
CREATE INDEX IF NOT EXISTS idx_acts_shop   ON activities(shop_id, status);
```

`DEFAULT 1` 是给存量数据兜底：现有全部商品、订单、活动都归 1 号店（零栋铺子），迁移只需要一次 `UPDATE ... SET shop_id=1 WHERE shop_id IS NULL`，并且老接口不传店铺参数时自然落到 1 号店。

### 6.2 商家成员表（替代 `users.merchant_role` 单点归属）

```sql
CREATE TABLE IF NOT EXISTS shop_members (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  shop_id INTEGER NOT NULL,
  user_id INTEGER NOT NULL,
  role TEXT DEFAULT 'staff',        -- owner / staff
  created_at TEXT DEFAULT (datetime('now','localtime'))
);
CREATE UNIQUE INDEX IF NOT EXISTS idx_shop_members ON shop_members(shop_id, user_id);
```

迁移策略：**双写一版**。旧字段 `users.merchant_role` 继续读写，同时写 `shop_members`；等商家端全部改成从 `shop_members` 取当前店铺后，再删旧字段。这样任何一步都能回退。

## 七、履约层的现实约束（与换供应商的关系）

这条必须写清楚，因为它决定了"多商家"能到什么程度。

现在的派车逻辑是：批次成型 → 取全局唯一上货点 → 一辆车去装 → 按楼栋送。多家店就有多个上货点，而平台**没有多点停靠能力**。所以：

- **一期（换供应商之前）**：一车一店，按店分批发车。多店时车次线性增加，装载率下降。1～2 台车、日均几十单的量级，这个损失可以接受。
- **三期（新供应商落地后）**：如果下家支持"多点取货 + 多点送达"（《03_给下家公司的要求清单》接口部分已列），再把批次结构从"单取货点"升级为 `stops` 数组：

```json
[
  { "type": "pickup", "shop_id": 2, "landmark_id": "lm-05", "order_ids": [101, 102] },
  { "type": "pickup", "shop_id": 3, "landmark_id": "lm-09", "order_ids": [103] },
  { "type": "drop",   "landmark_id": "lm-01", "order_ids": [101, 103] },
  { "type": "drop",   "landmark_id": "lm-02", "order_ids": [102] }
]
```

一期的 `delivery_batches` 建议就按 `stops` 的形状预留（JSON 字段），但**只写一个 pickup**。这样三期改算法时不用再改表结构。这是唯一一处"提前留形状"，因为它的成本只是"写入时写成数组"，不引入任何新逻辑。

另外，校外商家还有一个物理约束：机器人出不了校园。校外商家合作的产品形态只有三种——送到校门口中转点、骑手接驳、或干脆只做"校内自营供货"（校外商家供货给我们、我们仍是唯一卖家）。**这个选择直接决定要不要做多商家**，见 §十三 第 1、2 条。

## 八、可视化大屏的同步改造

大屏（`可视化大屏/`）不是独立系统：它读的是后端 `/api/dashboard/overview` 这一个聚合接口，数据源和小程序完全同源。所以多店改造必须同步——否则小程序里已经有两家店，大屏挂墙上还写着「零栋铺子」，运营看到的营业额是所有店混在一起的数，出问题也没法定位到店。

### 8.1 大屏现在的单店痕迹（代码核实）

| 位置 | 表现 | 出处 |
| --- | --- | --- |
| 页头标题 | 硬编码「零栋铺子 · 无人送餐调度大屏」，不随数据变 | `index.html:21` |
| 左栏「运行状态」 | 显示**一家店**的 店铺 / 营业状态 / 自动接单；取不到时兜底写死「零栋铺子」 | `index.html:34-41`、`js/dashboard/views-ui.js:31-40` |
| 后端聚合 | `buildDashboard` 里 `shop: q.shopRow(store)` 取 `WHERE id=1` 那一家 | `backend/domains/admin/service.js:168` |
| 统计口径 | `stats`（今日订单/营业额/完成）、`batches`、`pickup_alerts`、`log_events` 都是**全平台混合**，没有店铺维度 | `backend/domains/admin/service.js:164-186` |
| 批次卡 | 只显示 批次号 / 状态 / 在途 / 待取 / 设备尾号，看不出是哪家店的批次 | `js/dashboard/views-ui.js:170-179` |
| 地图图例 | 「上货点」只有一个图标，多店后地图上会同时出现多个上货点，分不清车是去谁家装的 | `index.html:75-80` |
| 实时动态 | 事件文案不带店名 | `js/dashboard/views-ui.js` 的事件渲染块 |

数据链路只有一条：`/api/dashboard/overview`（5s 轮询 + 后端 5s 缓存）→ `js/dashboard/api.js` → `main.js` 的 `apply()` → `views-ui.js` 各 `render*`。另外三个接口 `robot-positions`（1s）、`virtual-robot`（控制）、`recon`（3D 图层重构存档）与店铺无关，**本次一行都不用改**。

### 8.2 改造原则：大屏是挂墙上的，不做筛选

大屏的使用场景是办公室墙上常亮，没有人会走过去点筛选。所以一期**不加大屏端的店铺切换器**，而是改成"全局看板 + 每处都带店铺标识"：一眼能看出总量、也能看出这单/这批是哪家店的。

| 部分 | 一期改法 | 二期可选 |
| --- | --- | --- |
| 页头标题 | 去掉店名，改成「零栋 · 校园无人配送调度大屏」 | — |
| 左栏「运行状态」→「店铺概览」 | 列出所有营业中的店：店名 + 营业状态 + 今日单量；**只有一家店时自动退化成现在这一行**（不改变现有观感） | 触屏点某店 → 全屏只看该店 |
| 订单看板 | 大字仍是全平台总计，下面加一行分店小字（如「零栋铺子 12 · 东苑超市 5」） | 点店名下钻 |
| 批次卡 | 标题后加店铺名（「批次 B-07 · 东苑超市」），一眼区分 | 按店配色 |
| 地图图例 | 「上货点」旁标注店名，或按店给上货点标记换色 | 只看某店时高亮其取货点与路线 |
| 实时动态 | 事件文案前缀店名（「东苑超市 · 订单 #1023 已送达」） | — |

### 8.3 接口与文件改动（一期）

后端只扩字段，**不新增接口**——多一次轮询就多一次压力，而大屏本来就在 5s 一次地打这个聚合接口。

| 文件 | 改什么 |
| --- | --- |
| `backend/domains/admin/service.js` | `buildDashboard` 增加 `shops: [{id,name,business_status,today_orders}]`；保留 `shop` 字段（取 1 号店）供老版本前端与其它消费方兼容；`stats` 加 `by_shop` |
| `backend/domains/admin/queries.js` | 新增 `shopsAll`；`activeBatchesOverview` 增加 `shop_id` / `shop_name` |
| `可视化大屏/index.html` | 页头标题去店名；左栏「运行状态」面板改成可容纳多行的「店铺概览」（一行一店）；图例文案 |
| `可视化大屏/js/dashboard/views-ui.js` | `renderRunState`（现为单店三行）→ `renderShops`（一行一店，单店时走原样式）；`renderBatches` 加店名；事件渲染加店名前缀 |
| `可视化大屏/js/dashboard/main.js` | `apply()` 把 `shops` 传给视图；单店/多店分支 |

改完前端 JS 必须 bump `index.html` 里对应文件的 `?v=` 版本号，否则大屏机上的旧缓存不会刷新（这是零构建项目的固定动作，漏了会出现"改了没生效"）。

### 8.4 大屏不可触碰的部分

这几条是硬约束，扩容改造一律绕开：

- **3D 地图本体不动**：`js/map3d-gl.js`（2180 行）、`js/scene3d/`、`js/gl3d/recon.js`、`assets/map-calibration.js` 一行不改。多店只影响"面板文案与统计口径"，不影响几何。
- **青色导航线 / 吸附网绝不动**——那是机器人的固定行驶规则。
- **虚拟车控制、地图重构存档（`/api/dashboard/recon`）不动**。
- **验收口径按现有基线走**：`node "_tmp4\probes\verify\verify_keys.mjs"` + `verify_layout.mjs`（+ `verify_touch.mjs` / `verify_fix.mjs`）在真实浏览器跑通、**0 console 报错**，并确认服务器地图数据被原样还原（探针末尾会打印「校验一致 true/false」）。`node --check` 不算验证。
- **`configs/default.js` 不接入**：里面的 `campus` 字段是多校区预留模板，三期做多校区时再说，现在不要往 `index.html` 加它的 script。

### 8.5 与「按店分批发车」的联动

一期履约是"一车一店"，所以同一时刻屏上可能出现两个批次、两台车、两个上货点。地图上必须能区分：批次卡显示店名（8.2）、上货点标记按店区分（8.2）、车辆卡本来就有设备尾号。**路线颜色区分留到二期**——一期改动越小，越不容易碰坏 3D 渲染。

### 8.6 大屏的工期

一期大屏部分约 **0.5 人周**（后端扩字段 0.2 + 前端五处渲染 0.2 + 探针回归 0.1），已计入 §十一 的一期估算里，不额外占排期。

## 九、明确不做的事

| 不做 | 原因 |
| --- | --- |
| 跨店购物车 / 跨店合并支付 | 会连锁引爆拆单、按店退款、优惠分摊、配送费拆分、配送路线合并五件事，收益极低。美团早期也是"一家店一单"。一期只做单店结算 |
| 提前做多校区（`campuses` 表、租户隔离） | 项目既定"不提前实现多租户"。三期需求明确时再加表加列，SQLite `ALTER TABLE` 成本很低 |
| 换数据库 | SQLite WAL 在单机、日单量千级以内足够。触发条件写死：**日单量稳定超过 2000 单，或需要多台后端并发写**，再评估 PostgreSQL |
| 微服务化 / 拆进程 | 一个 Node 进程 + 六个域现在很好维护。多商家是"加列 + 加过滤"，不是"拆分服务" |
| 现在就做分账 | 技术上一期不做；但**校外商家上线前必须完成**，这是硬闸门，不是可选项 |
| 把大屏重做一遍 / 做店铺切换器 | 大屏是挂墙常亮的运营看板，没人会去点筛选。一期只加标识（见 §八），3D 与既有布局都不动；触屏下钻留到二期 |
| 让商家端"前端过滤"代替后端隔离 | 前端过滤等于没有隔离，B 店改个包就能看 A 店数据 |

关于新业务线（快递代取、跑腿）：这类订单没有商品明细，只有"取件点 → 送达点 + 计件费"。建议**一期不动**，但在一期改表时顺手加一列 `orders.biz_type TEXT DEFAULT 'goods'`（`goods` / `service`），以后加服务单就不用再动表。这同样只是留形状，不引入逻辑。

## 十、风险与合规

| 风险 | 触发条件 | 后果 | 应对 |
| --- | --- | --- | --- |
| **二清**（P0） | 校外商家（独立主体）的货款先进我们的商户号，再由我们转给商家 | 支付机构风控、资金冻结、监管处罚 | 走微信支付服务商模式 + 分账，或商家自己进件。**校外商家上线前必须完成** |

| 1 | 多商家是"平台入驻"还是"我们自营多门店" | A. 平台：商家自己管店、自己收钱（需分账 + 资质 + 审核）<br>B. 自营：商家只供货，我们仍是唯一卖家 | 一期按 B 做（不动资金链路），把 A 留到三期。B 能覆盖"校外商家合作"的大部分诉求，且不碰二清 |

### 14.3 与方案的偏差（要如实记）

1. 大屏页头**最终按方案去了店名**（早前一版曾把店名放进标题，与 §8.2 冲突，已改回）。
2. 用户端"店铺入口"没有做独立页面，而是**首页店名处点开 ActionSheet 切店**（只有一家店时连"切换"字样都不显示）。理由：一期目标是"能接第二家校内店"，专门做一个店铺列表页属于二期「逛店」。
3. 本机 3000 端口被一个 `gitfox.exe`（系统服务）占用，跑大屏探针时后端临时起在 **3010**。为此给四个基线探针加了 `DASH_BASE` 环境变量（默认仍是 3000，行为不变）。**本机以后跑探针前先确认 3000 是否被占**。

### 14.4 一期的已知遗留（不影响"能接第二家店"，但要排进二期）

- **管理员网页还没有店铺管理界面**：建店/改店/绑定店主的**接口已就绪**（§14.1「建店入口」），但管理员网页 `管理员网页/js/parts/admin/` 里没做面板，现在只能用接口（`curl` / 后端工具）建店。方案 §6.3 把这项标为"需人工回归"，所以留到有界面需求时再补。
- 用户端还没有店铺列表页/店铺详情页，"逛店"体验没有；商品搜索仍是单店内搜索。
- 起送价 / 打包费**只落了库与设置页，还没进计价链路**（下单金额计算仍只有配送费 + 活动 + 券）。这属于二期「交易规则」，要先定规则再写代码。
- 一辆车一趟只服务一家店，多店时车次线性增加；`delivery_batches.stops` 只预埋了列，没有实现多点停靠。
- 跨店售后、按店退款分摊未做（一期不跨店下单，暂时用不到）。
- 校内两家店以上就要考虑"上货点是否够用"（一个上货点只能停一台车）。
