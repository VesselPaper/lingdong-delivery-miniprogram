# 03 · 数据库设计

最后更新：2026-09（以 `backend/db.js` 为准）
数据库：SQLite 单库（`node:sqlite` 内置驱动），库文件 `backend/data/lingdong.db`。
建表、迁移、种子数据、商品导入全部集中在 `backend/db.js`（入口 `init()`）。

---

## 1. 总览

### 1.1 单库说明

- 整个后端只使用一个 SQLite 数据库文件，无分库、无独立缓存库；WAL 日志模式（`PRAGMA journal_mode = WAL`），读多写少场景下读写并发更好。
- 时间一律用 SQLite 本地时区 `datetime('now','localtime')` 写入（`created_at` 等），与编号取号、会话过期时间共用同一时钟源，避免 Node 与 SQLite 时区漂移。
- 金额类型为 `REAL`（元）；涉及优惠计算时后端以「分」为单位换算（见 `backend/services/promotion.js`），落库仍是元。
- 表间关联为**逻辑外键**：SQLite 建表未声明 `FOREIGN KEY` 约束，关联靠 `xxx_id` 列 + 应用层维护；删除/一致性由代码保证。

### 1.2 数据库文件位置与覆盖

| 项 | 说明 |
| --- | --- |
| 默认路径 | `backend/data/lingdong.db`（`data/` 目录启动时自动创建，目录被 `.gitignore` 忽略） |
| 覆盖变量 | 环境变量 `LINGDONG_DB` 可指定其他路径（多实例/测试隔离用），相对路径按进程工作目录解析 |
| 驱动 | `node:sqlite` 的 `DatabaseSync`（Node 内置，同步 API，单线程串行执行） |

### 1.3 建表与迁移策略（幂等）

启动时 `init()` 依次执行，全部幂等，可重复启动：

1. **建表**：所有 `CREATE TABLE IF NOT EXISTS ...` 一次执行（初次启动建齐 21 张表）。
2. **补列**：`migrate()` 对每张旧表用 `PRAGMA table_info(表名)` 探测已有列，缺哪列补哪列（`ALTER TABLE ... ADD COLUMN`），老库升级无需重建表。
3. **数据修正/回填**：历史 `daily_seq`、`seq_date` 按创建日期回填；同日序号去重；地址 `landmark_id` 规范化（`"2.0"` → `"2"`）。
4. **一次性修正**：通过 `meta` 表标记（如 `merchant_role_reset_at`），避免每次启动重复执行不可逆操作。
5. **种子数据**：仅当对应表为空时写入（shops / landmarks / goods）。
6. **商品导入**：`store_goods.json` 存在且 sha256 变化时整体替换 `goods` 表（见第 9 节）。

## 2. 核心业务表

约定：`PK` 主键自增（`INTEGER PRIMARY KEY AUTOINCREMENT`）；`TEXT` 时间默认 `datetime('now','localtime')`；“迁移补列”表示该列由 `migrate()` 的 `ALTER TABLE` 补齐（老库自动升级），新库建表语句中亦存在。

## 3. 订单/批次编号设计

### 3.1 设计原则

- **系统号与人读短号分离**：`order_no` / `batch_no` 为系统号，全局唯一且不可变（微信支付 out_trade_no、退款单号、平台 outOrderNo 都靠它）；短号只负责商家/管理员/用户看得懂、念得出、贴袋能扫。
- **序号每天重置，但日期写进号里**：跨天不歧义（`0923-07` 永远指 9/23 的第 7 单）。
- **原子取号**：取号不再用 `COUNT(*)`（删行会重号），改为 `seq_counters` 计数器表原子递增；Node + node:sqlite 为同步单线程执行，无同进程并发抢占，跨进程由 SQLite 写锁串行化。

### 3.2 seq_counters 计数器表

| 字段 | 类型 | 说明 | 默认值/约束 |
| --- | --- | --- | --- |
| scope | TEXT | 取号域：'order'（订单）/ 'batch'（批次），白名单常量 | NOT NULL |
| day | TEXT | 取号日期 YYYY-MM-DD | NOT NULL |
| last_seq | INTEGER | 当日已取到的最大序号 | NOT NULL DEFAULT 0 |
| 主键 | (scope, day) | 同一域同一天一行 | PRIMARY KEY |

### 3.3 原子取号流程（backend/services/seq.js `nextSeq`）

1. 日期在 SQL 里算：`SELECT date('now','localtime')`，与 `created_at` 同源，避免 Node/SQLite 时区漂移。
2. 播种：取当日 `MAX(daily_seq)+1` 作种子（首次取号/计数器表被清空时也不会重用历史号）。
3. UPSERT 递增：

```sql
INSERT INTO seq_counters (scope, day, last_seq) VALUES (?, ?, ?)
ON CONFLICT(scope, day) DO UPDATE SET last_seq = last_seq + 1
```

4. 回读 `last_seq` 作为本次序号，返回 `{ day, seq }`。

### 3.4 号码组成规则

| 号种 | 完整号（系统号） | 短号（人读） |
| --- | --- | --- |
| 订单 | `LD-YYMMDD-NNNN`（如 `LD-250923-0007`） | `MMDD-NN`（如 `0923-07`） |
| 批次 | `BD-YYMMDD-NNN`（如 `BD-250923-003`） | `B-MMDD-NN`（如 `B-0923-03`） |

- 完整号由 `orderNo(day, seq)` / `batchNo(day, seq)` 拼出并落库 `order_no` / `batch_no`（UNIQUE）。
- 短号由 `seq_date` + `daily_seq` 动态拼出（不落库）；历史数据只有 `created_at + daily_seq` 时用创建日期兜底（`orderShortOf` / `batchShortOf`）。

### 3.5 历史数据回填与兜底（migrate() 内）

- `seq_date` 回填为 `date(created_at)`；`daily_seq` 按创建日期逐日累计（id 即当日创建顺序）。
- 同日序号去重：旧的 `COUNT(*)` 方案在「当日删过行」后会重号；启动时对 `(seq_date, daily_seq)` 重复项按 id 顺序重编号到当日最大值之后（保留最早一条）。
- 兜底索引：`ux_orders_seq` / `ux_delivery_batches_seq` 唯一索引（`seq_date, daily_seq`）由数据库兜底；创建失败只告警不阻断启动（疑似仍有重复时人工核查）。
- 计数器播种：启动时 `INSERT INTO seq_counters SELECT scope, seq_date, MAX(daily_seq) ... GROUP BY seq_date ON CONFLICT(scope, day) DO UPDATE SET last_seq = MAX(last_seq, excluded.last_seq)`，保证首次取号与历史号不冲突。

## 4. 管理员体系表

管理员鉴权为「用户名+密码登录 → 签发随机 session token」（替代共享静态 `ADMIN_TOKEN`），见 `backend/services/adminAuth.js`。

### 4.1 admin_users 管理员账号

| 字段 | 类型 | 说明 | 默认值/约束 |
| --- | --- | --- | --- |
| id | INTEGER | 账号 id | PK 自增 |
| username | TEXT | 登录名 | UNIQUE NOT NULL |
| password_hash | TEXT | 密码哈希：`crypto.scrypt` 加盐，16 字节 salt + 64 字节哈希，存 `salt$hash`（hex），校验用恒定时间比较 | NOT NULL |
| nickname | TEXT | 昵称 | '' |
| role | TEXT | 角色 | 'admin' |
| status | INTEGER | 账号状态 | 1（1 启用 / 0 禁用；禁用时其全部会话一并失效） |
| created_at | TEXT | 创建时间 | datetime('now','localtime') |
| last_login_at | TEXT | 最近登录时间 | — |

### 4.2 admin_sessions 登录会话

| 字段 | 类型 | 说明 | 默认值/约束 |
| --- | --- | --- | --- |
| id | INTEGER | 会话 id | PK 自增 |
| token | TEXT | 会话令牌：32 字节随机 hex（登录签发，请求鉴权头携带） | UNIQUE NOT NULL |
| admin_user_id | INTEGER | 归属账号 → admin_users.id（逻辑外键） | NOT NULL |
| created_at | TEXT | 签发时间 | datetime('now','localtime') |
| expires_at | TEXT | 过期时间：`datetime('now','localtime','+N days')` 在 SQL 里计算，N = `ADMIN_SESSION_DAYS`（默认 7 天，可环境变量调整） | NOT NULL |

### 4.3 会话生命周期

- **签发**：登录校验通过后 `issueSession` 插入一行，返回 token。
- **校验**：`token` 匹配 + `expires_at > datetime('now','localtime')` + 账号 `status=1`（`adminAuth.resolveSession` 的 SQL 只查 token 与过期；`server.js` 端到端鉴权另加 `u.status=1` 条件，实际生效以 server.js 为准）。
- **过期**：过期行随 SQL 条件自然失效（无定时清理任务；语义上等同已登出）。
- **吊销**：登出/改密删除单行（`revokeSession`）；禁用账号、重置密码时删除该账号全部会话（`revokeAllSessions`）。
- **启动守卫**：`enabledCount()` 统计 `status=1` 账号数，无启用账号时拒绝启动，防止无鉴权裸奔。

### 5.1 status_events 业务状态流水

建表与索引均在 `db.js` 的 `migrate()` 内（`CREATE TABLE IF NOT EXISTS` + `CREATE INDEX IF NOT EXISTS`），无补列逻辑（新表）。

| 字段 | 类型 | 说明 | 默认值/约束 |
| --- | --- | --- | --- |
| id | INTEGER | 事件 id（自增即时间序，时间线按 id 升序渲染） | PK 自增 |
| entity_type | TEXT | 实体类型 | NOT NULL（order 订单 / batch 批次 / task 任务） |
| entity_id | INTEGER | 实体 id → orders.id / delivery_batches.id / delivery_tasks.id（逻辑外键） | NOT NULL |
| from_status | INTEGER | 变更前状态（首次记录可能为空，如采集器首次见到该实体） | NULL |
| to_status | INTEGER | 变更后状态 | NOT NULL |
| status_text | TEXT | 变更后状态的中文文案（**写入时快照**，≤40 字符；字典见 `backend/services/statusEvents.js`） | '' |
| actor_type | TEXT | 操作者类型（≤20 字符） | 'system'（system / admin / merchant / user / platform） |
| actor_id | INTEGER | 操作者 id（admin_users.id 或 users.id；system 为 0） | 0 |
| actor_name | TEXT | 操作者名称快照（管理员 username / 用户 nickname，≤60 字符） | '' |
| note | TEXT | 备注（≤300 字符；采集器写入「采集器捕获」等来源说明，命中操作者线索时写 handler 的 detail） | '' |

写入方 `backend/services/statusEvents.js`：

- `record(store, ev)` —— 落一条事件（校验 entity_type / entity_id / to_status，字段按上表长度截断）。
- `diffOnce(store)` —— 集中采集器：在内存里维护「活跃实体 → 状态」快照，比对发现变化即落一条；实体离开活跃集（进入终态）时补记最后一次迁移；**首次运行只建快照、不落事件**。
- `hintActor(target, actor, note)` —— 登记「操作者线索」（由 `domains/_shared.js` 的 `audit()` 顺带调用），采集器捕获该实体的迁移时据此署名；线索有 `STATUS_HINT_TTL_MS` 有效期，命中即消费。
- `recordTransition(store, type, id, from, to, fallbackNote)` —— 命中线索则用线索里的操作者，否则记 `system`。

活跃判定（离开活跃集即视为进入终态）：order `status NOT IN (4,5,7)`、batch `status NOT IN (3,4)`、task `task_status NOT IN (80,110,150)`。

采集器由 `server.js` 常驻启动：首次 `diffOnce` 建快照，之后每 `STATUS_EVENTS_MS`（默认 2500ms，见 `doc/08_常量与状态字典.md`）跑一次，**与 WS 订阅者无关**（无订阅也照跑）。已知局限：同一实体在 2.5 秒内连续跳两次状态，只会记到最终值（定时快照比对，非写点埋点）。

## 6. 表间关系（文字版）

```
users 1 ──── n addresses                （user_id：一个用户多个收货地址）
users 1 ──── n cart ──── n→1 goods      （user_id；cart.goods_id → goods.id）
users 1 ──── n orders                   （user_id）
orders 1 ──── n order_items             （order_id；明细带商品名/图/价快照，商品表整体替换后历史订单仍可展示）
orders n ──── 1 delivery_batches        （batch_id：一车多单，一个批次容量按商品件数计 BATCH_MAX_ITEMS=12 件）
orders 1 ──── n delivery_tasks          （order_id：当前每单一个有效任务；异常重配/取餐超时返程会作废旧任务（void_at）并重建新任务，故一对多）
delivery_batches 1 ──── n delivery_tasks（batch_id：同批次任务共用同一机器人/货仓）
landmarks 1 ──── n addresses / orders   （landmark_id 文本关联，订单/地址存点位名快照）
activities 1 ──── n orders              （activity_id：订单命中单个活动，优惠落 original/discount_amount）
orders 1 ──── n refunds                 （order_id：一单可多次售后记录）
orders 1 ──── n cancel_requests         （order_id）
admin_users 1 ──── n admin_sessions     （admin_user_id：一账号多会话，过期/吊销删行）
orders / delivery_batches / delivery_tasks 1 ──── n status_events
                                        （entity_type + entity_id 逻辑关联，无物理外键；每次状态迁移一条，按 id 升序即时间序）
shops                                 （单门店，id 固定 1；订单 delivery_fee 下单时快照）
pay_notifications / audit_logs / status_events / meta / merchant_invites（独立表，无业务外键）
```

无物理外键约束（见 1.1），关联一致性由应用层保证；删除商品、撤销批次等操作依赖订单/明细中的快照字段不受影响。

| --- | --- |
| 幂等键 | 对数据文件内容做 sha256，与 `meta.store_goods_import_hash` 比对；一致则跳过，**变更后重启才会整体重导** |
| 替换动作 | 事务内：`DELETE FROM goods` → `DELETE FROM cart`（旧商品不再存在，孤儿购物车无意义）→ 清 `sqlite_sequence('goods')` 重置自增 → 逐行重插（含 barcode / unit / status / stock） |
| 图片保留 | DELETE 前按条码快照已有商品图（`barcode → image`），重建后按条码贴回，避免清空商家已上传/已配的图 |
| 历史订单 | `order_items` 留存商品名/图/价快照，商品整体替换不受影响 |
| 种子图兜底 | `applySeedImages()`：商品表 `image` 为空且 `backend/seed_images/` 有同名种子图（规范化后精确匹配商品名）时回填 `/store-img/<文件>`；已有图片（`/uploads/...`）绝不覆盖；两者职责互补 |

### 8.3 启动时序

```
init()
 ├─ 建表（CREATE TABLE IF NOT EXISTS × 21）
 ├─ migrate()：补列 → 回填/去重/规范化 → 唯一索引 → 计数器播种 → 一次性修正（meta 标记）
 ├─ seed()：shops / landmarks / goods 种子
 ├─ importStoreGoods()：store_goods.json sha256 变化则整体替换 goods
 └─ applySeedImages()：空图商品回填种子图
```
