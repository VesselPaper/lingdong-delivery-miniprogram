## 一、为什么必须改：需求2「开仓的时候就走了」的根因

现象：车在上货点等单，5 分钟判断时间一到，先想回充电点、再判断有无订单、再回上货点。

根因（已定位，不是判断顺序写错）：

1. 上货点等待用的是**轻任务 lightTask**。平台语义：到达后等 `expireTime` 分钟，**到期自动返程**（回充电桩）。
   我们给 5 分钟窗口（`summonToLoadingPoint` 默认 `expireMin=5`）。
2. 为了不让车到期就走，`keepLoadingSummon`（timers ⑤）每 `SUMMON_LOADING_KEEP_MS=240000`（4 分钟）
   在窗口到期前**发一次新召唤**续命。但**新召唤会顶掉旧召唤**（平台语义：召唤会中断当前任务/召唤并响应新的）。
3. 于是：车刚停稳/快到期 → 新召唤下达 → 车短暂「无任务 → 重新决策」→ 表现成"先想回充电点，又回去"。

**关键结论：lightTask 天生有倒计时，不可能"驻停"；只要继续用 lightTask 守上货点，就必须靠
破坏性的重召唤续命，这个 bug 就治不干净。唯一治本方案 = 上货点改用真实配送任务（无倒计时）。**

（越凡 OpenAPI 已确认：`DELETE /open-api/v1/lightTask` 存在；`deviceCtrl/close` 关闭真实任务；
`deviceCtrl/authority/*` 控制权是"持有期间机器人不执行任务"的驻停机制，可 `renewal` 续约。）

## 二、设计：上货点改用真实配送任务

### 目标形态

| 环节 | 现状（lightTask） | 目标（真实任务） |
|---|---|---|
| 上货点待命 | lightTask 5 分钟窗口，到期返程 + 4 分钟破坏性重召唤 | `create/direct` 真实任务，`loading = unloading = 上货点`，`syncLoading:0`，**无倒计时**；车到达 30 后一直待命 |
| 到达门禁（开舱） | `ensureLoadingArrival` 查 lightTask `status===30` | 查真实任务 `task_status===30`（走既有 `delivery_tasks` 同步管道：回调 + 轮询） |
| 立即配送 | 召唤首站 lightTask | 先召唤/建任务到首站 → **成功** → 关闭上货点真实任务 → 释放控制权 |
| 送完回上货点 | lightTask 召回 + 3 分钟释放 | 真实任务召回（同上） |
| keepLoadingSummon | 4 分钟重召唤（破坏源） | **删除**。真实任务无到期，不需要续 |

### 为什么 `create/direct` 能驻停

`create/direct` 返回后机器人持有控制权（`authority/grant` 返回 `ctrlId`），**持有控制权期间不执行任务**；
到期自动释放（超时断连机制），可 `authority/renewal` 续约。开舱用 `drawerCtrl(1)`（不驱动任务状态），
关舱 `drawerCtrl(0)`；`loading/verify`+`loading/confirm` 只在 Route B 非召唤路径用。

### 衔接顺序（负责人 2026-10-14 定，硬规则）

1. 先召唤/建任务到**下一个点**，确认成功；
2. **成功后才**关闭旧的上货点真实任务（`deviceCtrl/close`）；
3. 最后释放控制权。

**反向顺序的后果**：先关旧任务再建新的，中间窗口车没有任务 → 平台语义"重新决策返程" → 车开回充电桩。
**另一条硬规则**：装货期间绝不 `deviceCtrl/close` 上货点任务（舱内有货时 close 会自动开舱）。

### 落地要点

- 新列 `delivery_batches.standby_task_id`（沿用 `light_task_id` 的持久化模式）或直接复用
  `delivery_tasks` 行（order_id 挂批次内第一单；复用既有 `applyStatus`/轮询同步管道最省事）。
- `keepLoadingSummon` 整段删除；⑤ 看门狗只保留「推进下一站/自愈」部分。
- 兜底：`deviceCtrl/pending`（131 挂起，送货挂起返回上货点）+ `deviceCtrl/recover`。
- Mock 档保持可测（mock 平台补 `standby` 真实任务推进）。

## 四、P4 · 动态承诺时间（公式与参数）

用户要：下单/订单详情展示承诺送达时间，且「在地图上估算小车路线行驶时间」（已定用路网估算，
路网对不上就退直线×绕行，见 `doc/14` §十一 3）。

### 公式

```
承诺 = 攒单剩余 + 排队等车 + 路网行程 + 缓冲
  · 攒单剩余 = 剩余到 batchHoldMs 的分钟数（batchHoldMs 会随压力缩短，须用同一口径）
  · 排队等车 = 当前待发批次/可用车的排队估计（简化：待发批次数 ÷ 可用车数 × 每趟时长）
  · 路网行程 = v2EstimateTripMin（真实坐标；路网不可用退直线×绕行）
  · 缓冲     = 固定常数（如 3~5 分钟，覆盖开舱/等待抖动）
```

### 参数（env）

- `PROMISE_MIN_MINUTES` / `PROMISE_MAX_MINUTES`（建议 15 / 30，对齐"攒单 15 + 行程 15"）
- 超上限**不许撒谎**：显示「当前繁忙」，不给数字承诺。

### 注意

- 与 15 分钟窗口的关系讲清：30 分钟承诺 = 攒单 ≤15 + 行程 ≤15，**没有余量**（`doc/14` §八 已标记）。
- `doc/14` §八「放宽每趟 ≤15 分钟」是产品决策，动了承诺时间才允许放宽。
- 出口位置：用户端下单确认页 + 订单详情（后端算好，追踪页 3 秒轮询读取，与 `orderAhead` 同管道）。
