# 04 · 核心业务链路 · 02 下单支付与接单组单

## 3. 下单与支付

### 3.1 下单 createOrder（含拆单、编号、取餐码、优惠）

触发点：确认订单页「提交订单」（点位/姓名/手机号已校验）。

请求接口：POST /api/order/create（landmark_id、landmark_name、remark、items、contact_name、contact_phone、activity_id）。

后端处理：`backend/domains/order/routes.js → /order/create` → `backend/domains/order/service.js → createOrder(store, deps, body, userId)`：
1. 店铺校验：`deps.goods.getShop` 歇业（business_status=closed）直接 400；
2. 参数校验：收餐人姓名 trim 非空 ≤20，手机号 `^1\d{10}$`；点位必须是 `type='deliverPoint'` 的可用送达点；商品数量正整数 ≤99；逐行查 `deps.goods.getGoods` 校验存在与库存；
3. 优惠（services/promotion.js）：`activity_id=0 / '0' / 'none'` → 用户选择「不使用优惠」，无折扣无满减按原价结算；否则后端权威重算应付（前端自报价无效）。配送费（shop.delivery_fee，缺省 1 元）整单只收一次，挂在拆单后的第一单上；
4. 拆单：`splitOrderChunks(lineItems, BATCH_MAX_ITEMS)`——单笔订单总件数超过单车容量（BATCH_MAX_ITEMS=12 件）时贪心拆成多个 ≤12 件的子单块，每个子单独立成单；
5. 编号取号：`backend/services/seq.js → nextSeq(store, 'order')` 原子取号（seq_counters 计数器表，种子取当日 MAX(daily_seq)+1，防删行重用），`orderNo = 'LD-' + YYMMDD + '-' + 4 位序号`，拆单各子单连号；
6. 取餐码生成与查重：`pickupCodeNew(seq)`——4 位随机数，在「未结束订单（status IN (0,1,2,3)）」范围内查重，撞码重摇（最多 20 次），兜底用当日序号派生（当日序号唯一 → 兜底码唯一）。取餐码是平台 loading/unloading 校验码与用户开舱凭据，必须唯一；
7. 落库与扣库存：`q.insert` 写 orders（status=0 待支付，快照 original_amount/discount_amount/delivery_fee/total_amount、seq、seq_date），逐商品 `q.insertItem` 写 order_items + `deps.goods.deductStock` 扣库存（扣不到抛「库存不足」，整单回滚）；
8. 清购物车：`deps.user.removeCartItems` 只删本次下单实际包含的商品（不再无条件清空整张购物车）。

金额与快照要点：
- 单价以后端 goods.price 为准（前端价格仅展示），每行 `total += price * qty`；
- 拆单配送费整单只收一次：`feeAssigned` 标记挂在第一子单上，否则一次下单拆 3 单会收 3 次配送费；
- 实付 = 商品活动后金额 + 配送费（配送费不参与活动折扣、不进 discount_amount）；四舍五入到分；
- 下单即快照 original_amount / discount_amount / delivery_fee / total_amount 进订单，事后商家调价/改配送费不影响历史订单的对账与退款金额；
- 拆单示例：购物车 5 件 A + 9 件 B = 14 件 > 12 → 拆成 [A×5+B×7] 与 [B×2] 两个子单，各自独立订单号（连号）、独立取餐码、独立支付（微信 out_trade_no 按子单 order_no 计）。

状态流转：无订单状态迁移（新单 status=0）。

落库字段：orders 一行（order_no、status=0、pickup_code、seq/seq_date、各金额快照、landmark_id/name、contact_*、remark）；order_items 每商品一行；goods.stock 扣减；cart 删除命中商品。

结果返回/后续：单笔返回 `{ order_id, order_no, total_amount, pickup_code }`；拆单返回 `{ orders:[…], split:true, split_count, total_amount }`，前端跳订单详情并拉起支付。

### 3.2 支付（PAY_MOCK 模拟档 / 微信支付 V3 真实档）

触发点：订单详情页「立即支付」或订单列表「去支付」。

请求接口：POST /api/order/pay（id）。

后端处理：`backend/domains/order/routes.js → /order/pay`（联表校验订单归属）→ `backend/domains/order/service.js → payOrder(store, deps, order, user)`：
- 状态守卫：非 0 待支付一律 400；
- 试点档（`runtime.realPay=false`，即 PAY_MOCK=true）：`q.markPaidMock` 置已支付（status 0→1），`deps.push.broadcast({type:'order_created'})` 推送商家端红点；随后 `maybeAutoAccept(store, deps, order)`：**店铺营业且 auto_accept=1** 时自动接单并入配送批次（1→2），返回 `{ mock:true, auto_accept:true }`；
- 真实档：校验 WX_APPID 与 `deps.wxpay.enabled()`（商户四要素），`deps.wxpay.jsapiPay` 调微信支付 V3 统一下单（JSAPI），`q.markPayChannel` 记 pay_channel=wxpay，返回 `payParams` 供 `wx.requestPayment` 拉起收银台。

状态流转：0 待支付 → 1 待接单（模拟档立即迁移；真实档以回调为准）→ 自动接单时继续 1→2。

落库字段：orders.status、pay_channel；真实档回调另写 pay_notifications 表。

支付结果回调：微信服务器 POST /api/pay/notify → `backend/domains/order/routes.js` 内联处理：`verifyNotifySignature`（平台证书验签）→ `decryptNotify` → 商户号/appid 比对 → `trade_state==='SUCCESS'` → 幂等 `q.payNotifyExists`（同一回调事件只处理一次）→ 按 order_no 找单 → **金额比对**（`info.amount.total` 与 `total_amount×100` 必须一致，防止篡改回调金额）→ `q.markPaidNotify`（CAS：仅 status=0 可置 1，记 transaction_id）+ `q.payNotifyInsert`（落 pay_notifications 事件表）→ 同样触发 `maybeAutoAccept`。前端支付成功后轮询订单详情确认 status>0。

边界与说明：
- 支付状态以**微信回调为准**（模拟档以 markPaidMock 为准），payOrder 只是发起下单获取收银台参数，不负责置已支付；
- 回调全程对微信侧返回 `{code:'SUCCESS'}` 语义（重试友好）；验签/商户号/金额任一不符返回 4xx 令微信重推；
- 试点档退款为本地标记（真实微信退款需商户号后接入，见链路 9）——与支付侧 PAY_MOCK 配套，`RUN_MODE=production` 下支付与退款都必须走真实通道。

## 4. 接单与组单

### 4.1 手动接单

触发点：商家端订单列表「确认接单」或订单详情「接单并装车」。

请求接口：POST /api/merchant/order/confirm（id）。

后端处理：`backend/domains/order/routes.js → /merchant/order/confirm`：`merchantGuard` 鉴权 → `deps.goods.getShop` 校验营业（歇业拒绝）→ 订单须 status=1 → `deps.batch.addOrderToBatch(store, order)`；`audit(req,'order/confirm',…)` 落审计。

### 4.2 自动接单（营业 + auto_accept）

触发点：支付成功（模拟档 payOrder 内 / 真实档 pay/notify 回调内）自动触发。

后端处理：`backend/domains/order/service.js → maybeAutoAccept(store, deps, order)`：`getShop` 须 business_status='open' 且 auto_accept=1，订单须 status=1 → `deps.batch.addOrderToBatch` → 事件驱动 `deps.autoLoadHook(batch)`（防抖 5s 后 `backend/services/autoLoad.js → evaluate`：挑在线空闲车召唤去上货点，忙/在送不打断）。

### 4.3 best-fit 分批（BATCH_MAX_ITEMS=12 件）

后端处理：`backend/services/batch.js → addOrderToBatch(store, order)`：
1. `orderItemCount` 实时统计本单商品件数（以「件」计容量，非单数）；
2. `getOrCreateOpenBatch(store, itemCount)`：从「组单中（status=0）」批次里取**能容纳本单件数且当前最满**的一个（`HAVING items + ? <= BATCH_MAX_ITEMS ORDER BY items DESC`，容量一律实时 SUM 计算，不信任 total_items 缓存列）；无合适批次则新建——`seqSvc.nextSeq(store,'batch')` 取号，`batchNo = 'BD-' + YYMMDD + '-' + 3 位`，插入 delivery_batches（status=0 组单中、daily_seq/seq_date）；单件数 >12 的订单任何批次都装不下，自动独占新建批次；
3. 订单挂批：`UPDATE orders SET batch_id=?, status=2, batch_removed_at=NULL`（清空摘除标记，防「异常重配」后计数虚高），批次 `total_orders+1、total_items+件数`。

状态流转：orders 1 待接单 → 2 配送中（并入批次后即视为「已接单配送中」）；delivery_batches.status=0 组单中。

落库字段：orders.batch_id/status/batch_removed_at；delivery_batches.total_orders/total_items。

结果返回/后续：商家端 toast「已接单，并入批次 BD…」→ 弹窗跳转配单/上货页。

补充：自动接单的车辆调度（仅召唤模式生效）
- `maybeAutoAccept` 并入批次后触发 `deps.autoLoadHook(batch)` → `backend/services/autoLoad.js → schedule/evaluate`（防抖 AUTO_LOAD_DEBOUNCE_MS 默认 5s，多单合并一次评估）；
- evaluate 按车状态决策：车正在配送/被召唤（lightTask/delivery/interaction）→ 不打断跳过；已在上货点途中/到达（light_task_id 到 30）→ 幂等跳过；空闲/待机/充电/返程（SUMMONABLE 白名单）→ `platform.summonToLoadingPoint` 召唤去上货点并记录 light_task_id；离线/异常 → 跳过并记日志，绝不对故障车硬发召唤；
- 直发模式无需召唤：任务在派车定型时创建（Route B syncLoading=0），车自行导航到上货点（任务 30 到达上货点即开舱门禁依据）。

批次详情视图：`backend/services/batch.js → getBatchDetail(store, batchId)`——批次卡（batch_no/daily_seq/status_text/device_sn/total_orders/total_items/picked_orders/route_text）+ 逐单子卡（order_no 短号/点位/收餐人脱敏/取餐码/商品明细/任务状态），已取餐数按订单 picked_up_at 动态统计（不信任计数器，防漂移），商家端「配单上货」页与批次详情共用此函数。

### 4.4 派车定型（批次 0 组单中 → 1 待上货）

触发点：配单/上货页「组单中批次 → 派车配送」（可指定 device_sn）；商家站车前扫码（POST /api/merchant/device/scan 对未派车的组单中批次自动调用本流程）；**或自动定型**：组单中批次满容（≥12 件）或成立超 BATCH_WAIT_MS（90s）由 timers ④ 自动触发（2026-09-25 起，无需人工）。

请求接口：POST /api/merchant/delivery/batch/dispatch（batch_id、device_sn）。

后端处理：`backend/domains/delivery/routes.js` → `backend/domains/delivery/service.js → doDispatchBatch(store, deps, batchId, deviceSn)`：
1. 真实档先确认可用空闲车：指定 device_sn 或 `deps.platform.pickAvailableRobot()` 自动挑在线空闲机器人；无可用车返回带设备清单的明确错误；`isRobotBusy` 拦截忙碌车；
2. 并发抢占：`q.claimDispatch` 条件更新批次 status 0→1（P1-7：自动派车扫描与商家手点并发时只有抢到者继续，失败方报「已派车」，杜绝同一批货下发两次）；
3. 查批次内待配送订单（status IN (1,2)），`q.setBatchDeviceSn` 定型设备；
4. 按模式分流：
   - 直发模式（非 summonDelivery）：`deps.platform.createTasksForBatch(store, b, orders, [])`——为每单创建独立平台任务（queue/create，outOrderNo 独立、取餐码独立、指定同一 deviceSn、priority 按停靠顺序递减、extInfo 含 batchNo/stop），任务在定型时创建后车自行导航去上货点（task 20/30）；
   - 召唤模式（summonDelivery）：**不创建任何配送任务**，仅定型设备与批次（路线与逐点召唤推迟到「立即配送」，见链路 6）；
5. 兜底 `UPDATE orders SET status=2 WHERE batch_id=? AND status=1`。

状态流转：delivery_batches 0 组单中 → 1 待上货；orders 保持 2。

落库字段：delivery_batches.status/device_sn/status_text；delivery_tasks 逐单新增（直发模式）+ orders.delivery_task_id 绑定。

失败回滚：任一步失败 `q.voidTasksByBatch` 作废本轮已建任务 + `q.revertDispatch` 批次退回组单中（清 device_sn/route，防下次沿用旧路线）。

自动定型说明（2026-09-25 起，`backend/domains/delivery/timers.js` 第④个定时器，BATCH_SCAN_MS 默认 15s）：
- 扫描 `status=0` 组单中批次，满足**商品件数 ≥ BATCH_MAX_ITEMS（12）满容**或**成立超 BATCH_WAIT_MS（90s）**即调 `doDispatchBatch` 自动定型（与店铺是否自动接单无关）；
- 定型失败（如暂无空闲车辆）由 `autoRetryAt` Map 做 60s 节流重试，车一上线自动补定型；并发安全由 `doDispatchBatch` 的 `q.claimDispatch`（status 0→1 条件更新）保证；
- 定型成功 `deps.push.broadcast({type:'batch_dispatched', batch_id, batch_no})`，商家端订阅页（配单上货/任务页/工作台）即时刷新，批次卡面从「组单中」旋转圆环变为「待上货」——即组单完成的自动反馈。
