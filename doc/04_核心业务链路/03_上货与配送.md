# 04 · 核心业务链路 · 03 上货与配送

## 5. 上货（扫码定位机器人 → 批次开舱 → 关舱 → 立即配送）

触发点：商家端「上货配单」页，顶部搜索后选中「待上货」批次（可先扫码或直接选批次操作）；批次列表来自 GET /api/merchant/device/pending（组单中可派车 + 待上货可上货，附 robot_available 占用标注）。

列表说明：`/merchant/device/pending`（delivery/routes.js）返回 open_batches（组单中，可派车）/ ready_batches（待上货）/ active_batches（配送中）三组；对每个待上货批次经 `deps.platform.isRobotBusy` 标注 robot_available/robot_busy/robot_busy_msg——商家按「上货」前即知设备是否被占用（正在配送的车不中断、不强召上货点），以及 pending_orders 红点计数（组单中+待上货批次内订单总数）。

### 5.1 扫码定位机器人

请求接口：POST /api/merchant/device/scan（deviceSn）。

后端处理：`backend/domains/delivery/routes.js → /merchant/device/scan`：
- 真实档按扫码设备号精确匹配（P1-10，绝不把货错装到别的车）：① 该车已派好的「待上货」批次（status=1 且 device_sn 匹配）直接复用；② 未派车（组单中 status=0）时逐批尝试 `s.doDispatchBatch(store, deps, cand.id, deviceSn)` 现场定型（并发被抢走则试下一批）；
- 找不到返回「本车暂无待上货批次」或「当前没有待配单的订单」；
- 命中后 `q.setBatchDeviceSn`/`q.setBatchTasksDeviceSn` 回写设备号，`deps.platform.grantControl(deviceSn)` 取设备控制权，`robotAtLoadingPoint` 附带「已就位 ✓ / 距上货点 N 米」。
- 演示档（PLATFORM_MOCK=true）：直接取最早一个待上货/组单中批次模拟返回。

### 5.2 批次开舱（召唤模式真到站门禁 / 直发模式到达门禁）

请求接口：POST /api/merchant/device/batch/open-bin（batch_id）。

后端处理：`backend/domains/delivery/routes.js` 分流：
- 召唤模式：无配送任务，开舱 = **先召唤到上货点 + 真到站门禁 + drawerCtrl(1)**。`s.ensureLoadingArrival(store, deps, b)`：以批次 light_task_id 查 `deps.platform.queryLightTask`，**status=30（arrivedPoint）才是机器人真正到达信号**——未到返回 `{waiting:true}` 友好提示（已存在的召唤任务绝不重复创建，防进度重置）；到 30 后 `deps.platform.drawerCtrl(device_sn, 1)` 开舱（开舱前 `isRobotBusy` 兜底，不打断正在配送的车），`q.setBatchLoading` 记 loaded；
- 直发模式：`deps.platform.robotAtLoadingPoint` 门禁（未到上货点返回 waiting 态不报错）→ 演示档 `verifyBatchLoading` 本地验证；真实档 `grantControl(device_sn, 600)` 取控制权（ctrlId 持久化到 delivery_batches.ctrl_id，内存 Map `batchCtrl` 快速访问）→ `verifyBatchLoading` 逐任务按各单取餐码验证（autoOpen=true，验证通过自动开舱，单仓一次放入全部货品）；
- 单任务版本 POST /api/merchant/device/open-bin（task_id）→ `s.getLoadingTask` 定位任务 → `deps.platform.loadingVerify(task.device_sn, task.platform_task_id, { anyCode: task.pickup_code })`。

状态流转：delivery_tasks 20/30（去/到上货点）→ 40 上货中（开舱）；演示档直接模拟成功。

落库字段：delivery_batches.ctrl_id/loaded_at；delivery_tasks.status_text。

### 5.3 关舱

请求接口：POST /api/merchant/device/batch/close-bin（batch_id）。

后端处理：`deps.platform.drawerCtrl(device_sn, 0)` 关舱 → `q.setBatchLoadedAt` 落「已上货待配送」（loaded_at 持久化，供重进批次详情恢复「立即配送」态）。直发模式任务仍停 40；召唤模式机器人原地等待。

状态流转：无订单/批次迁移，仅标记已上货待配送。

### 5.4 立即配送（开始配送）

请求接口：POST /api/merchant/device/batch/dispatch（batch_id）。

后端处理：`backend/domains/delivery/routes.js`：
- 召唤模式：`s.startSummonDelivery(store, deps, b.id)`——先 `deps.batch.planRoute` 规划路线（无则现算并 `q.setBatchRoute` 落库），`deps.platform.summonDeliveryToStop(store, b, first)` **先召唤首站成功**才把批次置「配送中(2)」+ `current_stop=1`（召唤失败直接抛错保持待上货，杜绝「配送中但首站没召唤」的半启动状态）；首站订单待取货由真到站后置位（见链路 6）；
- 直发模式：`deps.batch.planRoute` 计算路线写入 batch.route（规划失败不阻断配送）→ 演示档 `confirmBatchLoading` 本地确认；真实档 `confirmBatchLoading`（逐任务 loadingConfirm → 任务 50 已上货）→ `releaseControl` 释放控制权（ctrlId 优先取批次行持久化值，释放失败不阻断）→ `q.setBatchDelivering` 批次置 2 配送中；
- 演示档专用 POST /api/merchant/device/batch/mock-dispatch：仅 deviceMock 模式可用（非模拟档 404 防真实订单被假送达），落 `mock_arrive_at`（MOCK_ARRIVE_MS 默认 10s）→ 任务置 50、批次置 2，由 timers 第④扫描的 `s.processMockArrivals` 到点统一置已送达(3)（重启可自愈，不依赖内存定时器）。

状态流转：delivery_batches 1 待上货 → 2 配送中；任务 40 → 50 已上货。

落库字段：delivery_batches.route（JSON 停靠序列）/status/loaded_at 清除；delivery_tasks.task_status；mock 档写 mock_arrive_at。

## 6. 配送

### 6.1 两种配送模式总览

- 召唤多单配送（SUMMON_DELIVERY=true）：无逐单配送任务，批次定型后由「立即配送」`startSummonDelivery` 启动，机器人以**轻任务（lightTask）**逐站被召唤推进；用户开/关舱走 `drawerCtrl` 直接控制。适用于「车先到站、人再取」的多单逐站模型。
- 直发模式（默认）：派车时 `createTasksForBatch` 为每单创建独立平台任务，任务状态 0~150 由平台回调 + basicList 轮询双通道同步，订单状态由任务状态联动。

### 6.2 路线规划（单数加权最近邻）

后端处理：`backend/services/batch.js → planRoute(store, orders)`：按送达点位分组（同点多单合并为一站），从上货点（landmarks type='loadingPoint'）出发做贪心最近邻——**有效距离 = 距离平方 ÷ 订单数^α**（α=ROUTE_COUNT_WEIGHT 默认 0.5），多单楼栋的有效距离被缩小从而更早被选（近似最小化顾客总等待）；无坐标时退化为「单数从多到少，同单数按点位 sort」。停靠顺序写入 `delivery_batches.route`（每站含 stop/landmark_id/landmark_name/order_ids）。

### 6.3 任务与轻任务

- 直发模式「任务」：delivery_tasks 每单一任务，task_status 0 排队中 → 10 已接收 → 20 去上货点 → 30 到达上货点 → 40 上货中 → 50 已上货 → 60 去取货点 → 70 到达取货点 → 80 完成；90/100 失败、110/150 取消关闭。状态同步三通道：平台回调 POST /api/platform/callback/delivery（`backend/domains/delivery/service.js → handleDeliveryCallback` → `backend/services/platform.js → applyStatus`）、basicList 轮询兜底（`platform.js → syncTaskStatus`，POLL_MS 默认 8s，70/90-109 也在轮询范围防卡死）、本地模拟（mockAdvance）。
- 任务创建参数（`platform.js → createTasksForBatch`）：逐单 queue/create——outOrderNo 用各单独立 order_no、取餐码独立（各单 unloading/verify 校验码）、指定同一 deviceSn、priority 按停靠顺序递减提示排程、extInfo 含 batchNo/stop；真实档任务创建成功即回写 delivery_tasks.platform_task_id，回调/轮询凭它定位任务。
- 召唤模式「轻任务」：`platform.js → summonToLoadingPoint / summonDeliveryToStop / queryLightTask`。轻任务状态 0/10/20 前往·等待中、30 arrivedPoint **真到站信号**、40/50/60 终态（可重新召唤）。light_task_id 落 delivery_batches 供到达门禁查询。

### 6.4 真到站标记（召唤模式，lightTask status=30）

后端处理：`backend/domains/delivery/service.js → advanceSummonDelivery(store, deps, batchId)` 内先调 `ensureStopArrival(store, deps, b)`：查当前在途站（route[current_stop-1]）的 lightTask，**status=30 才算真到达**，才 `markStopDelivered` 把该站订单逐单 `deps.order.arriveOrder` 置待取货——修复过「机器人才被召唤去下一站、尚未开到时订单被虚标为已送达」的缺陷；未到保持配送中，绝不虚标。推进防重：`summonAdvancing` Set 保证同一批次同一时刻只执行一次召唤/召回。

状态流转（真到站）：orders 2 配送中 → 3 已送达（`arriveOrder` 幂等，已 3/4 直接返回；写 delivered_at + 结算销量 settleSales）。

### 6.5 召唤逐站推进（同批次进度）

触发点：每次用户关舱取走（`countPicked → notifySummonAdvance` 钩子）；看门狗兜底 `backend/domains/delivery/timers.js` 第⑤定时器（SUMMON_WATCHDOG_MS 默认 5s，恒扫 delivery_mode='summon' 且 status=2 的批次）。

后端处理：`advanceSummonDelivery`：当前站订单全部取走（status IN (2,3) 的剩余数=0）→ 停 `SUMMON_STOP_ADVANCE_MS`（默认 5s）→ 还有下一站则 `summonDeliveryToStop` 召唤过去并 `current_stop+1`；最后一站取完 → `q.setBatchCompleted` 批次置 3 已完成 + `settleRobotAtLoading`（有单召回上货点待命；无单召唤回上货点等 SUMMON_RELEASE_WAIT_MIN 分钟到期自动释放返程充电）+ **`q.setBatchCurrentStop(store, batchId, 0)` current_stop 归零**。看门狗还负责自愈「半启动」批次（status=2 且 current_stop=0：上次召唤首站失败残留 → 节流 25s 重跑 `startSummonDelivery` 补召唤）。

看门狗的上货点驻守（timers.js ⑤ 内部 ③ 段）：对「组单中/待上货且有单」的批次，若其设备不在配送中，则保持召唤上货点任务存活——`keepAt` Map 记录上次成功召唤时间，每 `SUMMON_LOADING_KEEP_MS`（默认 4 分钟）在轻任务到期前续一次（`summonToLoadingPoint`），车物理一直停在上货点；无待上货批次则不续（由释放事件走 3 分钟释放返程）。召唤节流 `keepTryAt`：离线/召唤失败时至少 30s 再试，避免刷爆平台。

### 6.6 直发模式任务→订单联动

后端处理：`backend/services/platform.js → applyStatus(store, taskId, status, text)`（任务状态写入唯一咽喉，三通道全部经过）：
- 终态守卫：任务已作废（void_at/110/150）或订单已取消退款（cancelled_at/5/7）时丢弃一切迟到状态（只接受平台对 150 的确认），防「已取消订单被推回已送达并结算」；
- 70 到达取货点 → 订单 3 已送达（写 delivered_at + settleSales）；
- 80 任务完成：**≠ 用户已取走**——只有 `picked_up_at` 非空才联动；平台 40s 自动关舱流转的 80 保持订单 3，交由取餐超时扫描处理；
- 90/100 系列失败 → 订单 6 配送异常；
- 110/150 取消/关闭 → `orderCancel.cancelLocal({finalStatus:5})` 走统一取消落账（作废任务 + 回补库存 + 摘批次）；
- 末尾 `batch.onTaskStatus` 联动批次计数与完成判断。

补充：回调防伪与设备侧业务校验
- 回调防伪：`backend/domains/delivery/service.js → callbackAuthorized(req, deps)`——令牌在创建排队任务时以 `?token=` 拼进 feedbackDeliveryTaskUrl / checkBizOrderStatusUrl，回调时 sha256 定长摘要 + `timingSafeEqual` 比对（防时序侧信道猜解）；令牌无法派生（PLATFORM_SECRET 为空且未显式配置 PLATFORM_CALLBACK_TOKEN）时放行（本地演示场景，启动日志已告警），校验失败返回 403；
- 设备侧校验：GET/POST /api/platform/check-order（`handleCheckOrder`）——设备在关键节点查业务订单状态：订单正常返回 `{code:'COMM_200', data:null}`；订单已取消(5)/已退款(7)/cancelled_at 时返回 `keyEvent { eventName:'forceCloseTask', taskSubStatus:201, eventDesc }` 令设备强制关任务（修复过「已退款订单平台侧收不到 forceCloseTask、钱退了餐照送」的缺陷）；taskSubStatus 按对接文档仅 201 已退款 / 202 人工送达，具体原因用 eventDesc 区分；
- 异常上报回调：POST /api/platform/callback/exception（`handleExceptionCallback`）接收设备 T/R/I/N 类异常报文，仅记录告警不阻断业务。

### 6.7 超时未接单检测

后端处理：`backend/domains/delivery/service.js → scanStuckDeliveries(store, deps)`（timers 第②定时器，DELIVERY_SCAN_MS 默认 60s，仅真实档）：任务非终态（不在 70/80/110/150）且 `updated_at` 超 DELIVERY_TIMEOUT_MS（默认 15 分钟）→ 订单 2 → 6 配送异常，任务 status_text 注明原因。

### 6.8 配送追踪（用户端）

请求接口：GET /api/delivery/track?order_id=（前端 3 秒轮询）。

后端处理：`backend/domains/delivery/routes.js → /delivery/track`：查订单归属 + `q.taskById` + `deps.platform.getDevicePosition`（真实模式 eviz 代理坐标，按地图 bbox 归一化为百分比坐标 percent；mock 无坐标回退纯文本）+ 地图数据（bbox/点位/路线折线）+ 批次信息 batch（batch_no/total_orders/picked_orders/multi_order/device_sn）+ task_text 文案（无任务时按批次状态给「商家已接单，正在组车配送 / 机器人前往上货点 / 等待商家接单」；已送达未取时按 pickup_timeout_stage 给两段式提示文案）。

返回结构：`{ order_status, order_status_text, pickup_code, landmark_name, task:{task_status,status_text}, task_text, position, percent, map:{bbox,landmarks,route}, batch }`。前端据此渲染进度条（已接单/取餐/配送/送达四段）+ 自绘地图（点位/路线/机器人位置）+ 取餐码；一车多单时展示「本车共 N 单 · 已取 X 单」，提示用户凭本单取餐码取走自己那份。

商家端监控：GET /api/merchant/delivery/monitor（`q.monitorTasks` 查所有未完成配送任务含失败任务，逐任务附 `getDevicePosition`）；GET /api/merchant/robots（`platform.getDeviceList` 调平台 runtimeStatusList 返回真实设备，状态码映射中文）；GET /api/merchant/map（`platform.getMapOverview` 真实校园地图底图 + 路网 graph + 点位 + 路线折线 + 机器人实时坐标，前端 canvas 按 bbox 线性映射绘制）。
