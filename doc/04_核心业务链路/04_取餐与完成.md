# 04 · 核心业务链路 · 04 取餐与完成

## 7. 取餐与完成

### 7.1 进入取餐（三种扫码）

- POST /api/delivery/pickup-scan（order_id）：校验订单归属 + 状态 ∈ {3,4}，返回 `pickupContext`；
- POST /api/delivery/pickup-by-code（device_sn + pickup_code）：校验本人订单、status=3、取餐码匹配、**车一致**（任务 device_sn 或批次 device_sn 匹配，代取场景）；
- POST /api/delivery/pickup-by-scan（device_sn）：扫车码后自动匹配本人在该车上的待取餐订单（`auto_matched:true` 免输码），匹配不到前端回退输码流程。

后端处理：`backend/domains/delivery/service.js → pickupContext(store, order)`：返回订单/取餐码/任务上下文 + **同批次订单列表**（batch_orders，提示「本车共 N 单」）+ 本人同点位待取订单（my_batch_orders，含商品明细，支持同点多单一起取走），避免把其他取货点已到/在途订单混进来。

### 7.2 开舱取餐（自动关、防超时、重开限制）

触发点：取餐页（配送追踪订单已送达 → 扫码/输码进入）「打开舱门」按钮；页面 40s 倒计时提示取走餐品。

请求接口：POST /api/delivery/pickup-open（order_id）。

后端处理：`backend/domains/delivery/routes.js → /delivery/pickup-open`：
1. 状态 ∈ {3,4} 才可开舱（4 为关舱后重开）；
2. 重开限制（P1-2）：`pickup_opened_at` 起算，超 PICKUP_REOPEN_WINDOW_MS（默认 10 分钟）拒绝；CAS 条件更新 `pickup_open_count < MAX_PICKUP_OPEN(3)` 抢次数，超上限拒绝；
3. 置 `picking_up_at=now`——**打开舱门 = 正在取餐，取餐超时计时暂停**；
4. 召唤模式：`deps.platform.drawerCtrl(device_sn, 1)` 直接开舱；直发模式：`deps.platform.unloadingVerify(device_sn, platform_task_id, { contact: 手机号, roomNum: pickup_code })`（strategies=手机号+取餐码，autoOpen=true）开舱即完成；无真实任务（测试兜底）本地完成并标记 test:true。

自动关舱与防超时：平台侧约 40s 未收到关舱调用会自动关舱（任务流转 80，但**不置订单 4**——picked_up_at 为空则订单保持 3，交给取餐超时扫描处理）；用户可在 40s 自动关后点「重新打开」再次开舱，受 `PICKUP_REOPEN_WINDOW_MS`（默认 10 分钟，自首次开舱起算）与 `MAX_PICKUP_OPEN`（默认 3 次）双限约束，超限返回「请联系商家处理」。

### 7.3 关舱取餐（标记已取走）

请求接口：POST /api/delivery/pickup-close（order_id）；同点多单版 POST /api/delivery/pickup-close-all（batch_id + landmark_id）。

后端处理：关舱 = **真正的「确认取餐」动作**（修复过「开舱即置 4 并结算、重开功能永远不可用」的缺陷）：
- 召唤模式：`drawerCtrl(0)` 关舱为**尽力而为**（失败不阻断取餐记录，防该单停在 3 导致推进器永不触发）→ 清 picking_up_at → `deps.order.fulfillOrder`（写 orders：picked_up_at + status 4 + settleSales 结算销量 + `deps.batch.countPicked` 批次计数 → 钩子 `notifySummonAdvance` 触发推进）；
- 直发模式：`deps.platform.unloadingConfirm` 关舱返回 → 清 picking_up_at → `deps.batch.markOrderPicked`（置 4 + 结算 + 计数 + maybeCompleteBatch）；
- close-all：把该用户本批次本点位全部待取(3)订单一次关舱置 4（fulfillOrder 逐单，召唤模式顺带 drawerCtrl(0)）；
- 40s 自动关：平台侧超时自动关舱，任务流转 80 时 `applyStatus` 走同一路径（picked_up_at 非空才置 4），未取餐保持 3，用户可「重新打开」再次开舱。

状态流转：orders 3 已送达 → 4 已完成（picked_up_at 落库）。

### 7.4 批次完成条件与 current_stop 归零

- 直发/通用：`backend/services/batch.js → maybeCompleteBatch(store, batchId)`——批次内全部**有效订单**（status IN (2,3,4)，排除取消/退款/异常）均已取走（picked_up_at 非空或 task_status ≥80）→ 批次 2 → 3 已完成（picked_orders、completed_at 落库）。取消/退款单经 `removeOrderFromBatch` 摘除（batch_removed_at 幂等，总单数 MAX(0,…) 防双扣；组单中批次空置 status=4 标记已取消）；
- 召唤模式：`advanceSummonDelivery` 最后一站取完 → `setBatchCompleted` + `settleRobotAtLoading` 召回上货点 + **current_stop 置 0**（批次完成收尾路径）；
- 测试/异常兜底：`reconcileBatchState`（全部取走→已完成；有已送达订单的待上货批次→推进配送中）。

### 7.5 确认收货（备用入口）

POST /api/delivery/confirm（order_id、scan_code）：订单须 3，scan_code 与 pickup_code 不匹配拒绝；置 4 + settleSales（免开舱按钮流程的备用完成路径）。
