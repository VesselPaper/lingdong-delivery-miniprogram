# 04 · 核心业务链路 · 01 登录与商品库存

## 1. 用户登录（演示登录 vs 真实 code2session）

触发点：用户端登录页「微信一键登录」，或商家端登录页「微信一键登录」（商家端需另填邀请码）。

请求接口：POST /api/auth/login（body：code、nickname、merchant_code、client=student|merchant）。

后端处理：`backend/domains/user/routes.js` → `/auth/login` → `backend/domains/user/service.js → login(store, deps, body, ip)`。
1. 登录限流前置检查：`loginFail.count(ip) >= LOGIN_LIMIT(20)` 时返回 429「登录尝试过于频繁」。限流键为来源 IP，由 `clientIp(req)` 计算：默认只信 socket 对端地址；仅当 `.env` 设 `TRUST_PROXY=1`（确实部署在反向代理后）才采信 `X-Forwarded-For` 首段——XFF 可被客户端伪造，默认采信会令限流形同虚设。失败计数 `loginFail.add(ip)`（10 分钟窗口滑动），成功时 `loginFail.ok(ip)` 回扣 2 次。
2. 凭证判定：`deps.runtime.loginCreds(clientKey)`——用户端（零栋GO）与商家端（零栋商家）是不同小程序，各自独立 appid/secret（WX_APPID/WX_SECRET 与 MERCHANT_WX_APPID/MERCHANT_WX_SECRET）。凭据就绪走真实 code2session：`fetch https://api.weixin.qq.com/sns/jscode2session` 换 openid，失败记限流并返回 401/500；无凭据走演示登录：`demoOpenid(code)` = `'demo_' + sha1(code) 前 24 位`（同一设备账号稳定，可预测、不可吊销，`RUN_MODE=production` 下启动守卫拒绝此配置）。
3. 商家授权（invite.verify，邀请码校验）：商家端——已是商家的老 openid 免码续登；否则必填邀请码，校验失败 403 并记限流。用户端——填了正确邀请码则可凭码升级为商家（`q.upgradeToMerchant`），填错不报错保持学生身份。
4. 建号/更新：`q.findByOpenid` → 无则 `q.create`（role=merchant|student），有则更新昵称、按需升级。

状态流转：无订单状态参与；仅决定 users.role（student / merchant）。

落库字段：users 表新增或更新（openid、nickname、role、updated_at）。

结果返回/后续：返回 `{ token: user.openid, user, runtime }`——**token 即 openid**（`backend/domains/_shared.js → auth` 中间件按 `Authorization: Bearer token` 直接查 users.openid 识别用户，商家接口再叠加 `merchantGuard` 校验 role）。runtime 下发 mode/device_mock/pay_mock/login 标志，商家端据此选择设备控制走真实还是模拟分支。前端将 token 与 user 存入本地 storage，商家端跳转工作台。

边界与说明：
- 演示档 openid 由 code 的 sha1 稳定派生：同一设备账号稳定、可预测、**不可吊销**（服务端无登出接口，登出即前端清本地 token）；因此 `RUN_MODE=production` 的启动守卫会拒绝演示登录配置；
- 真实档 code2session 返回的 openid 由微信侧保证唯一，用户端与商家端分属不同小程序、各自独立凭据，同一微信号在两端的 openid 不同，天然隔离两端身份；
- 登录限流的 Map 上限 10000 条：超过先清过期项再淘汰最早项（`_prune`），避免被伪造 IP 撑爆内存；
- 登录成功 `loginFail.ok(ip)` 回扣 2 次失败计数（而非清零），兼顾连续成功用户的额度恢复与防刷。

## 2. 商品与库存

### 2.1 浏览 / 列表 / 详情（只读）

触发点：首页/商城页 onShow 加载商品流；点击商品进详情页。

请求接口：GET /api/goods/list（category、keyword 过滤）；GET /api/goods/detail?id=；GET /api/goods/categories。

后端处理：`backend/domains/goods/routes.js` → `q.list(store, query)`（`WHERE status=1` 仅在售，`ORDER BY sales DESC` 按销量排序）+ `backend/domains/goods/service.js → withPromoPrices`（附加展示用 sale_price/discount_info，真实金额以下单时 order 域权威计算为准）；详情走 `q.findById` + withPromoPrices。

状态流转：无。

落库字段：无（只读）。

结果返回/后续：商品卡片流（名称/价格/月售/库存售罄态），售罄（stock=0）商品前端显示售罄并禁加购。

### 2.2 下单扣库存（防超卖）

触发点：确认订单页「提交订单」。

后端处理：`backend/domains/order/service.js → createOrder` 内逐行校验库存后，对每个商品调用 `backend/domains/goods/service.js → deductStock(store, id, qty)`——条件更新 `UPDATE goods SET stock=stock-? WHERE id=? AND stock>=?`，校验与扣减原子合一，`changes!==1` 即判定超卖并抛「库存不足」。拆单前还做一次整体预校验（同一商品跨子单多次扣减，先确认总量够）。扣减结果恒 ≥0，绝不为负。

状态流转：goods.stock 减少 quantity，无状态码。

落库字段：goods.stock。

补充说明：
- 拆单场景（单笔 >12 件）下同一商品会被多个子单分次扣减，createOrder 在拆单前先做整体预校验（每商品总量 vs 库存），确认总量够才继续，避免拆单后部分子单扣库存失败造成半成品订单；
- 扣库存失败在 createOrder 内以 throw 抛业务错误，路由层统一转 400 JSON（不再裸 throw 变 HTML 500）；已插入的订单行由 SQLite 事务语义回滚（createOrder 同步执行、失败即中断）。

### 2.3 售罄置 0 不回落

触发点：商家端商品管理「标记售罄 / 恢复库存」；或编辑商品时传 stock=0。

后端处理：`backend/domains/goods/routes.js` → PUT /merchant/goods/stock → `q.updateStock`（toStock 归一化，显式 0 保留为 0）；PUT /merchant/goods 编辑时**未传 stock 保留原库存**（`stock === undefined ? cur.stock : ...`），传 0 同样保留 0——修复过「设库存 0 保存后被重置」的历史缺陷；新增商品 `toStock(stock, 99)` 缺省 99。任何路径都不会把显式 0 悄悄改回默认值。

### 2.4 收货结算销量（幂等 goods_settled）

触发点：订单置「已送达(3)」或「已完成(4)」的多个入口（见链路 6/7 各状态推进点）。

后端处理：`backend/services/goodsStats.js → settleSales(store, orderId)`（由 `backend/domains/goods/service.js` 包装暴露）——两把幂等锁：`goods_settled=1` 已结算跳过；`stock_restored_at` 已回补库存则视为从未售出，不结算。通过后逐 order_items 行 `goods.sales += quantity`，最后写 `orders.goods_settled=1`。平台回调 + 用户取餐双通道触发也只结算一次。

调用点（全部真实存在，任一先到即结算、后到幂等跳过）：
- 送达置 3：`order/service.js → arriveOrder`（召唤真到站）、`platform.js → applyStatus`（任务 70）、`delivery/service.js → processMockArrivals`（演示档模拟到达）；
- 完成置 4：`order/service.js → fulfillOrder`（关舱）、`services/batch.js → markOrderPicked`（直发关舱）、`delivery/routes.js /delivery/confirm`（扫码确认收货）。

### 2.5 取消 / 退款回补库存（幂等 stock_restored_at）

触发点：订单取消（链路 8）、退款同意/异常退款（链路 9）、取餐超时驳回（链路 10）。

后端处理：`backend/services/orderCancel.js → cancelLocal` 内调用 `goodsStats.restoreStock`——同样双幂等锁（`goods_settled=1` 已结算不补；`stock_restored_at` 已补过不补），通过后 `goods.stock += quantity` 并写 `orders.stock_restored_at`。幂等键用 stock_restored_at 而非 goods_settled：取消单永远不会被结算，「用户取消 / 平台推送 110 / 商家异常退款」多条路径各补一次会被正确挡下。
