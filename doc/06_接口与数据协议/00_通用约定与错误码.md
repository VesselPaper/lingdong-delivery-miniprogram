# 06 · 接口与数据协议 · 00 通用约定与错误码

## 一、通用约定

### 1.1 Base URL 与静态资源

| 项 | 约定 |
| --- | --- |
| 开发环境 | `http://127.0.0.1:3000/api`（默认监听 `0.0.0.0:3000`，`BIND_HOST` 可改） |
| 生产环境 | 由小程序 `config.js` 的 `baseUrl` 配置，需为小程序后台白名单域名（https） |
| 请求格式 | `Content-Type: application/json`，body 为 JSON（`express.json` 上限 8MB，含图片 base64 上传） |
| 静态资源 | `/uploads/*`（商家/头像上传）、`/store-img/*`（商品种子图）；图片字段由后端统一转成绝对 URL |
| 其它页面 | 管理员工具页 `/admin/`、可视化大屏 `/dashboard/`（与 API 同端口，独立路径） |
| 平台回调 | 微信支付回调与开放物流平台回调需公网可达 https 地址（开发可用内网穿透） |

### 1.2 统一响应结构

所有业务接口（除平台/微信回调外）返回：

```json
{ "code": 0, "msg": "success", "data": { } }
```

- `code = 0` 表示成功；非 0 为业务失败码，数值与 HTTP 状态码一致。
- `msg` 为人类可读说明，失败时为具体原因（可直接展示给用户）。
- `data` 可为对象、数组或 `null`。
- **资源绝对地址化**：`ok()` 统一处理后，响应中所有 `/uploads/`、`/store-img/` 前缀的相对路径
  会按 `PUBLIC_ORIGIN`（未配置时按请求自身 host）拼接为完整 URL，前端无需二次拼接。
- **例外**：`/api/pay/notify` 与 `/api/platform/*` 回调类接口按微信/平台协议返回
  `{ "code": "SUCCESS"|"FAIL", "message": "…" }`（见 5.4 节），不套用本结构。

### 1.3 鉴权方式

| 类型 | 头字段 | 取值 | 判定逻辑 |
| --- | --- | --- | --- |
| 用户（student） | `Authorization: Bearer <token>` | 登录返回的 `token`（即 openid） | `_shared.js → auth`：`users.openid` 命中即通过，否则 401 |
| 商家（merchant） | `Authorization: Bearer <token>` | 同上 | `_shared.js → merchantGuard`：先 `auth`，再校验 `role === 'merchant'`，否则 403 |
| 管理员 | `x-admin-token: <token>` | `POST /api/admin/login` 签发的随机 session token | `_shared.js → adminGuard`：`admin_sessions` 有效（未过期且账号启用）即通过，否则 401 |

要点：

- token 即 openid 本身（演示档为 `demo_` + code 哈希）；正式环境接入微信 code2session 后仍以 openid 为 token，
  登录失效（users 表无此 openid）统一返回 401。
- 管理员会话有有效期（`admin_sessions.expires_at`），改密后吊销该账号全部会话；`x-admin-token` 只认请求头，不支持 query 传参。
- 商家端登录受邀请码机制约束（`services/merchantInvite.js`）：非商家 openid 登录商家端必须携带有效 `merchant_code`，否则 403；
  用户端填了正确邀请码可升级为商家。登录接口同时带失败限流（`services/merchantInvite` 与 user 域 `loginFail`）。
- 敏感操作（改价/上下架/退款/取消/派车/设备控制/活动/管理员操作）落 `audit_logs` 审计表（`_shared.js → audit`）。

### 1.5 时间、编号与分页约定

| 项 | 约定 |
| --- | --- |
| 时间格式 | 数据库统一 `YYYY-MM-DD HH:MM:SS`（SQLite `datetime('now','localtime')`，本地时区）；`server_time` 为 zh-CN 本地化字符串 |
| 订单编号 | `order_no` 日期+当日序号（`services/seq.js`，拆单时每子单一个连号）；展示用 `code_short`（人读短号 `MMDD-NN`） |
| 批次编号 | `batch_no` 前缀 `BD`；展示用 `code_short`（`B-MMDD-NN`）；`daily_seq` 为当日序号（每天从 1 重置） |
| 取餐码 | `pickup_code` 4 位数字，在未结束订单（0/1/2/3）范围内查重唯一，兼作平台开舱校验码 |
| 金额 | 元为单位，2 位小数（`total_amount`/`original_amount`/`discount_amount`/`delivery_fee`）；支付与回调按「分」比对 |
| 分页 | 当前接口以全量返回为主；批次列表限近 20 个（`recentBatches(store, 20)`）、大屏/管理页历史取最近 100 条；后续数据量大可统一加 `page/size` |

### 1.6 状态字典速查

| 字典 | 取值 |
| --- | --- |
| 订单 `status` | 0 待支付 / 1 待接单 / 2 配送中 / 3 已送达 / 4 已完成 / 5 已取消 / 6 配送异常 / 7 已退款 |
| 批次 `status` | 0 组单中 / 1 待上货 / 2 配送中 / 3 已完成 / 4 已取消（清理） |
| 任务 `task_status` | 0 排队中 / 10 任务已接收 / 20 去上货点 / 30 到达上货点 / 40 上货中 / 50 已上货 / 60 去取货点 / 70 到达取货点 / 71 等待取餐 / 80 完成 / 90 上货失败 / 100 取货失败 / 110 取消 / 120 上货流程挂起 / 150 关闭 |
| 售后 `status` | 0 待处理 / 2 已拒绝 / 3 已退款 / 4 已处理（投诉）；`type`：refund 退款 / complaint 投诉 |
| 取消申请 `status` | 0 待处理 / 2 已拒绝 / 3 已同意取消 |

## 五、错误码与业务失败约定

### 5.1 HTTP 状态码语义

| 码 | 语义 | 典型场景 |
| --- | --- | --- |
| 400 | 参数错误 / 业务状态不允许 | 缺参、格式错、售罄、店铺歇业、状态机不允许（如「机器人还未送达」「取餐码不匹配」「已超可取消时间」） |
| 401 | 未登录 / 登录失效 | `auth` 无 token 或 openid 不存在；`adminGuard` 会话缺失/过期；登录凭证错误 |
| 403 | 无权限 | 非商家访问 `/api/merchant/*`；商家邀请码缺失/无效/已吊销 |
| 404 | 资源不存在 | 订单/商品/批次/任务/申请/售后单不存在 |
| 409 | 并发冲突 / 状态已变更 | 取消/退款 CAS 抢占失败（「订单已取消或状态已变更，请刷新后重试」） |
| 429 | 触发限流 | 登录尝试过于频繁（用户登录、管理员登录账号+IP 锁定） |
| 500 | 服务端异常 | 未捕获异常、平台同步失败 |
| 501 | 功能未配置 | 支付通道未配置（`wxpay.enabled()` 为假）、支付回调未启用 |
| 502 | 上游调用失败 | 微信下单失败、开舱/关舱失败、获取机器人列表/地图失败、真实退款失败 |

### 5.2 业务失败约定

- 业务接口失败一律返回 **HTTP 状态码 + JSON `{ "code": <状态码>, "msg": "<可直接展示的中文原因>" }`**，`data` 缺省；
  `code` 与 HTTP 状态码一致，前端以 `code !== 0` 判定失败并展示 `msg`。
- 部分接口附带结构化错误原因字段：如开舱门禁 `{ "code": 400, "msg": "…", "reason": "not_at_loading_point" }`、
  召唤失败 `{ "code": 502, "msg": "…", "reason": "summon_failed" }`，供前端分流展示（友好提示 vs 红字报错）。
- 状态机类校验集中在 service 层（如 `orderTrulyDelivering`、`withinFreeCancelWindow`、批次并发抢占），失败原因区分「可自由取消」/「提交取消申请」/「退款投诉」三条路径。
- **回调类接口例外**（微信/平台协议要求）：`POST /api/pay/notify` 返回 `{ "code": "SUCCESS"|"FAIL", "message": "…" }`；
  `POST /api/platform/check-order` 返回 `{ "code": "COMM_200", "data": null | { "keyEvent": { "eventName": "forceCloseTask", "taskSubStatus": 201, "eventDesc": "订单已取消/退款" } }, "msg": "ok" }`。
- 商家端手机号统一脱敏展示（`maskPhone`，`138****0000`），明文仅服务端内部使用。

### 5.3 关键兜底机制（数据一致性约定）

- **库存/销量口径**：下单即时扣库存（防超卖）；订单到达收货完成（status 3/4，含平台任务 80、用户关舱、商家测试完成）时已售 +1（幂等，`goods_settled` 标记）；订单取消/退款且未结算时回补库存（不记已售）。
- **批次状态联动**：任务 80 完成 → 订单已完成并标记已取；任务 110/150 取消 → 订单取消并从批次计数移除；批次内全部有效订单已取/完成 → 批次 3 已完成。
- **自动调度**：`BATCH_SCAN_MS`（默认 15s）扫描自动派车（组单中达 `BATCH_MAX_ORDERS`=12 单或自动接单模式超 `BATCH_WAIT_MS`=90s）；
  `DELIVERY_SCAN_MS`（默认 60s）扫描超时未接单 → 订单置 6 配送异常；取餐超时两段式（先送其它单 → 返回再等 → 取消）。
- **回调防伪**：平台回调地址带 `?token=`（创建任务时拼接），`callbackAuthorized` 校验，防伪造任务状态驱动订单/退款。
