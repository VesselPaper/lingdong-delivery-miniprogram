`POST /admin/robot/cancel-tasks` 的实现顺序（`domains/admin/routes.js`）：

1. **枚举该设备全部任务**：先用 `platform.queryDeviceTasks(deviceSn)`（平台 `deviceCtrl/queryDeviceTasks`，`GET ?deviceSN=`，货舱占用是任务占用的权威来源）枚举；失败或为空则回退 `platform.deviceActiveTasks(store, sn)`（拉全量任务按设备过滤，受分页上限影响）。`source` 据此取 `platform` / `platform-empty` / `local-fallback`。
2. **本地统一落账**：对该设备关联的本地活跃订单（`activeOrdersByDevice`，经批次关联）逐个走 `order.applyOrderCancelled`（作废任务 + 回补库存 + 摘批次 + 平台召回），并记录已处理过的平台任务 id，避免下一步重复关闭。
3. **关闭剩余孤儿平台任务**：第 2 步未覆盖的平台任务逐个 `platform.closeTask`，逐项容错。**经第 2 步统一落账关闭的平台任务也计入 `closed`**（按 `delivery_tasks.recall_status=1` 计数，即平台召回成功），避免出现「取消了 N 单但 `closed=0`」的误导。
4. **批次置 4**：该设备涉及的活跃批次（`activeBatchesByDevice`）全部 `cleanBatch`。
5. **返回**计数（`closed` / `cancelled` / `batch_cleaned`）与失败列表 `failed[]`。

> 与旧 `/admin/robot/stop-cancel` 的差别：旧接口只关「平台任务」且最多 3 个，不回补库存、不摘批次，本地订单会卡在「配送中」；本接口逐个关闭全部任务并走 order 域统一落账，双端一致、不留脏数据。

#### 2.6.1 审计留痕与状态流水（两条链路：谁写、何时写、为什么）

管理端「操作均按账号留痕审计」与「详情抽屉 → 状态时间线」由两条**互不依赖**的后台链路支撑，业务代码只在少数入口打标注，落库统一由中间件/采集器完成。

**链路 A：操作审计（`audit_logs`）—— `domains/_shared.js` 的 `audit()` + `auditMw`**

| 项 | 说明 |
| --- | --- |
| 挂载 | `server.js` 中 `app.use('/api', auditMw)`，位于**所有域路由之前**（`user/goods/order/delivery/admin` 全部覆盖） |
| 记录范围 | 只记写请求；`GET` / `HEAD` / `OPTIONS` 直接跳过 |
| 排除前缀 | 默认 `/api/cart,/api/address,/api/user,/api/pay/notify`，可用环境变量 `AUDIT_EXCLUDE_PREFIXES`（逗号分隔）整体覆盖；否则用户端加购物车/改地址这类高频操作会把审计表刷爆 |
| 路径判断 | 一律用 `req.originalUrl`——中间件挂在 `/api` 上时 `req.path` 已被剥掉挂载前缀，用 `path` 会导致排除失效 |
| 记录时机 | 包一层 `res.json`，在响应前落库（此时 handler 的 `audit()` 标注一定已写入），并从中取失败原因；`res.on('finish')` / `res.on('close')` 兜底非 JSON 响应与连接中断；`done` 守卫防重复落库 |
| 身份 | `req.admin`（adminGuard）优先，否则 `req.user`（auth），均落 `user_id` + `user_role`；两者都没有则记 `0` / `''` |
| action | 优先用 handler 标注；否则由 `method + originalUrl` 规范化（去前导 `/`、去前导 `api/`）得出，形如 `order/create [POST]` |
| target | 优先用标注；否则按请求体 `order_id / batch_id / task_id / platform_task_id / goods_id / activity_id / id / device_sn` 顺序取首个非空，形如 `order#123` |
| detail | 成功用标注；失败优先标注，否则取响应体 `msg`（如「原密码不正确」） |
| 脱敏截断 | `detail` ≤500 字符、`ua` ≤200、`ip` ≤60、`action` / `target` ≤120 |
| 成功/失败 | `ok` = 1（HTTP 2xx/3xx）/ 0（4xx/5xx）；`status` 为 HTTP 状态码；`ms` 为处理耗时（毫秒） |
| 读取 | `GET /admin/audit`（见上表），默认只看 `user_role='admin'` |

> **语义变更（重要）**：`audit(req, action, target, detail)` 由「直接落库」改为「纯标注」——只写 `req._audit`，不写库；真正落库由 `auditMw` 在响应时统一负责。函数签名不变，因此原有 37 处调用一行都没改。副作用是写库时机从「handler 内即时」变为「响应时」，好处是**成功与失败都留痕**。
>
> **为什么这么改**：此前靠每个 handler 手写一行 `audit()`，商家端有 29 处但管理端只有 8 处，漏了 14 个写接口（`order/cancel`、`task/close-void`、`task/void`、`task/close`、`task/cancel`、`drawer`、`robot/*`、`control/*`、`landmarks/sync`、`precreate/del`），导致「操作均按账号留痕审计」对管理端大部分操作不成立。中间件兜底后，**新增写接口自动进审计**。

**链路 B：业务状态流水（`status_events`）—— `services/statusEvents.js`**

| 项 | 说明 |
| --- | --- |
| 目标 | 还原「每个状态变更的具体时间（含操作者）」。orders 只有零散时间列、delivery_tasks 只有 `updated_at` / `void_at`，靠现有列无法还原任务状态历史 |
| 写入方 ① | `record()` 直接落一条 |
| 写入方 ② | `diffOnce()` 集中采集器：内存保存「活跃实体 → 状态」快照，比对发现变化即落一条；实体离开活跃集（进入终态）时补记终态迁移；**首次运行只建快照、不落事件**（避免把存量数据当成一轮变更刷进去） |
| 写入方 ③ | `hintActor()` 登记「操作者线索」（由 `audit()` 顺带调用，带 `STATUS_HINT_TTL_MS` 有效期，命中即消费）；`recordTransition()` 命中线索则用线索里的操作者署名，否则记 `system` |
| 活跃判定 | order `status NOT IN (4,5,7)`；batch `status NOT IN (3,4)`；task `task_status NOT IN (80,110,150)` |
| 常驻启动 | `server.js` 首次 `diffOnce` 建快照，之后每 `STATUS_EVENTS_MS`（默认 2500ms）跑一次，**与 WS 订阅者无关**（无订阅也照跑） |
| 已知局限 | 同一实体在 2.5 秒内连续跳两次状态，只会记到最终值（采集器是定时快照比对，非写点埋点） |
| 读取 | `GET /admin/timeline`（见上表） |

### 2.8 公开（shop/status 等）

免鉴权接口完整清单见 1.4 节。其中与业务直接相关且用户端高频使用的：

- `GET /api/shop/status` —— 店铺营业状态：用户端据此展示「歇业」标签、结算按钮置灰；
  后端 `POST /api/order/create` 在店铺 `business_status=closed` 时兜底拒绝（400「店铺歇业中，暂无法下单」）。
- `GET /api/goods/*`、`GET /api/activity/list`、`GET /api/landmarks` —— 用户端商城与点位选择。
- `GET /api/dashboard/*` —— 大屏展示（只读，无写权限）。
