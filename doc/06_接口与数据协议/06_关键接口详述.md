# 06 · 接口与数据协议 · 06 关键接口详述

## 三、关键接口详述

> 以下为核心链路接口的入参/出参示例与处理逻辑要点（对应 service 函数定位）。

### 3.1 用户/商家登录 —— `POST /api/auth/login`

**实现**：`backend/domains/user/routes.js` → `backend/domains/user/service.js → login(store, deps, body, ip)`

入参（用户端 `client=user` 走微信 code2session；**商家端 `client=merchant` 走账号密码**，2026-09-24 起邀请码机制退役）：

```json
// 用户端
{ "code": "wx.login 返回的 code", "client": "user", "nickname": "可选昵称" }
// 商家端
{ "username": "商家账号", "password": "账号密码", "client": "merchant", "nickname": "可选昵称" }
```

出参：

```json
{ "code": 0, "msg": "success", "data": {
  "token": "用户端=openid / 商家端=随机32字节hex（后续请求的 Bearer token）",
  "user": { "id": 1, "openid": "…", "nickname": "…", "phone": "…", "role": "student|merchant", "merchant_role": "owner|staff" },
  "runtime": { "mode": "demo|production", "device_mock": true, "pay_mock": true, "login": "demo|wx" }
} }
```

处理逻辑要点：

1. 登录失败计数限流（超过 `LOGIN_LIMIT` → 429），账号密码登录同样防暴力试密码。
2. 用户端：凭据就绪走微信 `code2session` 换真实 openid；否则演示模式 `openid = 'demo_' + sha1(code)`（生产档启动守卫拒绝）。商家端：`findByUsername` + `verifyPassword`（scrypt 恒定时间比较）+ `status===1` 通过才签发 token。
3. 商家端 token 可吊销（管理员重置密码/停用 → `token=NULL`）；用户端 token 即 openid 不可吊销。
4. 学生不能凭码升级商家（升级逻辑已删除）；商家权限矩阵见 `doc/04_核心业务链路/01_登录与商品库存.md` §1.1。

### 3.2 创建订单 —— `POST /api/order/create`

**实现**：`backend/domains/order/routes.js` → `backend/domains/order/service.js → createOrder(store, deps, body, userId)`

入参：

```json
{ "landmark_id": "8", "landmark_name": "东苑1栋", "contact_name": "张三", "contact_phone": "13800000000",
  "remark": "不要辣", "activity_id": 1,
  "items": [ { "goods_id": 1, "quantity": 2 } ] }
```

出参（单笔）：

```json
{ "code": 0, "data": { "order_id": 7, "order_no": "LD…", "total_amount": 21.8, "pickup_code": "1234" } }
```

出参（总件数 > `BATCH_MAX_ITEMS`(12) 自动拆单）：

```json
{ "code": 0, "data": { "orders": [ { "order_id": 7, "order_no": "…", "total_amount": 10.9, "pickup_code": "1234" } ],
                        "split": true, "split_count": 2, "total_amount": 21.8 } }
```

处理逻辑要点：

1. 校验：店铺营业（歇业 400）、items 非空、收餐人姓名≤20、手机号 `1\d{10}`、送达点位须为 `deliverPoint`（P2-8）。
2. 计价以商品表单价为权威；优惠由后端 `promotion` 服务重算（前端自报价无效）；配送费按店铺配置快照进订单（拆单时整单只收一次）。
3. 取餐码 4 位随机并在未结束订单范围查重唯一（撞码重摇，兜底用当日序号派生）。
4. 逐单 `deductStock` 条件更新扣库存（校验与扣减原子，防超卖）；下单成功删除购物车中本次下单的商品（非整单清空）。
5. 返回 `order_id/order_no/total_amount/pickup_code`；拆单返回多单结构。

### 3.3 发起支付 —— `POST /api/order/pay`

**实现**：`backend/domains/order/routes.js` → `backend/domains/order/service.js → payOrder(store, deps, order, user)`

入参：`{ "id": 7 }`

出参（真实支付）：

```json
{ "code": 0, "data": { "order_id": 7, "payParams": { "timeStamp": "…", "nonceStr": "…",
  "package": "prepay_id=…", "signType": "RSA", "paySign": "…" } } }
```

出参（`PAY_MOCK=true` 试点档）：

```json
{ "code": 0, "data": { "order_id": 7, "mock": true, "auto_accept": true, "msg": "试点模式：模拟支付成功，已自动接单并入配送批次" } }
```

处理逻辑要点：

1. 仅 `status=0` 可支付；非真实支付档直接 `markPaidMock` 置已支付（status→1），并 `push.broadcast({type:'order_created', order_id})` 通知商家端。
2. 真实档校验微信四要素（缺失 → 501「支付通道未配置」），`wxpay.jsapiPay` 下单（金额按分、描述「零栋GO-订单NO」）；失败 → 502。
3. 支付结果以 `POST /api/pay/notify` 回调为准：平台证书验签 → 商户号/appid 比对 → 事件幂等（`pay_notifications`）→ 金额比对（分）→ CAS 置已支付（仅待支付可迁移）→ 推送 + `maybeAutoAccept`（自动接单）。

### 3.4 批次派车 —— `POST /api/merchant/delivery/batch/dispatch`

**实现**：`backend/domains/delivery/routes.js` → `backend/domains/delivery/service.js → doDispatchBatch(store, deps, batchId, deviceSn)`

入参：`{ "batch_id": 1, "device_sn": "可选，指定机器人" }`

出参（批次详情）：`{ "code": 0, "data": { "id": 1, "batch_no": "BD…", "status": 1, "status_text": "待上货", "device_sn": "…", "total_orders": 4, "orders": […], "route": […] } }`

处理逻辑要点：

1. 前置门禁（真实档）：可指定 `device_sn`，未指定时 `platform.pickAvailableRobot()` 自动挑在线空闲车；无可用车给出设备明细提示；`isRobotBusy` 忙碌则拒绝。
2. 并发抢占：任何 await 之前先条件更新 `status 0→1`（`queries.claimDispatch`），失败方直接报「该批次已派车，不能重复派车」；抢占后任一步失败则回滚（已建任务作废 + 批次退回组单中 + 清 device_sn/route）。
3. 批次内待配送订单（status 1/2）为空 → 400。
4. 非召唤模式：为每单创建独立平台任务（`platform.createTasksForBatch`，各单 outOrderNo/取餐码独立、指定同一设备）；召唤模式（`summonDelivery`）不创建平台任务，仅定型设备。
5. 批次内订单置 2 配送中；路线规划推迟到「开始配送（关舱后）」执行；返回批次详情。

### 3.4A 扫码识别机器人 —— `POST /api/merchant/device/scan`

**实现**：`backend/domains/delivery/routes.js`（内联 + `service.doDispatchBatch` + `platform.grantControl/robotAtLoadingPoint`）

入参：`{ "deviceSn": "R105A2601A76GK00K00" }`

出参：`{ "batch_id": 1, "batch_no": "BD…", "device_sn": "…", "status": 1, "status_text": "待上货", "total_orders": 4, "orders": [ { "id": 7, "order_no": "…", "pickup_code": "1234", "landmark_name": "东苑1栋", "items": […], "task": { "task_id": 12, "platform_task_id": "…", "device_sn": "…", "task_status": 30, "status_text": "到达上货点" } } ], "route": [ { "stop": 1, "landmark_id": "2", "landmark_name": "东苑1栋", "order_ids": [7, 8] } ], "control_ok": true, "control_msg": "", "at_loading_point": true, "distance_m": 0 }`

处理逻辑要点：

1. Mock 档取最早一个待上货/组单批次；真实档按扫码设备号精确匹配待上货批次（绝不装错车）。
2. 未派车的组单中批次（status=0）→ 现场直接 `doDispatchBatch` 派给该车（并发抢占被抢则试下一批）。
3. 回写 `device_sn` 到批次与批次内任务；`grantControl` 获取控制权（`control_ok/control_msg`）。
4. 附带 `at_loading_point/distance_m/loading_msg`（车是否已到上货点），供上货页展示。

### 3.5 批次开舱（整批上货）—— `POST /api/merchant/device/batch/open-bin`

**实现**：`backend/domains/delivery/routes.js`（内联 + `platform.verifyBatchLoading/grantControl/drawerCtrl/robotAtLoadingPoint`，召唤模式走 `service.ensureLoadingArrival`）

入参：`{ "batch_id": 1 }`

出参：`{ "code": 0, "data": { "batch_id": 1, "opened": 4 } }`；召唤模式车未到时出 `{ "batch_id": 1, "opened": 0, "summoned": true, "waiting": true, "msg": "机器人正在前往上货点，请稍候再次点击打开舱门" }`

处理逻辑要点：

1. 真实档门禁：`robotAtLoadingPoint` 必须已到达上货点，否则 400（带 `reason:'not_at_loading_point'`，前端友好提示而非红字报错）。
2. 召唤模式：先 `ensureLoadingArrival` 等车到（真实到达信号，非测距），`drawerCtrl(1)` 开舱；车忙时 400「暂无空闲机器人」。
3. Route B（真实）：`grantControl`（600s，ctrlId 持久化批次行）→ 逐任务 `verifyBatchLoading`（strategies=anyCode 各单取餐码，autoOpen=true），任一失败 → 502。
4. 全部成功后 `setBatchLoading` 批次状态推进。

### 3.6 批次开始配送 —— `POST /api/merchant/device/batch/dispatch`

**实现**：`backend/domains/delivery/routes.js`（内联 + `platform.confirmBatchLoading` / `service.startSummonDelivery` / `batch.planRoute`）

入参：`{ "batch_id": 1 }`

出参：`{ "code": 0, "data": { "batch_id": 1, "dispatched": 4 } }`；召唤模式出 `{ "batch_id": 1, "summoned": true, "detail": {…} }`

处理逻辑要点：

1. 召唤模式：`startSummonDelivery` —— 按单数加权规划路线、召唤到首站、该站订单置待取货（不创建平台配送任务），失败 400。
2. 普通模式：先 `batch.planRoute` 按收餐点位分组+最近邻写入 `batch.route`（失败不阻断配送）→ 逐任务 `confirmBatchLoading`（各单 loading/confirm，任务→50 已上货）→ 释放控制权（失败不阻断，等平台超时自动执行）→ `setBatchDelivering` 批次→2。

### 3.7 用户取餐开舱 —— `POST /api/delivery/pickup-open`

**实现**：`backend/domains/delivery/routes.js`（内联 CAS 抢占 + `platform.unloadingVerify/drawerCtrl`）

入参：`{ "order_id": 7 }`

出参：`{ "code": 0, "data": { "order_id": 7, "status": 3, "opened_at": "2026-09-03 12:00:00", "test": false } }`（召唤模式带 `"summon": true`；本地测试兜底带 `"test": true`）

处理逻辑要点：

1. 状态须为 3（已送达）/4（已取走后可重开）；重开限时 `PICKUP_REOPEN_WINDOW_MS`（默认 10 分钟）、限次 `MAX_PICKUP_OPEN`（默认 3 次），CAS 抢占保证并发双击只成功一次。
2. 开舱置 `picking_up_at`（「正在取餐」，取餐超时计时暂停）；**开舱不标记已取走**（P1-2：真正确认取餐收口到关舱）。
3. 有真实任务（deviceSn+platform_task_id）调 `unloadingVerify` 开舱（失败 502）；召唤模式 `drawerCtrl(1)`；无任务本地直接成功（`test:true` 测试兜底）。

### 3.8 用户取餐关舱 —— `POST /api/delivery/pickup-close`

**实现**：`backend/domains/delivery/routes.js`（内联 + `deps.batch.markOrderPicked` / 召唤模式 `deps.order.fulfillOrder`）

入参：`{ "order_id": 7 }`

出参：`{ "code": 0, "data": { "order_id": 7, "status": 4, "test": false } }`

处理逻辑要点：

1. 状态须为 3/4；真实任务调 `unloadingConfirm` 关舱（平台 40s 未调用自动关舱，任务 80 由 `applyStatus/onTaskStatus` 走同一路径）。
2. **关舱 = 真正取走**：清 `picking_up_at` → `markOrderPicked`（订单→4 已完成 + 结算销量 + 批次已取计数+1，全部取完批次完成）。
3. 召唤模式关舱是「尽力而为」：`drawerCtrl(0)` 失败不阻断取餐记录与批次推进（防订单卡在待取货导致机器人永不推进）。

**实现**：`backend/domains/delivery/routes.js` → `backend/services/batch.js → getBatchDetail(store, batchId)`

Query：`?batch_id=1`

出参：

```json
{ "code": 0, "data": {
  "id": 1, "batch_no": "BD…", "daily_seq": 3, "status": 2, "status_text": "配送中",
  "device_sn": "…", "total_orders": 4, "picked_orders": 1, "total_items": 9,
  "orders": [ { "id": 7, "order_no": "…", "daily_seq": 12, "pickup_code": "1234",
                "landmark_id": "8", "landmark_name": "东苑1栋", "picked_up": false,
                "task": { "task_id": 12, "platform_task_id": "…", "task_status": 70, "status_text": "已到达取餐点" },
                "items": [ { "goods_id": 1, "goods_name": "…", "goods_image": "…", "price": 10.9, "quantity": 2 } ] } ],
  "route": [ { "stop": 1, "landmark_id": "2", "landmark_name": "东苑1栋", "order_ids": [7, 8] } ],
  "route_text": "东苑1栋 → 东苑2栋" } }
```

要点：`orders[].items` 供上货操作页逐单逐商品展示；`daily_seq` 为当日批次序号；`picked_orders` 为已取走订单数（一车多单进度）。404 批次不存在。

### 3.11 配送异常重配 —— `POST /api/merchant/order/exception/retry`

**实现**：`backend/domains/order/routes.js`（内联 + `deps.batch.removeOrderFromBatch/addOrderToBatch`）

入参：`{ "order_id": 44 }`

出参：`{ "code": 0, "data": { "order_id": 44, "status": 2, "batch_id": 3, "batch_no": "BD…", "msg": "已重新并入批次 BD…，请派车上货配送" } }`

处理逻辑要点：

1. 仅 `status=6`（配送异常）可操作（400 拒绝其它状态）；404 订单不存在。
2. 按 `order_id` 精确作废旧任务（`task_status=110`、`void_at` 落库；不按 batch_id 以免误伤同批次其它订单）。
3. `removeOrderFromBatch` 从旧批次摘除 → `addOrderToBatch` 并入新的「组单中」批次（后续由自动定型扫描——满 12 件或成立超 90s——或商家上货按钮即时定型）。
4. `setExceptionHandled(order_id, 'retry')` 记录处理态（异常列表 `handled_text=已重新配送`）。

### 3.12 管理员登录 —— `POST /api/admin/login`

**实现**：`backend/domains/admin/routes.js`（内联 + `services/adminAuth.js`）

入参：`{ "username": "admin", "password": "…" }`

出参：

```json
{ "code": 0, "data": { "token": "随机 session token", "admin": { "id": 1, "username": "admin", "nickname": "…", "role": "admin" } } }
```

处理逻辑要点：

1. 账号+IP 失败计数限流：连续失败 `ADMIN_LOGIN_MAX`（默认 5）次锁定 `ADMIN_LOGIN_WINDOW_MS`（10 分钟），锁定中 429。
2. `adminAuth.findByUsername` + `verifyPassword`（scrypt）校验；账号禁用（status≠1）拒登；失败记一次并 401。
3. 成功签发 session（`issueSession` 随机 token 落 `admin_sessions`，带过期时间），更新 `last_login_at`，落审计。
4. 后续请求带 `x-admin-token`；`GET /api/admin/me` 用于前端启动/刷新时校验会话。
