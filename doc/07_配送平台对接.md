# 07 配送平台对接文档（robox 开放物流平台）

> 适用对象：后端维护与联调人员。本文描述后端与开放物流平台（robox，生产 `robox.eventec.cn`，测试 `test-robox.eventec.cn`）的对接全貌：凭据、启停开关、任务体系、召唤/直发两种配送模式、一车多单、本地 Mock 状态机、机器人侧能力与后台定时器。
> 代码定位约定：`platform.js:函数名` = `backend/services/platform.js`；`delivery/service.js:函数名` = `backend/domains/delivery/service.js`；`batch.js:函数名` = `backend/services/batch.js`；`timers.js` = `backend/domains/delivery/timers.js`；`runtime.js` = `backend/services/runtime.js`。
> 所有接口路径、任务状态码、函数名均摘自代码，字段口径以 Apifox「开放物流平台」open-logis_1.0 导出文档（接口\默认模块.openapi.json）为准。

## 1. 对接总览

### 1.1 平台角色与对接模型

后端（lingdong-backend）是开放物流平台的**调用方（principalId 主体）**，负责：

- 任务下发：排队任务 / 直发任务 / 召唤轻任务（详见 1.4）；
- 状态同步：平台回调（feedbackDeliveryTaskUrl）+ basicList 轮询兜底（`syncTaskStatus`）；
- 设备控制：授权（grant/release）、开舱/关舱（drawerCtrl、loading/verify、unloading/verify）；
- 数据回灌：平台点位（buildingList / landmarkInfo）同步进本地 `landmarks` 表；地图（mapInfo）与机器人实时位置（eviz iotGatewayProxy）供监控页/追踪页使用。

### 1.2 凭据与配置（PLATFORM_* 环境变量）

| 环境变量 | 含义 | 默认值 |
|---|---|---|
| `PLATFORM_MOCK` | `true` 走本地模拟状态机；`false` 调真实平台 | 未设置视为 false（真实） |
| `PLATFORM_APPID` | 请求 Header `appid` | 空 |
| `PLATFORM_SECRET` | 请求 Header `secret`；同时用于派生回调令牌 | 空 |
| `PLATFORM_PRINCIPALID` | 请求参数 `principalId`（主体 ID） | 空 |
| `PLATFORM_BASE` | 平台服务地址 | `https://test-robox.eventec.cn/service-open-logis` |
| `PLATFORM_CALLBACK_BASE` | 回调公网地址（如 cloudflared 内网穿透域名），未配置则创建任务不带回调、靠 basicList 轮询兜底 | 空 |
| `PLATFORM_CALLBACK_TOKEN` | 回调防伪令牌（显式配置）；未配置时由 `sha256('lingdong-callback:'+SECRET)` 取前 32 位派生（跨重启稳定） | 空 |
| `PLATFORM_POLL_MS` | 任务状态轮询间隔 | 8000 |

`platformReady()`（platform.js）判定：`APPID && SECRET && PRINCIPALID` 三者齐全才可发起真实调用。所有 HTTP 请求头固定携带 `Content-Type: application/json;charset=UTF-8`、`appid`、`secret`；单次请求 10s 超时（`requestPlatform`），超时即销毁连接，避免挂起请求拖死轮询/派车串行链路。

### 1.3 启停开关与运行档位（PLATFORM_MOCK / RUN_MODE）

runtime.js 在启动期把运行档位做成强约束（`assertBootable`，不合法直接 `process.exit(1)`）：

| RUN_MODE | PLATFORM_MOCK 约束 | 说明 |
|---|---|---|
| `demo`（默认） | **必须 true** | 演示档禁止连接任何真实物流平台 |
| `pilot` | 可 false（联调真机）；连**生产**平台需 `ALLOW_UNSAFE_PROD_PLATFORM=true` 显式担责 | 测试环境主机名以 `test-` 开头判定 |
| `production` | **必须 false** | 正式档必须真实配送 |

派生运行标志（server.js 一律读这些，不再直读 env）：

- `realPlatform = !platformMock`：是否走真实平台分支；
- `deviceMock = (mode==='demo')`：设备控制是否本地假装（控制 `mock-dispatch` / `test-complete` / 部分门禁放行）；
- `summonDelivery = (SUMMON_DELIVERY==='true')`：是否启用召唤多单配送（默认 false = 直发一单一单送）。

### 1.4 三类平台任务对比

| 类型 | 平台接口 | 用途 | 创建函数 | 备注 |
|---|---|---|---|---|
| 排队任务 queue | `POST /open-api/v1/deliveryTask/queue/create` | 单任务排队配送（完整上货流程），取餐超时返程重建 | `realDispatch` / `realDispatchBatch` / `recreatePickupTask` | 机器人充电中不拉取排队任务（待与越凡确认待机策略） |
| 直发任务 direct | `POST /open-api/v1/deviceCtrl/create/direct` | Route B 直接下发，`syncLoading=0` 异步上货 | `createDirectTask` | 需先 `deviceCtrl/authority/grant` 持有控制权；另有预留接口 `create/pre`（预创建，`taskExpireTime=600` 秒过期自动关舱）与 `del/pre` 删除预创建，见 `preCreateTask` / `deletePreCreateTask` |
| 轻任务 lightTask | `POST /open-api/v1/lightTask` | 召唤机器人到点位待命（不创建配送任务、不锁定批次） | `summonToLoadingPoint` / `summonToPoint` / `summonDeliveryToStop` | 召唤会中断正在执行的配送任务，调用前须确认无活跃配送 |

## 2. 任务体系

### 2.1 任务创建入口

- 单任务排队：`createQueueTask(store, order)` —— 建本地 `delivery_tasks` 行（status=0「排队中」），订单置 status=2 并挂 `delivery_task_id`；真实档调 `realDispatch` 发 queue/create，mock 档进本地状态机。
- 批量直发：`createTasksForBatch(store, batch, orders, route)`（platform.js）—— 一车多单每单一个平台任务，同一批次共用设备/货仓。
- 取餐超时返程重建：`recreatePickupTask(store, batch, order)` —— 为未取餐订单重建同卸载点位的 queue/create 任务（**不把订单改回 status=2**，保持已送达 3，避免被「卡死配送中」扫描误伤）。

任务行关键列：`order_id / batch_id / platform_task_id / device_sn / task_status / status_text`。创建成功回写 `platform_task_id`；失败经 `updateTask` 写错误文案。

### 2.2 任务状态枚举（task_status，与 doc/06 常量字典一致）

`platform.js:STATUS_TEXT`（以下以代码注释为准）：

| 状态 | 含义 | 状态 | 含义 |
|---|---|---|---|
| 0 | 排队中 | 10 | 任务已接收 |
| 20 | 去往上货点 | 30 | 到达上货点 |
| 40 | 上货中 | 50 | 已上货 |
| 60 | 去往取货点 | 70 | 到达取货点 |
| 80 | 任务完成 | 90 | 上货失败 |
| 91 | 去位置点失败 | 92 | 等待上货超时 |
| 93 | 等待上货关舱 | 94 | 去上货途中设备故障 |
| 95 | 去位置点超时 | 100 | 取货失败 |
| 101 | 去位置点失败 | 102 | 等待取货超时 |
| 103 | 机器返回失败 | 104 | 去送货途中设备故障 |
| 105 | 去位置点超时 | 106 | 召唤打断配送任务 |
| 110 | 任务取消 | 120 | 上货流程挂起 |
| 130 | 下货流程挂起 | 131 | 送货挂起，返回上货点 |
| 132 | 送货挂起，返回待命 | 140 | 待完善 |
| 150 | 任务被关闭 | — | — |

终态判定（代码常量）：任务终态 `TASK_TERMINAL = [110, 150]`；80 完成视同不再流转（轮询跳过）。订单联动规则见 2.5。

### 2.3 状态轮询兜底（syncTaskStatus / POLL_MS）

- 函数：`platform.js:syncTaskStatus(store, taskId)`，真实档专用（`MOCK || !platformReady()` 直接返回）。
- 接口：`GET /open-api/v1/deliveryTask/basicList?idList=<platform_task_id>`；返回 `data` 数组即任务本体（无 task 包装），按 `id` 或 `outOrderNo` 匹配，同步 `taskStatus` 并补记 `device_sn`。
- 跳过条件：仅跳过真正终态（80 / 110 / 150）与本地已作废（`void_at`）。**70 到达取货点必须继续轮询**——若平台到达回调丢失，轮询是唯一能把订单推进到「已送达(3)」的兜底；90~109（上货/取货失败）与 120~140（挂起）同样在轮询范围，驱动「配送异常(6)」或人工恢复（P1-4 修复，原 `task_status<80` 写法会把它们全挡在轮询外）。
- 周期：`POLL_MS`（默认 8s，`PLATFORM_POLL_MS` 覆盖），仅 `realPlatform` 时启动（timers.js ①）。

### 2.4 平台回调（feedbackDeliveryTaskUrl 等）

回调地址在创建任务时注册（`platform.js:callbackUrl`）：`CALLBACK_BASE + 路径 + ?token=<令牌>`。令牌走 **query 参数**而非路径段——平台侧示例回调 URL 自带 `&version+3d24d260000` 后缀，拼在 `?token=X` 之后仍可解析，拼路径段会 404。回调路径（`CALLBACK_PATHS`）：

| 用途 | 回调路径 | 处理函数（delivery/service.js） |
|---|---|---|
| 任务状态变更 | `/api/platform/callback/delivery`（备用 `/api/platform/cb/:token/delivery`） | `handleDeliveryCallback` |
| 设备端查业务订单状态 | `/api/platform/check-order`（备用 `/api/platform/cb/:token/check-order`，GET/POST 均挂） | `handleCheckOrder` |
| 设备异常上报（T 任务/R 机器/I IOT/N 导航） | `/api/platform/callback/exception` | `handleExceptionCallback` |

- **防伪**：`callbackAuthorized` 用 sha256 定长摘要 + `timingSafeEqual` 校验 `?token=`；`PLATFORM_SECRET` 为空且未显式配 `PLATFORM_CALLBACK_TOKEN` 时无法派生令牌 → 放行（本地演示；启动日志已告警）。
- **handleDeliveryCallback**：兼容直接字段 / `task` 包装 / `data` 包装三种报文形态，取 `taskId` 与 `taskStatus`，按平台任务 ID 反查本地任务后调 `applyStatus` 写状态，并同步 `device_sn`。
- **handleCheckOrder**：订单 status=5（已取消）/ 7（已退款）或 `cancelled_at` 有值 → 返回 `keyEvent: { eventName:'forceCloseTask', taskSubStatus:201, eventDesc:'订单已退款'|'订单已取消' }` 让设备强制关任务（taskSubStatus 仅 201/202 两种，用 eventDesc 区分原因）；订单正常返回 `data:null`。注意原先只判 5，已退款订单平台永远收不到 forceCloseTask，机器人照送不误——必须同时判 7。

### 2.5 状态写入唯一咽喉 applyStatus 与终态守卫

`platform.js:applyStatus` 是任务状态写入的唯一入口，三条通道全部经过：平台回调（handleDeliveryCallback）、basicList 轮询（syncTaskStatus）、本地模拟（mockAdvance），因此终态守卫只需在此实现一处：

- **终态守卫**：本地已作废（`void_at` 或任务 110/150）或订单已取消/退款（`cancelled_at` 或订单 5/7）时，**丢弃一切迟到的平台状态**——仅接受平台对「任务被关闭(150)」的确认（`forceCloseTask` 生效回执），且只更新任务自身，绝不联动订单/库存/批次（副作用在取消时已执行过一次）。少了这道守卫，取消订单后 mockAdvance 推来的 70 会把已取消订单改回已送达并结算销量、锁死库存回补。
- **110/150 落账**：任务置取消/关闭并写 `void_at`（一次写完），随后走 `orderCancel.cancelLocal`（finalStatus=5）完整落账（幂等）。
- **订单联动**：
  - 70 到达取货点 → 订单 3 已送达（写 `delivered_at` + `goodsStats.settleSales` 结算销量）；
  - 80 任务完成 ≠ 用户已取走（平台 40s 自动关舱同样流转 80）→ 仅当 `picked_up_at` 已置位才视为取走；否则保持已送达(3)，交取餐超时扫描处理；
  - `90 ≤ st < 110`（上货/取货失败）→ 订单 6 配送异常；
  - 迁移前经 `canMoveOrderStatus` 校验：禁止从终态迁出、禁止正常链路倒退；6 配送异常是旁路状态（1/2/3 可进，重试回 2）。
- 批次联动：任务状态变化后调 `batch.js:onTaskStatus`（80 且已取走 → `markOrderPicked` 计数；110/150 → 从批次摘除计数）。
- 平台取消/关闭会写 `recall_status` 相关字段的路径在 orderCancel 域，本文不展开。

## 3. 召唤模式（SUMMON_DELIVERY=true）

模式说明：弃用越凡配送任务接口，只用「召唤(lightTask) 移动 + drawerCtrl 开关舱门」两个原语逐点推进（背景见交接文档 9）。此模式**不创建任何配送任务**，一车多单靠后端编排逐站召唤。

### 3.1 召唤轻任务

| 函数（platform.js） | 目标 | 说明 |
|---|---|---|
| `summonToLoadingPoint(store, preferredSn, optExpireMin)` | 上货点 | 组单中批次待上货时提前把车叫到商铺；`preferredSn` 为已定型批次指派的车（扫描 status IN (0,1) 批次时传入） |
| `summonToPoint(store, deviceSn, landmarkId, optExpireMin)` | 任意点位（含地图 chargePoint 充电点） | 管理员手动召唤 / 配送停靠站复用 |
| `summonDeliveryToStop(store, batch, stop)` | route 停靠点 | 内部复用 summonToPoint，`stop.landmark_id` 是本地 landmarks 主键，需反查 `platform_landmark_id` 传入；窗口取 `SUMMON_STOP_EXPIRE_MIN`（默认 20 分钟） |

选车优先级：指定 `deviceSn`/`preferredSn` → 在线且 `machine_status ∈ {idle, standby, charging, returnChargingPile, returnStandby, lightTask}` → 任意在线车。

【mock】两个召唤函数直接返回 `{ ok:true, light_task_id:'mock-light-'+Date.now() }`，不真正调平台（保证「真到站」链路可测）。

### 3.2 expireTime 窗口与 wait 动作（真机实测约束）

`POST /open-api/v1/lightTask` 请求体关键约束（2026-09-16 真机受控对比实测）：

- `expireTime` 必须是 `yyyy-MM-dd HH:mm:ss` 日期时间字符串（`formatLocalDt`）；**传毫秒时间戳字符串会被平台拒绝**「expireTime字段类型错误」；
- `action` 必须带 `type:'wait'`，缺 type 平台报「请求发生异常」；
- `extInfo` 必须显式给出（空对象即可），缺它同样报「请求发生异常」；
- `waitTime`（秒）必须与 `expireTime` 匹配：expire 是 20 分钟而 waitTime 固定 300 秒时，车到达后只等 5 分钟任务就结束返程（issue2「等一会儿就回充电」）——统一按 `optExpireMin` 走；
- 窗口默认 5 分钟：lightTask 无取消接口，创建后只能等它到期；窗口太长（10 分钟）会在「开始配送」后挡住配送任务启动最多 10 分钟（2026-09-17 实测）。释放场景传 3 分钟（`settleRobotAtLoading`），配送停靠站传 `SUMMON_STOP_EXPIRE_MIN`（默认 20 分钟）。

### 3.3 真到站门禁（queryLightTask status=30 arrivedPoint）

- 接口：`GET /open-api/v1/lightTask/{id}?principalId=...`，函数 `platform.js:queryLightTask(id)`。
- 轻任务状态枚举：0 unconfirmed（排队未下发）/ 10 accepted（已接受）/ 20 goingtoPoint（前往中）/ **30 arrivedPoint（到达目标点）** / 40 finished（完成）/ 50 failed（失败）/ 60 closed（被删除）；`arrived = (status === 30)`。
- 设计原则：到达判断以**机器人真实到达信号(30)**为准，不再用 `getDevicePosition` 测距估判。
- 【mock】`queryLightTask` 恒返回 `{ ok:true, status:30, arrived:true }`——召唤后立即视为已到。
- 配套：`lightTaskArrived(store, batch)` 按批次 `light_task_id` 查询；`taskId` 为空/查询失败按未到处理（由 route 决定是否重新召唤，绝不误判为已到）。

### 3.4 开舱门禁 ensureLoadingArrival

`delivery/service.js:ensureLoadingArrival(store, deps, b)`——「到达上货点后才可开舱」门禁（召唤模式 open-bin 用）：

- 已存在未终结召唤任务（status ∈ {0,10,20} 前往/等待中）→ 返回 `waiting:true, keep:true`，**绝不重复召唤**（重复召唤会新建 lightTask、重置导航进度，导致永远等不到 30）；
- status ∈ {40,50,60} 已终态 → 落下去重新召唤；
- 查询失败 → 保守重新召唤一次（幂等 lightTask）；
- 新召唤成功 → 回写批次 `light_task_id`（`q.setBatchLightTask`）。

商家 open-bin（routes.js）：召唤模式下先过 `isRobotBusy` 忙碌兜底（问题4：不打断正在投递的车）→ `ensureLoadingArrival` → 未到返回 200 `{waiting:true, lighttask_status}` 让前端给等待提示 → 已到才 `drawerCtrl(1)` 开舱并 `setBatchLoading`。

### 3.5 逐站推进（startSummonDelivery / advanceSummonDelivery / ensureStopArrival）

- **startSummonDelivery(store, deps, batchId)**（「立即配送」入口）：
  - 幂等：`delivery_mode==='summon' && status===2 && current_stop>=1` 直接返回详情（不重复召唤/重标）；
  - 路线：取批次已有 `route`，为空则 `batch.planRoute` 规划并落库；
  - **先召唤首站成功，再置「配送中」+ current_stop=1**；首站召唤失败直接抛错，批次保持待上货/组单，不留「已配送中但首站没召唤」的半启动状态；
  - 首站订单「待取货」不在此置位，由真到站后补（见下）。
- **ensureStopArrival(store, deps, b)**：查询当前在途站 `route[current_stop-1]` 的召唤任务，`lightTask status=30` 真到达 → `markStopDelivered` 把该站订单 2→3 置「待取货」（`arriveOrder`，幂等）。修复了「机器人才被召唤去下一站、尚未开到时，订单被虚标为待取货」的问题。
- **advanceSummonDelivery(store, deps, batchId)**（推进器）：
  1. 仅 `status ∈ {2,3}` 推进（3 已完成可能是最后一单刚标记，仍需走完成收尾）；
  2. `ensureStopArrival` 真到站标记；
  3. 检查当前站订单是否全部取走（该站 `order_ids` 中无 status ∈ {2,3} 的订单）——未取完继续等；
  4. 取完 → 防重 Set `summonAdvancing` → 延迟 `SUMMON_STOP_ADVANCE_MS`（默认 5s）→ 校验 `current_stop` 未被其它路径推进（放弃本次）：
     - 还有下一站：`summonDeliveryToStop` 召唤过去并 `current_stop+1`；
     - 全部送完：`setBatchCompleted` + `settleRobotAtLoading` 召回上货点 + `current_stop` 归零。
  - 触发源：每次取餐（`batch.js:countPicked → notifySummonAdvance` 钩子，经 `registerSummonAdvance` 注册）+ 看门狗每 `SUMMON_WATCHDOG_MS` 兜底。

### 3.6 推进看门狗与半启动自愈（timers.js ⑤）

每 `SUMMON_WATCHDOG_MS`（默认 5s，`SUMMON_WATCHDOG_MS` 覆盖）执行三件事（仅 `summonDelivery` 时启动）：

1. **上货点守候**（见 7.3 keepAt）；
2. **正常推进**：扫描 `delivery_mode='summon' && status=2` 的批次逐一 `advanceSummonDelivery`——即使取餐事件钩子丢了、或服务重启，也能保证「送完本栋 → 必然推进下一栋 / 召回完成」；
3. **半启动自愈**：扫描 `status=2 && current_stop=0` 的批次（上次召唤首站失败抛错、或崩溃于「召唤成功但 future_stop 未落库」，用户端订单卡死在配送中）→ 重跑 `startSummonDelivery` 补召唤+补标；节流 `SUMMON_START_HEAL_MS`（默认 25s，`healAt` Map 记录），避免连续失败刷爆机器人/平台。

### 3.7 上货点守候与释放返程

- **守候 keepAt**（timers.js）：存在「组单中/待上货」批次（`status IN (0,1) && total_orders>0 && device_sn!=''`）且该车不在召唤配送时，保持它的上货点召唤任务：查询现 `light_task_id`，任务已终态（40/50/60）或距上次续约超过 `SUMMON_LOADING_KEEP_MS`（默认 4 分钟，在 5 分钟窗口到期前续一次）→ 重新 `summonToLoadingPoint`；重试节流 `keepTryAt` 至少 30s。车物理一直停在上货点，不会到期返程。
- **释放返程 settleRobotAtLoading(store, deps, deviceSn)**（delivery/service.js）：事件驱动（批次送完 / 取消订单 / 其他车要回去触发），不轮询：
  - 该车正做召唤配送（`delivery_mode='summon' && status=2`）→ 不打断，直接返回；
  - 有其他待上货订单（`status IN (0,1) && total_orders>0`）→ 召唤回上货点，正常窗口待命装货；
  - 无其他待上货订单 → 召唤回上货点等 `SUMMON_RELEASE_WAIT_MIN`（默认 3 分钟）；到点任务到期 = 自动释放返程充电。

## 4. 直发模式（SUMMON_DELIVERY=false）

### 4.1 每单创建平台任务

`doDispatchBatch`（delivery/service.js）真实档流程：选车（`pickAvailableRobot`：在线且空闲/待机/充电/返程/召唤中）→ `isRobotBusy` 门禁 → `claimDispatch` 抢占 → 调 `createTasksForBatch(store, b, orders, [])` 每单创建一个平台任务（Route B 直发）。召唤模式则不创建任何配送任务，仅定型设备，路线与逐点召唤在「立即配送」时进行。

### 4.2 Route B syncLoading=0 直发

`platform.js:createDirectTask`（2026-09-17 定型方案）：

- 接口 `POST /open-api/v1/deviceCtrl/create/direct`，`syncLoading: 0`（异步上货）：任务定型即创建直接任务，**车自行导航到上货点**（任务状态 10/20 → 30 到达上货点），不再用 `create/pre` 预创建（避免在错误位置开舱）；
- 开舱门禁以**任务状态 30 为准**（平台权威「到达」信号），不用带标定误差的距离判断；
- 请求体要点：`stockPos:'pos_1'`（货舱位置）、`priority`（按停靠顺序递减，第一站最高）、`outOrderNo:[order_no]`、`loadingStrategy/unloadingStrategy`（见 5.5）、`feedbackDeliveryTaskUrl`、`checkBizOrderStatusUrl`、`extInfo:{businessType:'takeaway', batchNo, stop}`；
- 创建成功回写 `platform_task_id`，状态置 0「待到达上货点」。

### 4.3 到达门禁 robotAtLoadingPoint

`platform.js:robotAtLoadingPoint(store, deviceSn)`（需求 3：开舱前必须确认车在上货点）：

- 【mock】恒 `{ ok:true, at_loading_point:true, distance_m:0 }`；
- 机器状态预检：`machine_status ∈ {charging, returnChargingPile, returnStandby}` → 明确提示等待（充电桩旁误判就位防护）；
- 判据（2026-09-18 修复）：**该设备存在任一**未作废配送任务 `task_status ∈ {30,40}` 且 `platform_task_id != ''` 即视为已就位——不再取「最新一条」任务判定（同批次多单同机下某单创建失败会误把「正在前往上货点」当最新）；
- 未就位：取最新一条有效任务做等待提示（排除平台未下发的空任务）；查不到任务提示「请先上货定型」。

### 4.4 开舱/关舱/派发时序（batchCtrl 控制权）

商家端批量操作（routes.js `/merchant/device/batch/*`）：

1. **open-bin 开舱**：`robotAtLoadingPoint` 门禁 → `grantControl(deviceSn, 600)` 获取控制权（`deviceCtrl/authority/grant`，header `duration` 秒数）→ 控制权 ID 暂存内存 `s.batchCtrl`（Map，batchId → {ctrlId, deviceSn}）+ 持久化批次行 `ctrl_id`（重启不丢）→ `verifyBatchLoading`（逐任务 `loadingVerify`）→ 开舱（任务流转 40 上货中）→ `setBatchLoading`；
2. **close-bin 关舱**：`drawerCtrl(deviceSn, 0)` 关舱（不影响任务状态，货已装好）→ 落 `loaded_at` 持久化「已上货待配送」；
3. **dispatch 开始配送**：先 `planRoute` 规划路线写入 `batch.route`（失败不阻断）→ `confirmBatchLoading`（逐任务 `loadingConfirm`，任务流转 50 已上货、关舱并开始配送）→ `releaseControl`（`deviceCtrl/authority/release`，header `ctrl-id`；**释放失败不阻断配送**——控制权可能已超时，机器人会自行开始执行任务）→ 清 `batchCtrl` 与 `ctrl_id` → `setBatchDelivering`（批次 2 配送中）。

单任务扫码上货流程（/merchant/device/scan → open-bin → close-bin → dispatch）与之同构；真实档扫码按 `deviceSn` 精确匹配，且 **status=0 组单中批次扫码即自动派车**（`doDispatchBatch` 指车，P1-10）。

取餐侧：`unloadingVerify`（先 `deviceCtrl/verify/match`（autoOpen:true）再开舱——2026-09-17 真机实测直接调 unloading/verify 会报 DLV_CTRL_0011「机器人当前不在取货阶段」，两步缺一不可）、`unloadingConfirm` 关舱（40s 未调用平台自动关舱，不改变任务状态）。

`loadingVerify` 同理两步：先 `verify/match`（校验阶段）再 `loading/verify`（autoOpen:true 真正开舱动作）。

## 5. 一车多单

### 5.1 best-fit 分批（BATCH_MAX_ITEMS）

`batch.js:getOrCreateOpenBatch(store, itemCount)`——以**商品件数**计容量（一车最多 `BATCH_MAX_ITEMS` 件，默认 12；兼容旧常量 `BATCH_MAX_ORDERS`）：

- 取「能容纳本单件数且当前最满」的组单中（status=0）批次（`HAVING items + n <= BATCH_MAX_ITEMS ORDER BY items DESC`）；
- 无合适批次则新建（批次号 `BATCH_NO` = 日期+当日序号，`seqSvc` 原子取号）；
- 单件数 > 容量 → 任何批次都装不下，自动独占新建批次；
- 批次容量**一律实时计算**（P1-9）：`total_items` 是缓存列，best-fit 与自动派车判断都以实时 SUM 为准，避免 UI 口径与调度器分叉；
- 并入：`addOrderToBatch`（订单 1 待接单 → 2 配送中，挂批次并清 `batch_removed_at`）；摘除：`removeOrderFromBatch`（幂等，批次计数 MAX(0,..) 防负，组单中批次空则置 4 已取消）。

自动派车条件（BATCH_SCAN_MS 扫描）：容量满（`BATCH_MAX_ITEMS`）或自动接单模式且批次成立超过 `BATCH_WAIT_MS`（默认 90s）；手动「派车」始终可用。

### 5.2 单数加权路线规划 planRoute

`batch.js:planRoute(store, orders)`——从上货点出发的单数加权最近邻：

- 同一楼栋多单合并为一站；
- **有效距离 = 距离平方 ÷ (该站点订单数 ^ α)**，α = `ROUTE_COUNT_WEIGHT`（默认 0.5）；与纯最近邻的区别：同距离下、甚至稍远一点点，单数多的楼栋被优先安排，避免 1 单近楼栋抢在 5 单楼栋前拖长多单楼栋平均等待；α=0 退化为纯最近邻，负值被钳制为 0；
- 无坐标时退化：单数从多到少，同单数按点位 sort 顺序（仍单数优先）；
- 产物写入 `batch.route`：`[{stop, landmark_id, landmark_name, order_ids}]`。

### 5.3 批量建任务 createTasksForBatch

`platform.js:createTasksForBatch(store, batch, orders, route)`：

- 每单一个平台任务（`outOrderNo` 独立、取餐码独立），同批次所有任务共用同一设备/货仓；
- 路线在「开始配送（关舱后）」才规划，因此派车时 route 可为空；传入 route 时 `priority = max(1, 10-(stop-1))` 按停靠顺序递减提示平台排程（第一站最高），为空时全部固定 priority=10（仅提示，不影响目的地）；
- 防御：函数内重读最新批次行（派车流程会在中途写入 device_sn）；
- 【mock】每单进本地状态机（6s 一步推进）；【真实】每单调 `createDirectTask`（Route B syncLoading=0）。
- 失败回滚：`doDispatchBatch` 任一步失败 → `q.voidTasksByBatch`（任务作废 void_at）+ `q.revertDispatch`（批次回组单中、清 device_sn/route）。

### 5.4 批次开舱/关舱/派发

批次生命周期：0 组单中 → 1 待上货（派车定型后）→ 2 配送中（开始配送后）→ 3 已完成 / 4 异常（`batch.js:BATCH_STATUS`）。

| 动作 | 召唤模式（SUMMON_DELIVERY=true） | 直发模式（false） |
|---|---|---|
| open-bin | isRobotBusy → ensureLoadingArrival（真到站 30）→ drawerCtrl(1) | robotAtLoadingPoint → grantControl(600) → verifyBatchLoading |
| close-bin | drawerCtrl(0) + setBatchLoadedAt | 同左（控制权仍在手） |
| dispatch | startSummonDelivery（召唤首站 + current_stop=1） | planRoute → confirmBatchLoading → releaseControl → 批次 2 |
| 批次完成 | 全站取完 → 召回上货点 → 批次 3（advanceSummonDelivery） | maybeCompleteBatch（订单全取走或任务 ≥80） |

### 5.5 取餐码策略

- 每单独立取餐码 `pickup_code`（防拿错；平台按任务匹配取餐码开舱）；
- 任务创建时随策略下发：`loadingStrategy: {match:10, strategies:{anyCode: pickup_code}}`（上货开舱验证）、`unloadingStrategy: {match:10, strategies:{contact: 手机号, roomNum: pickup_code}}`（用户取餐开舱验证）；
- 用户侧校验：`/delivery/pickup-by-code`（本人订单 + 待取餐 + 取餐码匹配 + 车一致）、`/delivery/pickup-by-scan`（扫车码自动匹配本人订单，免输码，匹配不到回退输码）；
- 同点多单一起取：`/delivery/pickup-close-all` 一次关舱 = 确认该用户本批次本点位全部待取(3)订单取走（`fulfillOrder` 逐单结算+计数，召唤模式顺带 drawerCtrl(0)）；
- 开舱（pickup-open）：不再把订单标记为已取走（P1-2），限 `MAX_PICKUP_OPEN` 次（默认 3）、限 `PICKUP_REOPEN_WINDOW_MS`（默认 10 分钟）；「正在取餐」`picking_up_at` 置位期间取餐超时计时暂停。真正「已取走」收口在关舱（pickup-close → 置 4 + 结算 + 批次计数）。

### 5.6 派车并发抢占与回滚

P1-7：两个并发派车（自动派车扫描 + 商家手点）都会读到 status=0 并各自创建平台任务 → 同批货被下发两次、真机被调度两次。`doDispatchBatch` 在任何 await 之前先用**条件更新抢占**（`q.claimDispatch`：status 0→1），只有抢到的一方才继续，失败方直接报「该批次已派车，不能重复派车」。

### 7.1 设备列表（getDeviceList / machine_status）

`platform.js:getDeviceList()`：`GET /open-api/v1/deviceRuntime/runtimeStatusList?principalId=&curPage=1&size=50`。`onlineStatus`：1 在线 / 2 离线 / 3 故障。机态 `machine_status` 与文案（`MACHINE_TEXT`）：

| machine_status | 含义 | machine_status | 含义 |
|---|---|---|---|
| idle | 空状态 | init | 初始化 |
| setting | 设置 | charging | 正在充电 |
| returnChargingPile | 返回充电桩 | standby | 待机中 |
| returnStandby | 前往待机 | exception | 异常 |
| lightTask | 召唤（轻任务） | update | 升级 |
| interaction | 交互 | patrol / Patrol | 巡逻中 |
| delivery / Delivery | 配送中 | remoteDevOps | 远程运维 |
| Acceptance | 验收 | — | — |

### 7.2 忙碌判定（isRobotBusy）

`platform.js:isRobotBusy(store, deviceSn)`（派车门禁 / 商家上货可用性标注）：

1. 存在 `task_status BETWEEN 50 AND 79` 的未作废配送任务 → 忙（配送中/待取餐）；
2. 召唤多单配送：存在 `delivery_mode='summon' && status=2 && light_task_id` 活跃批次 → 忙——否则车停在取餐点等待时是 lightTask 态，会被下方机态判定为「空闲」，商家可强行上货打断正在投递的车（问题4）；
3. 设备离线 → 忙；
4. 机态 ∈ {Delivery, delivery, patrol, Patrol, exception, remoteDevOps, update, interaction} → 忙；**lightTask 不算忙**（车正被叫到上货点等待，正是要派它的时候，2026-09-16 真机实测）；
5. 设备列表查不到该车 → 保守拒绝；【mock】恒空闲。

### 7.3 上货点守候与释放返程（keepAt / settleRobotAtLoading）

见 3.7。补充：`keepAt`（device_sn → 最近成功召唤时间戳）与 `keepTryAt`（节流时间戳）均为 timers.js 模块级 Map，只随看门狗轮次维护，不落库（重启后靠查现有 light_task_id 恢复新鲜度判断）。

### 7.4 抽屉控制（drawerCtrl）

`platform.js:drawerCtrl(deviceSn, stockCmd)`：`POST /open-api/v1/deviceCtrl/drawerCtrl`，`stockPos:'pos_1'`，`stockCmd` 1 开 / 0 关，**不影响任务状态**——这是召唤模式成立的核心支点（机器人退化成「移动到点 + 开关舱门」两个原语，不依赖配送任务与货仓类型）。【mock】直接返回成功。召唤模式关舱为「尽力而为」：用户已取走餐，物理关舱报错不阻断取餐记录与推进（否则该单停在待取货(3) → 推进器永不触发 → 机器人回充电桩）。

### 7.5 位置与标定

- `getDevicePosition(store, taskId)`：`GET /open-api/v1/iotGatewayProxy/{sn}/buildingManager/om-api/EvizServer`（eviz）。返回 `data` 是「字符串包着 JSON」（内层序列化），必须先 `JSON.parse` 再取字段（2026-09-16 真机实测，否则恒 null、开舱门禁一直报「无法获取无人车位置」）；取 `robotpose`（激光 SLAM 网格坐标）经相似变换 `robotposeToMeters` 转平台局部米（`POS_CAL`：s=182.67、R=-55.37°、t=(-2144.6, 4649.8)，两组对应点求解自洽验证）；3s 缓存（posCache）。⚠️ 平台重新标定地图（点位 pose 变化）需用同法重新标定。
- `getDevicePositionBySn(store, deviceSn, hintText)`：按设备号直取位置（不依赖 delivery_tasks，召唤多单配送无配送任务；地图/到达门禁用）；另返回管理页坐标系 `ax/ay`（`robotposeToMetersForAdmin`）。
- **管理页自动标定**（`ADMIN_AUTO_CALIB` 默认开，`ADMIN_CALIB_RANGE_M` 默认 8m）：机器人**正常配送/召唤**每到已知点位（`robotAtPoint` 判定到达）自动记录「robotpose 原始网格, landmark 米」锚点对（`recordCalibPosePair`，与已存锚点米距 <4m 略过，最多 64 对）→ 攒到 ≥2 个相距 ≥8m 的锚点解相似变换（`solveCalibSimilarity`）→ 持久化 `backend/data/admin-calib.json`；管理页显示用它换地图帧，**全局 POS_CAL / 配送到达判定完全不碰**（只读观测）。
- `getRobotRadar(store, deviceSn)`：同 eviz 代理取 `laserscan`（极坐标 ranges 或直角点数组，原样透传）+ `costmap`（base64），3s 缓存。
- `robotAtPoint(store, deviceSn, landmarkId, landmark)`：召唤模式点位到达门禁（无配送任务可依赖任务状态）——机器状态预检（充电/返程/回待机拒绝）→ `getDevicePosition` 测距到目标 landmark 坐标（≤ `ARRIVE_RADIUS_M`，默认 2.0m，乘 `POS_M_PER_UNIT` 标定系数）判已到；到达即采样自动标定；定位拿不到 → 保守拒绝。

### 7.6 地图与底图

- **点位同步** `syncLandmarks(store)`：`buildingList`（取首个 building）+ `landmarkInfo?type=deliverPoint` 拉平台真实点位，按 `platform_landmark_id` 幂等 upsert 进本地 `landmarks`（名称含「上货/商铺/店铺/铺子」判为 loadingPoint）；成功后清理无平台映射的历史演示点位。
- **监控地图** `getMapOverview(store)`：`building/mapInfo/{mapId}`（60s 缓存 mapInfoCache）→ map_url/barrier_url（OSS 签名直链）、bbox（`computeMapBbox`：点位+固定路径 graph 节点外包框）、`mapDetailInfo.landmarks`（含 chargePoint 充电点去重追加）、路网 graph、活跃批次路线（status=2 批次按 route 停靠点坐标）、机器人实时位置（按设备列表直取，兼容召唤多单无配送任务）；`admin_calib` 附带自动标定状态。
- **底图字节** `getMapImageBytes(store)`：building/mapInfo 返回的 map 是 OSS 签名直链，**签名约 14s 即过期**（实测取到手已过期 14 秒、直接下载 403）→ 后端每次下载前强制取新鲜签名（`fetchMapRawFresh`，失败回退 60s 缓存 URL），下载失败重新签名重试 3 次（`httpGetBuffer` 处理 302 重定向，10s 超时），字节缓存后前端只访问后端稳定地址（/api/dashboard/map-image）。【mock】返回失败（无平台底图）。
- 追踪页归一化：机器人坐标 ÷ 地图 bbox → 百分比（8% 内边距，routes.js /delivery/track）；mock 档位置无 x/y → percent 保持 null，前端回退纯文本展示。
