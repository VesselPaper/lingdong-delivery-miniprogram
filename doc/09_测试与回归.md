## 1. 测试总览

### 1.1 为什么用独立脚本

回归测试采用「临时库 + 临时端口 + 独立 server 进程」的完全隔离方案，而不是在开发库上直接跑接口：

- **临时数据库**：脚本在 `os.tmpdir()` 下用「前缀 + 时间戳」新建 SQLite 库（`LINGDONG_DB` 指向临时文件），与 `backend/data/lingdong.db` 的真实数据完全隔离。脚本结束后自动删除临时库文件（含 `-wal` / `-shm`），不残留任何测试数据。
- **临时端口**：`test_batch_flow.js` 用 3100（主链路）+ 3101（取餐超时子用例）、`test_summon_flow.js` 用 3102，不与开发默认端口 3000 冲突，也不影响正在运行的开发/演示服务。
- **独立 server 进程**：脚本用 `spawn` 拉起一个全新的 `server.js` 子进程（`cwd` 为 `backend/`，`stdio: pipe` 收集日志用于排障），通过轮询 `GET /api/shop/status` 确认就绪（15 秒超时保护），跑完在 `finally` 中 `kill`。进程退出码即回归结果：0 = 全部断言通过，1 = 存在失败。
- **不污染真实数据**：商家邀请码使用固定测试值 `test-invite`，微信凭据（`WX_APPID`/`WX_SECRET` 等）置空，支付与平台全部 Mock。测试产生的订单、批次、库存/销量变动全部落在临时库中。

### 1.2 两个脚本的定位（互补覆盖两种配送模式）

| 脚本 | 环境开关 | 覆盖的配送模式 | 关键差异点 |
|---|---|---|---|
| `test_batch_flow.js` | `SUMMON_DELIVERY=false` | **直送链路**：批次派车即为每单创建开放物流平台配送任务（task），机器人按路线逐点位送达，用户凭本单取餐码取走 | 断言「每单已创建配送任务」（L116）、「每单独立取餐码且互不相同」（L114） |
| `test_summon_flow.js` | `SUMMON_DELIVERY=true` | **召唤链路**：批次定型时不创建平台任务；立即配送时规划路线并召唤机器人到站，由真到站门禁 + 推进看门狗把订单置待取货 | 断言「召唤模式不创建配送任务，orders[].task 为空」（L121）；逐站推进依赖 `SUMMON_STOP_ADVANCE_MS` 步进 |

两者复用同一套登录 / 下单 / 支付 / 组单 / 开关舱 / 取餐接口，分别验证后端两种配送执行引擎（直送 vs 召唤）都能走完整闭环，且共享的状态机、批次、库存、结算逻辑在两条链路上行为一致。

### 1.3 脚本运行机制（两脚本同构）

1. `startServer()`：spawn server 子进程 → 轮询 `/api/shop/status` 直到 200（每 300ms 一次，15 秒超时）。
2. `api(method, pathname, body, token)`：封装 fetch，自动带 `Content-Type: application/json` 与可选的 `Authorization: Bearer <token>`，响应 JSON 解析失败兜底为空对象。
3. `assert(cond, msg)`：条件不成立抛 `ASSERT FAIL: <msg>`，成立则打印 `  ✔ <msg>` —— 覆盖链路清单中的每一条即对应一次 `assert`。
4. 顶层 `try/catch/finally`：失败置 `fail=true` 并打印 `❌ <message>`；`finally` 中 kill 子进程、删除临时库，最后 `process.exit(fail ? 1 : 0)`。

## 2. 用法与前置

### 2.1 环境要求与命令

- **环境要求**：Node.js 22+（内置 `node:sqlite`，Node 22.5+ 可用；本地已验证 v22）。执行 `npm install` 后即可运行，无额外依赖。
- **命令**（在 `backend/` 目录下执行）：

```bash
node test_batch_flow.js     # 直送链路回归：端口 3100（主）+ 3101（取餐超时子用例）
node test_summon_flow.js    # 召唤链路回归 + 路线规划单测：端口 3102
```

- **端口前置**：3100 / 3101 / 3102 需空闲；被占用时脚本在 15 秒等待后报 `server start timeout` 并退出码 1。
- **运行时长预期**：
  - `test_batch_flow.js`：约 20~40 秒。主要开销在取餐超时子用例：需要再启动一个 server（端口 3101），并包含多处 `waitMs(4200)`（超过 1500ms 超时窗口 + 秒级精度余量）。
  - `test_summon_flow.js`：约 15~40 秒。包含首站待取货轮询（最多 24×500ms）、逐站推进等待（每站停 `SUMMON_STOP_ADVANCE_MS=1200ms`）与完成收尾轮询（最多 40×400ms）。
- **输出格式**：
  - 每步断言通过打印一行 `  ✔ 断言说明`；
  - 断言失败抛 `ASSERT FAIL: 说明`，随后打印 `❌ <失败原因>`；
  - 结尾打印 `✅ 全部冒烟测试通过（…）`；
  - 进程退出码 0 = 通过，1 = 失败（Node 的 `node:sqlite ExperimentalWarning` 输出无害，不影响结果）。

## 5. 基线自适应说明

### 5.1 库存/销量断言为何从写死数值改为相对基线

- `test_batch_flow.js` 第 70~73 行先读取当前商品#1 的库存与销量作为基线：`stock0 = Number(g0.stock)`、`sales0 = Number(g0.sales)`。此后所有断言均为**相对差值**：下单扣库存 `stock0-4`、下单不结算销量 `sales0`、收货结算 `sales0+4`、异常退款回补 `stock0-5`。
- 原因：种子库导入**真实商品后商品#1 的库存/销量已不再固定**（早期版本写死 100/326；第 198 行注释「sales 326+4=330」仅为说明性残留，实际断言用的是 `sales0+4`）。若继续写死数值，真实库数值变化后回归会误报失败；改为基线后，脚本对「真实商品导入后的当前值」自适应，也允许不同环境（演示/试点）使用不同种子数据。
- 同类处理：商品分类断言（L90）只校验「包含『即食卤味』这一真实分类」而不校验完整列表；标记售空用例用商品5（L93），避免依赖商品1 的库存语义。

### 5.2 首站待取货为何轮询等待而不是立即断言

- 召唤模式下，批次「立即配送」返回时**首站订单尚未置为待取货**：置位由「真到站门禁 + 推进看门狗（默认 5s）」异步完成（`test_summon_flow.js` L144 注释）。
- 因此脚本用轮询替代立即断言：循环读取批次详情，最多 24 次、每次间隔 500ms，直到「首站订单 ≥2 且全部 `status===3`」才判定通过（L145~157）。等待期间看门狗完成置位，属预期时序而非竞态——若改成立即断言，在真实门禁回调前必然误报。
- 同类等待：批次完成收尾同样异步——当前站取完 → 停 `SUMMON_STOP_ADVANCE_MS` 步进 → 下一站 → 全部取完 → 召回。脚本以「status=3 且 current_stop=0」为完成条件轮询（最多 40×400ms，L183~191）。

## 6. 管理员账号体系验证

```bash
cd backend

# ① CLI 建号：密码至少 8 位；--gen 自动生成 16 位强密码（只打印一次，注意保存）
node tools/admin_user.js add --username admin --gen
# 其他子命令：list / disable --username x / enable --username x / reset --username x --gen

# ② 启动后端（管理员鉴权与 Mock 无关，普通启动即可）

```

### 6.2 接口验证步骤（curl 示例）

```bash
# ① 登录 → 返回 { code:0, data:{ token, admin } }

  -H "Content-Type: application/json" \
  -d '{"username":"admin","password":"<密码>"}'

# ③ 错密限流：连续 5 次错误密码（同一「账号+IP」键）后，再登录返回 HTTP 429
#    「尝试次数过多，请 10 分钟后再试」（ADMIN_LOGIN_MAX 默认 5，窗口默认 10 分钟）
curl -X POST http://127.0.0.1:3000/api/admin/login \
  -H "Content-Type: application/json" \
  -d '{"username":"admin","password":"wrong-password"}'

# ④ 登出：吊销当前 session
curl -X POST http://127.0.0.1:3000/api/admin/logout \
  -H "x-admin-token: <token>"

# ⑤ 登出后用旧 token 请求 /me → HTTP 401「未登录或登录已过期」
curl http://127.0.0.1:3000/api/admin/me \
  -H "x-admin-token: <旧token>"
```

| 步骤 | 接口 | 预期 |
|---|---|---|
| 建号 | `node tools/admin_user.js add --username admin --gen` | 打印账号 id；`--gen` 时打印一次性初始密码（routes 侧 L86~103 对应登录落库） |
| 登录 | `POST /api/admin/login` | code=0 + token + admin（routes.js L86~103） |
| 会话校验 | `GET /api/admin/me`（x-admin-token） | 返回当前登录管理员（L106） |
| 错密限流 | 连续 `POST /api/admin/login` 错密 | 第 6 次起 HTTP 429「尝试次数过多，请 10 分钟后再试」（L12~16、L89~91） |
| 登出 | `POST /api/admin/logout`（x-admin-token） | 吊销当前 session，返回成功（L109~113） |
| 登出后 | `GET /api/admin/me`（旧 token） | HTTP 401「未登录或登录已过期」（_shared.js L76~85） |

补充（tools/admin_user.js L58~73）：`disable` 会同时吊销该账号全部已登录 session；`reset` 改密后同样要求重新登录。前端登录表单的错误密码同样计入同一限流键，验证限流时请与真实账号、真实档环境隔离（限流计数在内存，重启即清零）。

## 7. 手动回归清单

> 以下冒烟项提炼自「理思路文件夹/06_回归与验证清单.md」与 README，标注为真实操作步骤。
> 人工回归前置：后端运行 `node server.js`（pilot 档 + 真实平台，或 demo + Mock 均可）；机器人上线（如 `R110A2603AUEQC00` 在线，平台设备列表确认）；双端 `config.js` 指向后端地址（换网络必改）。

### 7.1 用户端（学生小程序）

1. 微信一键登录成功 → 首页/商品/购物车/地址可用。
2. 下单：选送达点位 + 收餐人 + 手机号 → 模拟支付 → 订单进入「待接单」。
3. 超过 12 件商品自动拆单 → 显示多个订单。
4. 订单列表/详情/红点正确（进行中订单在「我的」页常驻红点，全部处理完才消失）。
5. 免费取消窗口内（默认 10 分钟）取消 → 订单状态=已取消(5)；超窗口提交「取消申请」。
6. 售后：对已送达/已完成/配送异常订单发起退款/投诉申请。

### 7.2 商家端（商家小程序）

1. 登录 → 工作台首页统计正确。
2. 接单（手动 + 自动接单两种）→ 订单并入「组单中」批次。
3. 批次列表 → 派车定型（直送模式创建配送任务）。
4. 扫码/选择批次 → 批次上货详情页 → 机器人就位显示。
5. 打开舱门（任务 30/40 门禁）→ 放货 → 关舱 → 立即配送。
6. 配送监控/地图：机器人位置、活跃路线、按批次分组展示（真实地图需 `TIANDITU_TK`；Mock 下看占位）。
7. 配送异常处理：重新配送 / 取消并退款。
8. 售后处理：同意退款（可改金额）/ 拒绝（需理由）/ 回复投诉；取消申请处理。
9. 商品/活动/店铺设置（营业、自动接单、分类选择器、标记售罄）。

### 7.3 用户取餐（可并入用户端冒烟）

1. 机器人送达（订单「已送达」）→ 用户扫码/输取餐码取餐页。
2. 打开舱门 → 取餐 → 关舱 → 订单「已完成」+ 商品销量结算；同车多单展示「本车共 N 单 · 已取 X 单」。
3. 40s 自动关舱 → 重新开舱（限次 3 次、限时 10 分钟）。
4. 取餐超时：15 分钟未取 → 一段超时 → 返程再等 → 二段驳回退款。

### 7.4 管理员网页（`/admin/`）

1. 账号密码登录（无共享令牌）→ 状态总览：机器人/平台任务/批次/订单/任务/告警正确。
2. 雷达图：机器人在线时有点云；离线时占位。
3. 任务取消/关闭/作废、删除订单、清理批次（含批量操作）。
4. 设置页：召唤/开舱/关舱/控制权获取与释放/点位同步。
5. 一键初始化：全部回到干净态（批次置 4、无活跃订单、无平台任务）。

### 7.5 可视化大屏（`/dashboard/`，免登录）

1. 5 秒轮询：统计/地图/车辆/批次/取餐超时告警正常。
2. 根路径 `/` 自动跳转管理员网页；`/dashboard/?demo=1` 演示模式可用。
3. 后端离线时一键脚本给出排查提示而非白屏；路径末尾必须带斜杠（`/admin/`、`/dashboard/`）。

### 7.6 双端闭环演示（README §2.5 提炼）

用户端下单支付 → 商家端订单出现「待接单」→ 接单（并入批次）→ 商家上货派车 → 用户端配送追踪可见机器人推进（Mock 模式每几秒自动前进）→ 到达后扫码/输取餐码取餐 → 关舱 → 订单完成、批次完成。

## 8. 注意事项

- **只在 demo + Mock 下跑**：两个回归脚本均以 `RUN_MODE=demo`、`PLATFORM_MOCK=true`、`PAY_MOCK=true` 启动 server（test_batch_flow.js L17、L260~262；test_summon_flow.js L20~24），微信登录、微信支付、开放物流平台全部走本地模拟，不产生真实平台调用与真实资金流水。
- **真实档不适用项**（脚本里的测试捷径在真实环境不存在，勿在 pilot/真实档照搬）：用户端演示档「模拟扫码」入口（仅 demo 登录时显示；**商家端扫码已是真实 `wx.scanCode`**）、`test-complete` 测试完成配送、`mock-dispatch` 模拟开始配送、`DEVICE_MOCK` 模拟 ~10 秒到达、取餐超时用例的 1500ms 极小窗口、用 SQL 直改订单状态构造配送异常。真实档只能等平台回调推进状态。
- **测试后自动清理**：脚本在 `finally` 中 kill 子进程并删除临时库文件（含 `-wal`/`-shm`），断言失败也会执行（test_batch_flow.js L349~355、L361~365；test_summon_flow.js L197~201），无需人工清理，可反复执行。
- **端口占用**：3100/3101/3102 被占用会启动超时报错；同时只跑一个脚本或确认端口空闲。
- **改代码后先清理再回归**（06 文档铁律）：每次对配送流程做代码修改后，先取消活跃订单 + 关闭平台任务 + 批次置已取消，再跑回归或让用户重新下单测试，避免旧数据干扰状态机。
- **管理员限流是内存态**：按「账号 + IP」计数，重启即清零；不要在真实档用真实账号反复试错，否则锁定 10 分钟。
- **Node 版本**：必须 22+（`node:sqlite` 内置）；`ExperimentalWarning` 输出属正常噪声，不影响结果。
- **回归与改造节奏**（06 文档 §1）：分层改造期间，每完成一步先跑对应冒烟（登录+商品+购物车+地址 → 下单拆单+支付+取消+退款 → 全量 test_batch_flow + 取餐超时 → 管理员 state/radar/reset），全部通过才进入下一步；提交前向用户确认，禁 `--force`。
