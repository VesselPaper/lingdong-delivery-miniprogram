# 07 · 前后端链路文档

最后更新：2026-09-04
说明：记录小程序用户端与商家端每个关键操作的前后端完整链路（点击按钮 → API 请求 → 后端处理 → 数据库变化 → 前端渲染）。接口细节见 doc/02_接口文档.md。

## 基础说明

后端地址：http://127.0.0.1:3000
配置：backend/.env（复制 .env.example 填写），微信登录/支付/开放物流平台凭据均从环境变量读取。
前端请求封装：utils/request.js，统一携带 Authorization 头（Bearer token），返回结构 code=0 为成功。
鉴权：后端根据 token（openid）识别用户，商家接口校验 role=merchant。
订单状态：0 待支付、1 待接单、2 配送中、3 已送达、4 已完成、5 已取消、6 配送异常、7 已退款。
配送批次状态：0 组单中、1 待上货、2 配送中、3 已完成、4 异常。
数据库：backend/data/lingdong.db（SQLite，node:sqlite 内置驱动）。

## 链路 1：微信登录（用户端/商家端）

点击位置：用户端登录页「微信一键登录」或商家端登录页「微信一键登录」。
前端动作：调用 POST /api/auth/login，传 code、role（student/merchant）、nickname。
后端处理：测试阶段为演示登录——未配置 WX_APPID/WX_SECRET 时，以 code 的稳定哈希作为 openid，点击登录直接成功（便于预览）；正式环境启用真实 code2session（代码在 server.js 注释保留，配置 .env 后取消注释）。
数据库变化：users 表新增或更新一行（openid、nickname、role）。
前端渲染：返回 token 与 user 存入本地 storage；商家端登录后跳转工作台首页。

## 链路 2：首页加载商品

页面加载：首页 onShow。
前端动作：GET /api/goods/list。
后端处理：查询 goods 表 status=1 的商品，按销量排序。
数据库变化：无（只读）。
前端渲染：商品卡片流展示，月售、价格、加购按钮。

## 链路 3：加入购物车

点击位置：首页或商品列表的加号按钮。
前端动作：POST /api/cart/add，传 goods_id、quantity=1。
后端处理：查询 cart 表是否已有该用户该商品，有则加数量，无则插入。
数据库变化：cart 表新增或更新一行。
前端渲染：toast「已加入购物车」。
移除：商城/详情/购物车页数量减到 0（即数量为 1 时点「−」）调 DELETE /api/cart/remove 删除该行；商城/详情页随后从「− 1 +」步进器切回「+」加购按钮。

## 链路 4：购物车结算

点击位置：购物车页「结算」按钮。
前端动作：读取选中项，写入本地 storage checkout_items，跳转确认订单页。
后端处理：无。
数据库变化：无。
前端渲染：确认订单页展示商品清单与送达点位。

## 链路 4.1：收货地址（结算页关联）

页面：确认订单页收货地址卡（关联「我的-收货地址」）。
前端动作：加载 GET /api/address/list（同时加载 /api/landmarks 点位）；自动选中默认地址（无默认则取第一条，无地址则回填上次下单选项）；弹层选择地址或「新增收货地址」。
前端处理：选中地址后按 landmark_id 匹配点位自动回填送达点，并回填 contact_name / contact_phone（数值比较兜底，兼容历史 "2.0" 文本数据）。
后端处理：/api/address/save 将 landmark_id 显式转字符串存储（node:sqlite 会把整数绑定到 TEXT 列存成 "2.0"，导致与点位 id 无法匹配）；启动迁移自动修正历史 "2.0" 数据。
数据库变化：addresses 表增删改。
前端渲染：地址卡展示收餐人/电话/点位/详细地址；新增地址从地址管理页返回后自动刷新。

## 链路 5：提交订单（下单）

点击位置：确认订单页「提交订单」按钮。
前端校验：点位、姓名、手机号格式。
前端动作：POST /api/order/create，传 landmark_id、landmark_name、remark、items 数组。
后端处理：按 goods 表单价计算总额，生成 order_no 与 pickup_code，插入 orders 表（status=0 待支付），写入 order_items 明细，**同步扣减库存**（MAX(0,…)，售罄商品拒绝下单），清空购物车。
数据库变化：orders 新增一行、order_items 新增多行、goods 库存扣减、cart 清空。
前端渲染：跳转订单详情页并拉起支付。

> **库存/销量模型**（goodsStats 服务，见 链路 10/11）：下单只扣库存（防超卖）；**收货完成（订单到 3/4）时已售 +数量**（orders.goods_settled=1 幂等）；取消/退款且未售出时回补库存。

## 链路 6：支付订单（微信支付 V3）

点击位置：订单详情页「立即支付」或订单列表「去支付」。
前端动作：POST /api/order/pay，传 id。
后端处理：校验订单为待支付状态，调用微信支付 V3 统一下单（jsapiPay），返回小程序端拉起收银台所需参数。
前端渲染：wx.requestPayment 拉起微信收银台。
支付结果：微信服务器回调 POST /api/pay/notify，后端解密 resource 后将订单 status 0 → 1（待接单）；前端支付成功后轮询订单详情确认已收款（status>0）。

## 链路 7：支付订单（微信支付 V3 / 模拟支付 + 自动接单）

点击位置：订单详情页「立即支付」或订单列表「去支付」。
前端动作：POST /api/order/pay，传 id。
后端处理：
- 校验订单为待支付状态；
- `PAY_MOCK=true`（试点）：直接置已支付（status 0→1），随后调用 `maybeAutoAccept`：**店铺营业且 auto_accept=1 时自动接单**（订单 1→2 并入「组单中」配送批次），返回 auto_accept 标记；
- 真实支付：调用微信支付 V3 统一下单（jsapiPay），返回拉起收银台参数。
前端渲染：wx.requestPayment 拉起微信收银台。
支付结果：微信服务器回调 POST /api/pay/notify，后端解密后将订单 status 0→1，并同样触发自动接单判断；前端支付成功后轮询订单详情确认已收款（status>0）。

## 链路 7.1：商家接单（并入配送批次，一车多单）

点击位置：商家端订单列表「确认接单」或订单详情「接单并装车」。
前端动作：POST /api/merchant/order/confirm，传 id。
后端处理：校验商家身份、店铺营业状态（歇业则拒绝）、订单状态（须为 1 待接单），调用 `batch.addOrderToBatch`：订单并入当前「组单中」批次（无则新建，一车最多 12 单），**不立即创建平台任务**。
数据库变化：orders.status 1→2、orders.batch_id 写入、delivery_batches 新建/计数+1。
前端渲染：toast「已接单，并入批次 BD...」→ 弹窗「是否前往配单页」→ 是则跳转配单/上货页（免去「任务→商品→扫码配单」多步操作）。

## 链路 7.2：批次派车（路径规划 + 批量创建平台任务）

点击位置：配单/上货页「组单中批次 → 派车配送」；或自动派车调度（批次满 12 单 / 自动接单模式等待期满 90s）。
前端动作：POST /api/merchant/delivery/batch/dispatch，传 batch_id（可带 device_sn）。
后端处理（server.js doDispatchBatch）：
1. 校验批次为组单中且内有待配送订单；
2. `batch.planRoute`：按送达点位分组，从上货点做贪心最近邻排序（坐标来自 landmarks.pos_x/pos_y，无坐标退化为点位 sort 顺序），生成 route（停靠顺序，同点位多单合并）——近似最小化顾客总等待时间；
3. 指派机器人：指定 device_sn 或自动挑在线空闲机器人（platform.pickAvailableRobot），否则由平台队列分配；
4. `platform.createTasksForBatch`：为批次内每单创建独立 delivery_tasks 与平台任务——真实模式逐个调 queue/create（outOrderNo 独立、取餐码独立、指定同一 deviceSn、priority 按停靠顺序递减、extInfo 含 batchNo/stop）；Mock 模式本地状态机；
5. 批次状态 0→1 待上货，机器人前往上货点。
数据库变化：delivery_batches.route/device_sn/status 更新；每单 delivery_tasks 新增 + orders.delivery_task_id 绑定（status 保持 2）。
前端渲染：批次进入「待上货」列表，展示路线（route_text）与逐单取餐码，可扫码/选择上货。

## 链路 8：配送追踪

页面：用户端「配送」tab 或订单详情「查看配送位置」。
前端动作：GET /api/delivery/track?order_id=x，每 3 秒轮询。
后端处理：查询 orders 与 delivery_tasks，返回订单状态、任务状态、机器人位置（真实模式走 eviz 代理接口，Mock 模式返回模拟坐标）；附加同批次信息 batch（batch_no/total_orders/picked_orders/multi_order/device_sn）与 task_text（无任务时给出「商家已接单，正在组车配送/机器人前往上货点」等准确文案）。
数据库变化：无（只读）。
前端渲染：进度条（已接单/取餐/配送/送达四段）、机器人位置在地图移动、取餐码展示；一车多单时展示「本车共 N 单 · 已取 X 单」，提示用户凭本单取餐码取走自己那份。

## 链路 9：平台状态回调（真实模式）

触发：开放物流平台任务状态变更时回调 POST /api/platform/callback/delivery（feedbackDeliveryTaskUrl）。
后端处理：按 platform_task_id 找到 delivery_tasks，调用 platform.applyStatus 更新任务状态并联动订单状态：
任务 70 到达取餐点 → 订单 3 已送达（待取餐）
任务 80 完成 → 订单 4 已完成（并标记本单已取走，批次计数+1）
任务 110/150 取消/关闭 → 订单 5 已取消（并从批次计数移除）
任务 90/100 系列失败 → 订单 6 配送异常
**批次联动**（batch.onTaskStatus）：任务 80 → 该单 picked_up_at 记录 + 批次已取计数；批次内全部有效订单已取/完成 → 批次状态 3 已完成。
数据库变化：delivery_tasks.task_status、orders.status、orders.picked_up_at、delivery_batches 计数/状态更新。
兜底：后端每 PLATFORM_POLL_MS（默认 8s）轮询 deliveryTask/basicList（idList 查询）同步活动任务状态。
checkBizOrderStatusUrl：设备端在关键节点校验业务订单状态（POST /api/platform/check-order），订单正常返回 code=COMM_200、data=null；订单已取消/退款时返回 keyEvent（taskSubStatus 201）令设备强制关任务，见 doc/02 10.2。

## 链路 10：确认取餐（完成订单）

点击位置：配送追踪页「扫码取餐/输入取餐码」或订单详情同按钮。
前端动作：POST /api/delivery/confirm，传 order_id、scan_code（扫码或输入）。
后端处理：校验订单状态为 3 已送达；若传 scan_code 则与订单 pickup_code 比对，不匹配拒绝。
数据库变化：orders.status 3 → 4。
前端渲染：订单状态变为「已完成」。

## 链路 11：取消订单

点击位置：订单列表「取消」。
前端动作：确认弹窗后 POST /api/order/cancel，传 id。
后端处理：仅待支付（0）与待接单（1）可取消，置为已取消（5）。
数据库变化：orders.status → 5。
前端渲染：订单显示「已取消」。

## 链路 12：商家工作台统计

页面：商家端工作台（进入站点）。
前端动作：GET /api/merchant/stats。
后端处理：按天统计今日订单数、营业额（排除待支付与已取消）；主面板四态：待接单（订单 status=1）、待上货（批次 status=1）、配送中（批次 status=2）、待取货（订单 status=3）；次面板：异常（订单 status=6）、售后（待处理退款/投诉）、待处理取消申请。
数据库变化：无（只读）。
前端渲染：主面板四态卡 + 异常/售后次面板 + 底部圆形扫码上货按钮角标。

## 链路 13：店铺营业/自动接单（真实后端状态）

页面：商家端店铺设置。
前端动作：GET /api/merchant/shop 拉取状态；PUT /api/merchant/shop 切换营业/自动接单。
后端处理：读写 shops 表（id=1 单门店）；接单接口校验店铺营业状态，歇业时拒绝接单。
数据库变化：shops.business_status / auto_accept 更新。
前端渲染：首页/订单页展示营业标记，设置页切换后即时生效（多端共享同一后端状态）。

## 链路 14：商家商品管理

新增：POST /api/merchant/goods，插入 goods 表（stock 未传默认 999；**传 0 保留 0 售罄**）。
编辑：PUT /api/merchant/goods，更新 goods 表（**未传 stock 保留原库存**）。
上下架：PUT /api/merchant/goods/status，更新 status 字段（1 在售 / 0 下架），用户端仅展示在售商品。
售罄/库存：PUT /api/merchant/goods/stock（标记售罄=置 0 / 恢复库存），更新 stock；用户端据此显示售罄态并禁止加购。
分类：GET /api/merchant/goods/categories 返回现有分类，新增/编辑页选择器「选现有或新增」。
图片：POST /api/merchant/upload 上传 base64 图片至 backend/uploads，返回 /uploads/xxx 路径。
前端渲染：商品列表刷新（显示实时库存/已售/售罄标记），下架商品用户端不再可见。

## 链路 15：配送监控（商家端）

页面：商家端「配送监控」。
前端动作：GET /api/merchant/delivery/monitor，每 5 秒轮询；GET /api/merchant/robots 获取机器人真实状态。
后端处理：monitor 查询所有未完成配送任务（含失败任务），关联订单编号与送达点位，附加机器人位置；robots 调用开放物流平台 runtimeStatusList 返回真实设备（编号/名称/在线/电量/运行状态/位置，状态码映射为中文）。
数据库变化：无（只读）。
前端渲染：顶部展示真实机器人卡（可多台）；任务列表展示状态文本与位置。平台未配置或调用失败时，机器人区显示错误卡（"未配置开放物流平台凭据 / 本地演示模式"）+ 重试按钮。

## 链路 16：平台点位同步（真实模式）

入口：商家端调用 POST /api/merchant/landmarks/sync（需商家身份）。
后端处理：调用开放物流平台 buildingList 获取 buildingId，landmarkInfo 获取点位列表，将 platform_building_id / platform_map_id / platform_landmark_id 写入本地 landmarks 表。
数据库变化：landmarks 表平台映射字段更新。
前端渲染：用户端下单选址展示真实点位；接单时据此创建真实排队任务。

## 链路 17：商家端活动管理（发布/编辑/上下线/删除）

页面：商家端工作台「活动管理」→ 活动列表/编辑。
前端动作：
新建：POST /api/merchant/activities，传 title、subtitle、link、sort（保存后默认发布 status=1）。
编辑：PUT /api/merchant/activities，传 id 与字段。
上下线：PUT /api/merchant/activities/status，传 id、status（1 发布 / 0 下线）。
删除：DELETE /api/merchant/activities，传 id。
列表：GET /api/merchant/activities（含未发布活动）。
后端处理：读写 activities 表；用户端 GET /api/activity/list 仅返回 status=1（已发布）活动。
数据库变化：activities 表增删改，status 控制发布状态。
前端渲染：商家端活动列表展示状态标签（已发布/已下线），可编辑/发布/下线/删除；用户端活动页展示已发布活动，点击跳转 link。

## 链路 18：商家配单/上货（上货配单 · 批次 · 一车多单）

页面：商家端「上货配单」页（入口：订单接单后直达、商铺首页底部圆形「配单上货」按钮、任务页右上角「配单上货」、订单详情「去配单/上货」、配送监控）。
展示：顶部搜索框（按批次序号/批次号/订单序号/订单号/商品名/点位/收餐人过滤批次列表）；**只展示「组单中（可派车）+ 待上货（可上货）」两类批次**（配送中/待取货由配送监控与任务页展示）；批次卡面标题为当日序号「批次 N」（daily_seq，每天从 1 重置），完整批次编号只在点进单批次详情后弱化展示；批次内每单子卡标题为「订单 N」（order.daily_seq），完整订单号只在订单详情页显示；单内每商品一行「图 + 名称 + 价格 + 数量」（价格在数量前），批次内全部订单全部商品完整展示（批次详情接口每单返回 items 商品明细）；取餐码弱化为一行小字；**无页面内冗余返回按钮**（左上角系统返回即返回上一页，派发完成自动回列表）。
流程（真实模式，设备控制接口）：
1. **组单**：商家接单（或自动接单）→ 订单并入「组单中」批次（≤12 单）。
2. **派车**：GET /api/merchant/device/pending 列表 → 组单中批次点「派车配送」→ POST /api/merchant/delivery/batch/dispatch → 路径规划 + 为每单创建平台任务 → 批次 1 待上货，机器人前往上货点（任务状态 20/30 去/到上货点，basicList 轮询同步 device_sn）。自动派车：批次满 12 单或自动接单模式等待期满 90s 自动触发。
3. **选择批次**：GET /api/merchant/device/pending 待上货批次 → 点「选择该批次上货」进入单批次详情（显示完整批次编号）。
4. **打开舱门**：POST /api/merchant/device/batch/open-bin → 对批次内全部任务逐个 loading/verify（各单取餐码，autoOpen=true）验证通过自动开舱（单仓一次放入全部货品）。**测试阶段（DEVICE_MOCK=true）按钮为「模拟打开舱门」，本地模拟成功，真实调用代码注释保留**。
5. **放货**：商家按清单放入各单货品（每单独立取餐码标签）。
6. **关闭舱门**：POST /api/merchant/device/batch/close-bin → 平台 drawerCtrl 关舱 → 机器人原地等待（任务仍 40）。前端弹窗「是否立即配送」。测试阶段本地模拟。

Mock 模式（PLATFORM_MOCK=true）：pending/scan 返回批次模拟，批量设备接口返回模拟成功，用于本地演示页面流程。

## 链路 18A：配送异常订单处理（重新配送 / 取消并退款）

触发：机器人超时未接单（定时扫描）/ 上货失败 / 送货失败 → 订单状态 6 配送异常（tasks 90/100 系列或超时扫描）；工作台「异常」→ 任务页异常分类可见。
流程（二选一）：
- **重新配送**：POST /api/merchant/order/exception/retry → 作废旧批次未完成任务（task_status 110）、从旧批次计数摘除 → 并入新的「组单中」批次（订单→2）→ 商家在上货配单页为新批次「派车」→ 重新上货配送。
- **取消并退款**：POST /api/merchant/order/exception/refund → 作废平台任务 → 订单→7 已退款 + 写入 refunds 售后记录（自动已退款）+ 回补未售商品库存 + 从批次摘除。
数据库变化：orders.status（2 或 7）、delivery_tasks 任务作废、delivery_batches 计数/状态（空批次标记批次已取消）、refunds 记录。

## 链路 19：用户取餐（扫码后：开舱→取餐→关舱→40s自动关→重开，一车多单计数）

页面：用户端「取餐」页（入口：配送追踪订单已送达 → 「模拟扫码取餐」/ 订单详情同按钮）。
流程：
1. **模拟扫码取餐**（测试阶段）：跳转取餐页（真实流程为扫机器人二维码，校验为本单机器人）。
2. **进入取餐页**：POST /api/delivery/pickup-scan（order_id）→ 校验订单归属 + 已送达(3) → 返回订单/取餐码/任务上下文。
3. **打开舱门**：POST /api/delivery/pickup-open → 有真实任务调平台 unloading/verify（strategies=手机号+取餐码，autoOpen=true）开舱即完成；无真实任务（测试兜底）本地完成并标记 test:true。**一车多单：开舱即标记本单已取走（batch.markOrderPicked → orders.picked_up_at + 批次已取计数），全部取完批次完成**。
4. **取餐**：页面提示取走自己的餐品，40s 倒计时。
5. **关闭舱门**：POST /api/delivery/pickup-close → 平台 unloading/confirm 关舱返回；订单置已完成。
6. **40s 自动关**：超时未关，平台自动关舱 → 页面进入"已自动关舱"，用户可点「重新打开」再次开舱（防止未取到餐）。
数据库变化：订单 status 3→4、orders.picked_up_at；任务状态由平台回调/basicList 轮询同步；批次计数/状态更新。
Mock/测试兜底：无真实任务时开/关舱本地直接完成（响应 test:true），便于无真机器人测试页面流程。

## 链路 20：退款/投诉售后流程

页面：用户端「订单详情→退款/投诉」「我的→售后记录」；商家端「工作台→售后」。
流程：
1. **用户申请**：订单已送达/已完成/配送异常 → POST /api/refund/apply（type=refund|complaint，reason）→ refunds 表新增，状态 0 待处理（退款金额=订单全额）。
2. **商家查看**：工作台售后数字=待处理数 → 售后列表 GET /api/merchant/refunds（待处理优先）→ 详情。
3. **商家处理**：
   - 退款：同意（POST /refund/handle action=approve，金额默认全额可改）→ 售后状态 3 已退款、订单状态 7 已退款；或拒绝（action=reject，需理由）→ 状态 2。
   - 投诉：回复（action=reply）→ 状态 4 已处理。
4. **用户查看**：GET /api/refund/list 我的售后记录，显示处理状态与商家回复。
数据库变化：refunds 表增改；同意退款时 orders.status → 7。
说明：试点阶段"退款"为本地标记（真实微信退款需商户号后接入）。

## 链路 21：订单取消 / 取消申请（免费窗口 + 商家审批）

页面：用户端「订单列表/订单详情」取消；商家端「工作台→取消申请」。
规则：
1. **免费窗口直接取消**：下单后 FREE_CANCEL_WINDOW_MS（默认 10 分钟）内，待支付/待接单/未真正开始配送（任务状态 < 50）的订单 → POST /api/order/cancel 直接取消（订单→5，任务→110，并从批次计数移除）。
2. **超时转取消申请**：超过窗口且未配送（待支付/待接单）→ 不可直接取消，POST /api/order/cancel-request（reason）提交，商家判断。
3. **配送中**：不支持取消/申请；送达后可走退款/投诉（链路 20）。
流程：
1. 用户订单详情/列表按钮：免费窗口内显示「取消订单」；超时显示「提交取消申请」（跳 pages/order/cancelRequest 填原因）。
2. 商家工作台「取消申请」角标=待处理数（GET /merchant/stats 的 cancel_requests）→ 列表 GET /api/merchant/cancel-requests → 详情。
3. 商家处理：同意（action=approve）→ 取消申请状态 3、订单→5 已取消（试点 PAY_MOCK 仅标记，真实退款待商户号）；拒绝（action=reject，需理由）→ 状态 2、订单继续。
4. 用户查看：订单详情展示最新取消申请状态与商家回复；GET /api/order/cancel-request/list 我的取消申请记录。
数据库变化：cancel_requests 表增改；同意时 orders.status → 5、delivery_tasks 任务 → 110、**delivery_batches 总单数 -1（批次内有效订单动态统计，取消单不参与批次完成判断）**。
