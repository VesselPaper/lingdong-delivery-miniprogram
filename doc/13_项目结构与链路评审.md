## 一、整体结构（评分：8.5/10 —— 清晰）

```
校内快递配送机器人/
├── backend/          单 Node 后端：domains（5 业务域）× services（13 共享服务）+ db.js + server.js
├── 管理员网页/        纯静态 + parts 拆分构建（build.js 拼 admin.js / admin-map.js）
├── 用户端/            微信小程序：9 页面组 + 8 utils
├── 商家端/            微信小程序：8 页面组 + 7 utils
├── 可视化大屏/        纯静态：dashboard + map3d 4 件套

└── 上线计划/ 逻辑树/  独立于 doc 的专项目录
```

**亮点**：
- 五块职责边界非常清楚：后端单一进程承载「API + 管理页 + 大屏 + WS + 定时器」（三服务同端口），运维面小，符合校园试点规模。
- 文档体系与代码 1:1：`04_核心业务链路` 7 篇正好对应订单状态机的每条主线，`06_接口协议` 覆盖全部 API，页面详解按端按页拆 60+ 篇——这在同类项目里是极高水准。
- 管理页采用「parts 源码 + build.js 产物」拆分构建，src/产物分离符合前端工程惯例。

**小瑕疵**：
- 管理页 parts 存在两个 `09-`（09-merchants / 09-ops），序号语义是「构建顺序」而非「层级」，新读者易误以为是同域。建议改 `09a-`/`09b-` 或按域改名。

## 二、后端分层（评分：7.5/10 —— 约定清晰，收口未完成）

### 2.1 分层模型（清晰）

```
server.js（组装）→ domains/{user,goods,order,delivery,admin}/routes.js（HTTP+守卫+参数）
                 → 同域 service.js（业务规则+状态机）
                 → 同域 queries.js（SQL 专属表）
        ↕  deps 注入（server.js 统一组装，域间通过 services/ 或注入传递）
services/{platform,runtime,push,wxpay,wxmp,batch,orderCancel,promotion,seq,...}（共享服务）
```

- **三层职责分离干净**：routes 只做 HTTP 适配，service 承载规则，queries 封装 SQL；同域内调用方向单向（routes→service→queries），没有反向依赖。
- **依赖注入防环**：server.js 是唯一组装点；batch.js「不持有 deps、钩子由 server 注册」（registerSummonAdvance），platform.js「回调钩子由 server 注入」（setDispatchHook），显式规避了 services 之间的循环依赖——这是本项目分层设计最好的部分。
- **约定成文**：order/service.js 头部明确写了「跨域读以只读 SQL + 注释；跨域写一律走 deps.goods / deps.user」，delivery 定时器注释也标注了「与 delivery/routes.js 同源」——约定不是秘密，是可审查的。

### 2.2 问题 A（重点）：orders 表写点未收口 —— 3 处直写 【已修复 2026-09-26】

> 修复后状态：`grep "UPDATE orders SET status"` 仅剩 order 域收口函数本身、order/queries.js（支付 0→1）、orderCancel.js（取消/退款 5/7 落账唯一实现）与测试文件。delivery/platform 域不再直写 orders.status。

`order/service.js` 注释声称「召唤配送 + 取餐关舱路径写 orders 的唯一咽喉」（arriveOrder / fulfillOrder），但 grep 全量扫描显示 **orders 的 UPDATE 分布在三个文件**：

| 位置 | 写点数量 | 内容 | 性质（修复前） |
| --- | --- | --- | --- |
| order/queries.js + service.js | 5 处 | 入库 / markPaid / arriveOrder(→3) / fulfillOrder(→4) | ✅ 归属正确，已收口 |
| **delivery/routes.js** | 6 处 | confirm 完成(→4)、批次派车(→2)、picking_up_at 复位、delivery/confirm | ⚠️ 跨域直写 |
| **delivery/service.js** | 8 处 | 批次开始配送(→2)、送达(→3)、异常(→6)、pickup_timeout_stage 两段式 | ⚠️ 跨域直写 |
| **services/platform.js** | 4 处 | 派车(→2)、回调置送达/其他状态 | ⚠️ 历史遗留（注释自认） |

**影响**：状态迁移守卫 `canAdvanceOrderStatus` 只覆盖收口路径；delivery 直写与 platform 直写走各自的判断（platform 另有自己的 canMoveOrderStatus），三套判断语义"保持一致"靠注释约束，存在漂移风险。状态迁移的正确性是本系统最核心的不变量（涉及资金/退款/配送推进），写点分散是最大的结构债务。

**修复做法（分 3 小批，每批独立回归）**：
1. ✅ delivery 域 4 处状态迁移直写 → order.service 收口函数：`markOrderInBatchStart`（批次→2）、`markOrderDelivered`（→3）、`markOrderException`（→6），delivery 只调 `deps.order.*`；**取餐过程字段**（picking_up_at / pickup_opened_at / pickup_open_count / pickup_timeout_stage / pickup_revisit_at）不涉及状态合法性，保留在 delivery 域并注明归属；
2. ✅ platform 域 4 处 → 注入钩子 `platform.setOrderStateSink`（server.js 装配调 order 域收口），platform 只做 HTTP 与回调解析；删除 platform 自己的 canMoveOrderStatus（与 order 域 canAdvanceOrderStatus 语义等价）；
3. ✅ 收口后删除等价重复实现 `batch.markOrderPicked`（与 fulfillOrder 逻辑重复），batch 侧只保留纯计数 `countPicked`。

### 2.3 问题 B：platform.js 1808 行职责过重（占 services 总量 ~45%）【已拆分 2026-09-26】

platform.js 同时承担：①平台 HTTP 客户端（请求签名/路由）②回调状态机（applyStatus/onTaskStatus，**并直写 orders/delivery_tasks**）③Mock 模拟器（本地配送状态机）④设备控制适配（开舱/召唤/位置）⑤轮询同步。五个职责一个文件，且与 order/delivery 域存在双向数据耦合。

**修复做法**：按职责拆三件 + 入口聚合（依赖方向单向：mock→callbacks→http，入口→全部）：
- `services/platform-http.js` —— 通信/查询/控制基础层（HTTP 原语、点位地图、设备位置/标定、控制、门禁）；
- `services/platform-callbacks.js` —— 回调/轮询状态同步咽喉（applyStatus/updateTask/syncTaskStatus + 注入的订单状态迁移钩子 setOrderStateSink/emitOrderState）；
- `services/platform-mock.js` —— 本地模拟状态机（MOCK_STEPS / mockTasks / mockAdvance / cancelMockTask）；
- `services/platform.js` —— 任务创建/派车/召唤等业务编排 + 聚合导出（导出清单与原文件完全一致，调用方无感）。

### 2.4 问题 C：状态字典多份重复（漂移源）【结论：保持按数据项分层，不设横切单源】

`ORDER_STATUS`（order/service.js）、`ORDER_STATUS_TEXT`（statusEvents.js，注释自认口径不完全一致）、`BATCH_STATUS`（batch.js）、`ADMIN_TASK_STATUS`（admin/service.js）、`TASK_STATUS_TEXT`（statusEvents.js）——同一实体的状态文案在 4+ 处定义，注释靠「管理页口径」和「内部基准文案」区分。目前有 doc/08 常量文档兜底，但代码内重复定义终会漂移（statusEvents 已出现"批次 4 写已取消 vs 内部异常"的口径差异）。

**评审结论（2026-09-26 决定不新设 `services/constants.js` 横切单源）**：项目分层按「数据项归属」约定 —— orders 状态字典归 order 域、批次字典归 delivery 域（services/batch）、展示快照字典归 statusEvents。字典随数据项归属本域是既有约定，新增一个横切常量层反而引入第三种分层范式；展示口径差异是 statusEvents **有意为之**（面向管理页的精简文案），已在头部注释说明。保持现状 + 注释标注口径，视为已决策项。

### 2.5 其余小项
- server.js 223 行承担组装+启动+静态+WS+进程兜底，可接受；若继续膨胀再拆 `app.js`（组装）/ `index.js`（启动）。
- 跨域**读**直接 SQL 是全库共享 SQLite 的必然（单库无物理隔离），当前规模务实；若未来拆服务/多实例，需把这些跨域读迁移为服务 API（doc/02 已有演进说明可补充该路径）。

## 三、订单核心链路（评分：9/10 —— 清晰，文档完备）

### 3.1 主线链路（状态机 8 态：0 待支付 → 1 待接单 → 2 配送中 → 3 已送达 → 4 已完成；5 已取消 / 6 配送异常 / 7 已退款）

```
下单 createOrder（服务端算价/促销/拆单/取餐码）
  → 支付 payOrder（mock 直通 / 微信 V3 回调 markPaidNotify）
  → 自动接单 maybeAutoAccept（营业+auto_accept → batch.addOrderToBatch best-fit 组单）
  → 批次定型（满 12 件 或 90s 超时，定时器④ + doDispatchBatch 并发安全）
  → 上货（扫码/开舱/关舱，召唤模式 syncLoading=0）
  → 召唤配送 startSummonDelivery → 逐点送达 arriveOrder(→3)
  → 取餐关舱 fulfillOrder(→4) → batch.countPicked → 全取完 → 下一站/召回
  → 取消（免费窗内直接 / 申请审批）/ 退款 / 异常(6) 重配送 → 全链路文档化于 04_核心业务链路 7 篇
```

**亮点**：
- 金额权威计算（促销/配送费/拆单收一次费）与支付幂等（event_id + CAS + 金额比对）集中在 order 域，链路主线无旁路。
- 状态推进「收口函数 + 兜底轮询」双保险：事件钩子丢/进程重启后，定时器①③④⑤ 都能补位推进，注释对每条兜底都说明了触发条件。
- 拆单、取餐码查重、批次容量实时计算（不读缓存列）等边界都有专项注释与修史（P1-x 编号），可追溯性强。

### 3.2 风险点
- **双守卫**：order 的 `canAdvanceOrderStatus` 与 platform 的 `canMoveOrderStatus` 并存（语义"保持一致"靠注释）；加上 delivery 直写绕过了两者——状态迁移合法性检查并非全路径强制。与问题 A 同源，收口后自然消除。
- **订单状态迁移的「写点」比「收口点」多**：新读者按注释追「唯一咽喉」会被 delivery/platform 直写误导，建议在收口完成前，doc/04 补充一张「orders 写点地图」。

## 四、事件触发逻辑（评分：8/10 —— 设计得当，理解成本偏高）

### 4.1 事件全景（触发源 × 通道 × 消费方）

| 触发源 | 通道 | 消费者 |
| --- | --- | --- |
| 用户 HTTP 动作（下单/支付/取消/取餐/开舱） | 直接调用 service | 本域 + deps |
| 微信支付回调 | wxpay 验签 → markPaidNotify | order 域 → maybeAutoAccept |
| 平台回调（任务/设备状态） | platform applyStatus/onTaskStatus | 任务/订单状态同步 |
| **内部钩子**（注入式） | autoLoadHook（新单→车去上货点） | autoLoad.schedule（防抖 5s） |
| | settleRobot（取消→回上货点释放） | deliveryService.settleRobotAtLoading（3 分钟释放） |
| | registerSummonAdvance（取走→下一站） | advanceSummonDelivery（5s 步进） |
| **定时器 5 组**（delivery/timers.js 统一装配） | ① 平台状态轮询 8s（兜底）② 超时未接单 60s ③ 取餐超时两段式 30s ④ 批次自动定型 15s ⑤ 召唤推进看门狗 5s | delivery service / batch |
| 状态流水采集器 | statusEvents.diffOnce 2.5s 快照比对 | status_events 表（管理页时间线） |
| 实时推送 | push.broadcast（order_created/batch_dispatched 全站）/ broadcastTopic（admin/live 泵） | 商家端 / 管理员页 |

**亮点**：
- 「事件驱动优先 + 定时器兜底」是刻意且正确的架构：主链路由钩子推进（低延迟、无空转），轮询只兜异常（重启丢失/事件失败），注释对每个定时器都写明了「为什么轮询不能省」。
- statusEvents 的设计是亮点：**零侵入采集器**（不埋 28 处 SQL 写点）+ **audit 线索关联操作者**（37 处 audit 已有信息复用），用 2.5s diff 换来了完整时间线，避免触碰核心配送代码——取舍非常务实。
- 无订阅者时 adminLive 泵自动跳过（零开销）；push 断线指数退避 + 无订阅不重连（省电省流量）。

### 4.2 风险点
- **事件类型无枚举约束**：push.broadcast 的 type 字符串散落在调用点（order 域 payOrder、delivery 域 dispatch），新增事件类型无编译期/运行期校验。建议 push.js 导出 `EVENT_TYPES` 并在 broadcast 校验，doc/06_07 已有 WS 文档可同步。
- **autoLoad 全局单防抖器**（模块级 debounceTimer）：单实例正确，多实例部署会互相清定时器（当前试点单实例无碍；若未来多实例需改为按批次防抖）。
- **双引擎重叠**：autoLoad（"去"上货点，事件驱动）与看门狗⑤（"守"上货点，4 分钟续一次）分工明确但初次阅读者容易混淆；doc/04 或代码注释建议补一张「谁负责车的哪个动作」的职责表。
- 进程兜底 `unhandledRejection` 只记不退出：服务可用性优先（正确），但无告警出口——上线后建议把 fatal 日志接守护进程告警（上线计划已有 pm2/nssm 规划）。
