## 1. 订单状态机（orders.status）

出处：`backend/domains/order/service.js:13`（ORDER_STATUS）、`service.js:67`（canAdvanceOrderStatus）、`backend/services/orderCancel.js:21/32`（claimCancelled / claimRefunded）。

| 数值 | 文案 | 含义 | 允许流转到（业务路径） |
| --- | --- | --- | --- |
| 0 | 待支付 | 下单成功未支付；可支付或直接取消 | 1（支付成功）；5（窗口内取消）；7（退款） |
| 1 | 待接单 | 已支付，等待商家接单；自动接单（营业中且 auto_accept=1）时直接并入批次 | 2（接单并入批次）；5（取消）；6（任务失败/超时）；7（退款） |
| 2 | 配送中 | 已接单并入配送批次，批次派车后机器人配送中 | 3（到达取餐点/任务 70）；5（取消）；6（上货失败 9x/取货失败 10x、超时未接单）；7（退款） |
| 3 | 已送达 | 机器人到达取餐点，待用户取餐（orders.delivered_at 记录到达时刻） | 4（关舱取走）；5（取消）；6（异常）；7（取餐超时二段驳回自动退款） |
| 4 | 已完成 | 用户关舱取走（orders.picked_up_at 记录取餐时间） | 7（售后退款，商家同意） |
| 5 | 已取消 | 用户/商家取消或平台任务取消（110/150） | 7（退款） |
| 6 | 配送异常 | 上货失败（90~95）/取货失败（100~106），或机器人长时间未接单/任务挂起（DELIVERY_TIMEOUT_MS） | 2（重新配送）/ 3 / 4（商家处理后恢复）；5（取消）；7（退款） |
| 7 | 已退款 | 退款已同意并落账，终态 | — |

状态守卫规则（`canAdvanceOrderStatus`，`service.js:67-79`）：

- 终态集合 `_ORDER_TERMINAL = [4, 5, 7]`：终态不可迁出。
- 置 5（已取消）：仅允许从 0 / 1 / 2 / 3 / 6 进入。
- 置 6（配送异常）：仅允许从 1 / 2 / 3 进入；6 可去向 2 / 3 / 4。
- 其余按 `_ORDER_RANK = {0:0, 1:1, 2:2, 3:3, 4:4, 5:0, 6:5, 7:0}` 只允许前向迁移。
- 退款（→7）不走上述守卫：由 `orderCancel.js:32 claimRefunded` 从 0~6 任意状态进入（CAS 抢占，7 为终态不可重复退）。

取餐超时阶段（orders.pickup_timeout_stage，`backend/db.js:352` 注释 + `backend/domains/delivery/service.js:456-571`）：

| 数值 | 含义 | 触发与去向 |
| --- | --- | --- |
| 0 | 无（正常待取） | 已送达(3) 超 PICKUP_TIMEOUT_MS（默认 15 分钟）且从未开舱 → 置 1 |
| 1 | 一段超时：先送其他单，稍后返回 | 批次有其他未取单时重排路线（本单停靠点移末尾）；其他单送完 → 重建任务返程再等，置 2 |
| 2 | 已返回，二段等待中 | 自 pickup_revisit_at 起再等 PICKUP_RETRY_TIMEOUT_MS（默认 15 分钟）仍未取 → 驳回退款，置 3 且订单 → 7 |
| 3 | 已驳回（取消并退款） | 自动写一条 refunds 记录（type=refund，状态 3 已退款） |

取餐守卫：用户开舱 = orders.picking_up_at 置位，超时计时暂停；超过 PICKUP_PICKING_GUARD_MS（默认 5 分钟）未关舱视为「打开后没取」，清位恢复计时（`delivery/service.js:528-531`）。

## 2. 批次状态机（delivery_batches.status）

出处：`backend/services/batch.js:16`（BATCH_STATUS）、`backend/domains/delivery/queries.js:52-69`（各状态写库）。

| 数值 | 文案 | 含义 | 流转说明 |
| --- | --- | --- | --- |
| 0 | 组单中 | 批次创建，持续收单（best-fit 按商品件数并入，容量 BATCH_MAX_ITEMS） | 满容量（12 件）**或成立超 BATCH_WAIT_MS（90s）→ 自动定型置 1**（`timers.js` ④ 批次自动定型，与是否自动接单无关；无空闲车等失败 60s 节流重试，车一上线自动补定型）；批次被取消清空 → 置 4「批次已取消」 |
| 1 | 待上货 | 已派车定型：创建平台任务/召唤上货点，等待商家上货 | 商家开舱-关舱后点「立即配送」→ 置 2；撤销派车 → 回 0（组单中）；模拟送达时批次首单送达 → 自动置 2 |
| 2 | 配送中 | 已确认上货，机器人按路线逐点位配送 | 批次内全部有效订单已取走（picked_up_at 非空或任务 ≥ 80）→ 置 3 |
| 3 | 已完成 | 批次配送完成（completed_at 落库） | 终态 |
| 4 | 异常 | 批次异常/已取消 | 文案按场景写库：空批次取消写「批次已取消」（batch.js:134）；管理员测试清理写「测试清理已取消」（admin/queries.js:58）；字典基准文案为「异常」 |

批次关键字段：route（JSON 停靠顺序，开始配送后才规划）、device_sn（指派机器人）、total_orders / total_items（单数与件数计数）、picked_orders（已取走计数）、delivery_mode（'summon' 召唤多单配送 / '' 或 'task' 一单一单送）、current_stop（召唤模式当前停靠点，1-based，0=未开始）。

| 130 | 下货流程挂起 | — |
| 131 | 送货挂起，返回上货点 | — |

> 另有一份**精简版任务字典** `backend/services/statusEvents.js:21`（`TASK_STATUS_TEXT`），只供 `status_events.status_text` 写入时快照用，与上表同源但文案更短且只覆盖常用码：`0 排队中 / 1 已取消 / 10 已接收 / 20 去往上货点 / 30 到达上货点 / 40 上货中 / 50 已上货 / 60 去往取货点 / 70 到达取货点 / 71 等待取餐 / 80 完成 / 90 上货失败 / 100 取货失败 / 110 已取消 / 120 挂起 / 150 已关闭`；上表其余码（91~95、101~106、130/131/132/140）不在其中，落库文案为兜底 `状态 <n>`。故 `delivery_tasks.status_text`（平台全量文案）与 `status_events.status_text`（精简文案）同一状态码可能不同字，例如 80 =「任务完成」/「完成」、110 =「任务取消」/「已取消」、120 =「上货流程挂起」/「挂起」。

终态与轮询（`platform.js:1210-1216`、`delivery/timers.js:29-31`）：

- 任务终态：80 / 110 / 150 及本地作废标记 void_at；终态任务不再轮询、迟到回调一律丢弃（防「已取消订单复活成已送达」）。
- 70 与 90~109 必须继续轮询：70 是「等待取餐」停等态，轮询是到达回调丢失时的送达兜底；9x/10x 需轮询驱动到配送异常(6)。
- 本地模拟推进序列（PLATFORM_MOCK=true）：0 → 10 → 20 → 30 → 50 → 60 → 70 → 80，每步间隔 4 秒（`platform.js:56-65`）。

## 4. 售后 / 退款 / 取消申请状态

### 4.1 售后（refunds.status）

出处：`backend/domains/order/service.js:17`（REFUND_STATUS）、`backend/db.js:150-161`（表注释）。

| 数值 | 文案 | 含义 |
| --- | --- | --- |
| 0 | 待处理 | 商家未处理 |
| 2 | 已拒绝 | 商家拒绝 |
| 3 | 已退款 | 退款已同意并标记（模拟支付仅本地标记，不真实退钱） |
| 4 | 已处理 | 投诉（type=complaint）已回复 |

type 字段：`refund` 退款 / `complaint` 投诉；amount 默认订单全额，商家同意时可改（部分退款）。

### 4.2 取消申请（cancel_requests.status）

出处：`backend/domains/order/service.js:19`（CANCEL_REQ_STATUS）、`backend/db.js:162-171`。

| 数值 | 文案 | 含义 |
| --- | --- | --- |
| 0 | 待处理 | 商家未处理 |
| 2 | 已拒绝 | 商家拒绝 |
| 3 | 已同意取消 | 同意后订单同步置 5 已取消 |

免费取消窗口：下单后 FREE_CANCEL_WINDOW_MS（默认 10 分钟）内可直接取消，无需申请；超过窗口须提交取消申请由商家判断（`service.js:22 withinFreeCancelWindow`，前端展示剩余秒数见 `order/routes.js:112`）。

## 7. 运行标志（登录响应 runtime 与 /api/shop/status）

登录响应（`backend/domains/user/service.js:128`）返回：

```json
{ "token": "...", "user": {...}, "runtime": { "mode": "demo", "device_mock": true, "pay_mock": true, "login": "demo" } }
```

| 字段 | 取值 | 含义 |
| --- | --- | --- |
| mode | demo / pilot / production | 运行档（RUN_MODE） |
| device_mock | true / false | 设备控制（开舱/关舱/派发）是否走本地模拟；仅 demo 档为 true（runtime.js:80） |
| pay_mock | true / false | 是否模拟支付（= PAY_MOCK=true）；模拟支付下退款不产生真实资金流 |
| login | user=real/demo（真实微信登录是否可用）；merchant=**acct**（账号密码体系，2026-09-24 起） | 按端判定：用户端凭据独立（runtime.js:63-68）；商家端登录不再依赖微信凭据 |

前端使用点（已确认）：

- 用户端 `用户端/pages/order/detail.js:17`、`用户端/pages/order/confirm.js:43`：`pay_mock === true` 时支付按钮显示「模拟支付」。
- 商家端 `商家端/pages/device/batchDetail.js:11-12`：`device_mock === true` 时开舱/关舱按钮走本地模拟分支（取不到默认 false，宁可真实分支报错也不假装成功）。

`/api/shop/status`（`backend/domains/goods/service.js:15-19`）额外下发 run_mode / device_mock / pay_mock / login_user / login_merchant（商家端据此选择设备控制分支；login_merchant 恒为 'acct'）。

服务端运行诊断 `runtime.describe()`（`backend/services/runtime.js:202-219`）全字段：run_mode、device_mock、real_login、login_user、login_merchant、real_pay、pay_mock、real_platform、platform_host、prod_platform、unsafe_prod、summon_delivery、route_count_weight、arrive_radius_m、pos_m_per_unit、callback_token_configured。

## 8. 业务状态流水（status_events）

出处：`backend/db.js:422`（建表）、`backend/services/statusEvents.js`（写入与文案字典）；表结构、索引与写入方详见 `doc/03_数据库设计.md` 5.1。用途：管理页「详情抽屉 → 状态时间线」（`GET /api/admin/timeline`）还原每次状态变更的时间与操作者。

### 8.1 entity_type 枚举

| 取值 | 含义 | 状态列 | 活跃判定（离开活跃集即视为进入终态并补记迁移） |
| --- | --- | --- | --- |
| order | 订单 | orders.status | `status NOT IN (4,5,7)`（终态：已完成/已取消/已退款） |
| batch | 批次 | delivery_batches.status | `status NOT IN (3,4)`（终态：已完成/异常） |
| task | 配送任务 | delivery_tasks.task_status | `task_status NOT IN (80,110,150)`（终态：完成/取消/关闭） |

### 8.2 actor_type 枚举

| 取值 | 含义 | 来源 |
| --- | --- | --- |
| system | 系统自动（默认值） | 无操作者线索时的兜底（采集器捕获、定时任务、平台回调驱动的迁移） |
| admin | 管理员 | `req.admin`（adminGuard），`actor_id` = admin_users.id，`actor_name` = username |
| merchant | 商家 | `req.user` 且 `role='merchant'`，`actor_id` = users.id，`actor_name` = nickname |
| user | 用户端用户 | `req.user` 且非 merchant，字段同上 |
| platform | 开放物流平台 | 预留值：写入方目前由采集器记 system（`record()` 显式传入时才落 platform） |

`actor_id` 为 0、`actor_name` 为 '' 表示无具体操作者。操作者归属的传递路径：`audit(req, action, target, detail)` 顺带调用 `hintActor(target, actor, note)` 登记线索（`STATUS_HINT_TTL_MS` 默认 20 秒有效、命中即消费），采集器 `recordTransition` 捕获到该实体迁移时用线索里的操作者署名，否则记 `system`。

### 8.3 status_text 文案字典

`status_events.status_text` 是**写入时快照**，取自 `statusEvents.js` 的三份字典（与各域字典同源，但有精简差异）：

| 实体 | 字典常量 | 与业务字典的差异 |
| --- | --- | --- |
| order | `ORDER_STATUS_TEXT` | 与 `order/service.js` 的 `ORDER_STATUS` 完全一致（0~7） |
| batch | `BATCH_STATUS_TEXT` | 4 =「已取消」，而 `batch.js` 的 `BATCH_STATUS[4]` 基准文案是「异常」（`delivery_batches.status_text` 实际写库还可能是「批次已取消」/「测试清理已取消」） |
| task | `TASK_STATUS_TEXT` | 精简版，见 §3 表下注（80/110/120 等文案更短，且不含 91~95、101~106、130/131/132/140） |

### 8.4 采集器局限（已知）

- 采集器是**定时快照比对**（`STATUS_EVENTS_MS` 默认 2500ms），不是写点埋点：同一实体在 2.5 秒内连续跳两次状态，只会记到最终值（中间态丢失）。
- 首次运行只建快照、不落事件，避免把存量数据当成一轮变更刷进去；因此采集器启动前发生的历史迁移没有事件，`/admin/timeline` 会用 `legacy` 推断节点兜底（推断语义由「放在 `legacy` 而非 `events`」表达，节点只有 `{label, at}`，与真实事件不混排；有真实事件时 `legacy` 一律为空）。
- 事件写入失败不阻断业务（`record()` 内部 catch 返回 false）。
