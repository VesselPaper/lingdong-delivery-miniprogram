> 最后更新：2026-09-22

## 1. 总体架构

### 1.1 单进程三服务同端口

后端只有一个 Node.js 进程（`backend/server.js`），监听 `0.0.0.0:3000`（`server.js` → `BIND_HOST` 常量），同一个 Express 应用同时托管三套 Web 服务，外加 WebSocket 实时推送与静态资源：

```
                         +----------------------------------------------------+
                         |        backend 单进程（node server.js）            |
                         |         Express · 端口 3000（默认）                |
                         |                                                    |
 用户端小程序  ------>   |  /api/*   小程序 API（user/goods/order/            |
 (微信原生 18 页)        |          delivery/admin 5 域路由）                 |
 商家端小程序  ------>   |  /admin/* 管理员网页（静态页+adminGuard 鉴权）     |
 (微信原生 19 页)        |  /dashboard/* 可视化大屏（静态页+只读聚合接口）    |
 浏览器·管理员 ------>   |  /ws      WebSocket 实时推送                       |
 浏览器·大屏  ------>    |  /uploads /store-img 静态资源（图片）              |
                         |  /        根路径 302 -> /admin/                    |
                         +---------+------------------------+-----------------+
                                   |                        |
                     +-------------v-------------+     +----v------------------------+
                     | SQLite（本地文件）        |     | robox 开放物流平台（HTTPS） |
                     | backend/data/lingdong.db  |     | queue/create、basicList、   |
                     | 业务数据零外部数据库服务  |     | eviz、设备控制、回调（等）  |
                     +---------------------------+     +-----------------------------+
                                                            |（公网可达时才注册回调；
                                                            | 无公网时 basicList 轮询兜底）
```

- 小程序 API、管理员网页、可视化大屏**共用同一端口、同一进程、同一来源**（同源），因此管理员页与大屏不需要单独部署，后端一启动三者同时可用（`server.js` → 静态托管段）。
- 静态托管细节：`app.use('/admin', express.static(ADMIN_DIR))`、`app.use('/dashboard', express.static(DASHBOARD_DIR))`。Express 的 serve-static 对目录请求自带 301 → `/admin/`、`/dashboard/`，页面里的相对路径（`admin.js`、`css/…`）因此能正确解析；**URL 末尾必须带斜杠**，否则相对路径会被解析到错误位置（`server.js` 注释）。
- 大屏走路径而非单独起服务的原因（`server.js` → `DASHBOARD_DIR` 注释）：大屏主机只需访问后端同一个端口，不再多一个进程/端口要运维。
- 微信服务器（code2session、支付回调）为外部依赖：登录走 HTTPS 调用微信接口；支付回调需公网可达的 https 地址（`.env` 的 `WXPAY_NOTIFY_URL`）。

### 1.2 后端分层

```
backend/
├── server.js          装配入口：.env 加载 → 运行守卫 → 5 域路由挂载 → 静态托管 → WS → 定时器
├── db.js              建表 / 迁移 / 种子数据（init / seed / importStoreGoods / applySeedImages）
├── domains/           分层域（每域 queries.js + service.js + routes.js）
│   ├── user/          登录、用户、购物车、地址（/api/auth/* /api/user/* /api/cart/* /api/address/*）
│   ├── goods/         商品、活动、店铺状态、商家商品管理（/api/goods/* /api/activity/* /api/merchant/{shop,goods,activities}*）
│   ├── order/         订单、支付、退款、售后、取消（/api/order/* /api/pay/* /api/refund/* 等）
│   ├── delivery/      配送、批次、设备、平台任务（/api/delivery/* /api/merchant/delivery/* /api/platform/*；另含 timers.js 定时器）
│   ├── admin/         大屏只读聚合（/api/dashboard/*，免登录）+ 管理员工具（/api/admin/*，adminGuard；另含 live.js 实时泵）
│   └── _shared.js     公共中间件工厂 createShared(store)：auth / merchantGuard / adminGuard / audit / ok / maskPhone / toStock
├── services/          共享服务（不依赖任何域，域间互相 require 时不会成环）
├── tools/             维护脚本（邀请码 / 管理员账号 / 图标生成）
└── data/ uploads/ seed_images/  运行时数据（.env 等）
```

- 域路由工厂签名统一为 `(store, deps) => router`（`server.js` → 域挂载段），URL 与重构前完全一致，前端零改动。
- 依赖方向：`services/runtime.js` 只依赖 `services/wxpay.js`，**禁止反向 require `services/platform.js`**（platform 的导出在文件末尾，成环会拿到空对象使守卫静默失效，`runtime.js` 注释明确说明）。
- 跨域协作通过「依赖注入 + 钩子」完成：如批次推进钩子 `batch.registerSummonAdvance(...)` 由 `server.js` 注入 `deliveryService.advanceSummonDelivery`（`server.js` → deliveryHookDeps），避免 batch 域反向持有各域依赖造成循环引用。

### 1.3 前端三端与后端的关系

| 端 | 载体 | 访问入口 | 关键点 |
|---|---|---|---|
| 用户端 | 微信小程序（原生） | `/api/*`（HTTP JSON）+ `/ws`（可订阅推送） | `用户端/utils/config.js` 配 baseUrl；token=openid |
| 商家端 | 微信小程序（原生） | `/api/*` + `/ws` | `商家端/utils/config.js` 配 baseUrl；商家接口过 merchantGuard |
| 管理员网页 | 浏览器 | `/admin/` 静态页 + `/api/admin/*` + `/ws` | 账号密码登录，请求头 `x-admin-token` |
| 可视化大屏 | 浏览器 | `/dashboard/` 静态页 + `/api/dashboard/*` | 只读免登录，支持 `?demo=1` |

- 小程序端**不存放**开放物流平台凭据与微信支付商户凭据，全部只在后端 `.env`（凭据仅后端持有，见本文「环境变量」节）。
- 真机预览：把双端 `utils/config.js` 的 baseUrl 改为电脑局域网 IP（如 `http://192.168.x.x:3000/api`），并保证同一 WiFi（`README.md` §6 真机预览）。
- 商品图片：商家上传图走 `/uploads`（`server.js` → `UPLOAD_DIR`），内置种子图走 `/store-img`（`seed_images/`）；响应中相对资源统一由 `_shared.js → assetAbs / ok` 拼成完整 URL 返回。

## 2. 运行模式与环境变量

### 2.1 运行模式三档（RUN_MODE）

后端把「登录 / 支付 / 配送 / 设备控制」四条链路的真假绑定成一致的组合，杜绝「演示登录 + 模拟支付 + 生产物流平台 + 前端假配送」这类能真实误调度机器人的混用（`runtime.js` 头注释）。`RUN_MODE` 留空默认 `demo`，非法值由 `check()` 报错并拒绝启动。

| 档位 | 定位 | 强制约束（`runtime.js → check()`） |
|---|---|---|
| `demo` | 本地演示 | 必须 `PLATFORM_MOCK=true`（禁止连任何真实物流平台）；设备控制自动走本地模拟 |
| `pilot` | 试点 | 真实配送 + 真实设备控制；登录/支付可模拟；`PLATFORM_BASE` 主机名必须以 `test-` 开头，否则需 `ALLOW_UNSAFE_PROD_PLATFORM=true` 逃生阀 |
| `production` | 正式 | 禁止 `PLATFORM_MOCK` / `PAY_MOCK` 为 true；要求双端真实微信登录凭据 + 微信支付四要素齐备 |

守卫执行时机：`server.js` → `runtime.assertBootable()`，**必须在 `require('./services/platform')` 之前**（platform/wxpay 在模块加载期就把 env 捕获成模块级常量）。守卫只拒绝启动、绝不静默改写 `process.env`。

### 2.2 环境变量全表

以下默认值以 `backend/services/runtime.js`、`backend/.env.example` 为准（与 `services/platform.js`、`services/wxpay.js`、`domains/*` 中的读取点核对一致）。

**A. 运行模式与开关**

| 变量 | 默认值 | 含义 | 影响 |
|---|---|---|---|
| `RUN_MODE` | `demo`（留空即 demo） | 三档运行模式 | 决定整档约束组合，非法值拒绝启动（`runtime.js → check`） |
| `PLATFORM_MOCK` | 未设=false（真实模式）；模板默认填 `true` | 配送走本地 Mock 状态机还是真实平台 | demo 必须 true；production 必须 false；platform.js 模块加载期捕获 |
| `PAY_MOCK` | 未设=false；模板默认填 `true` | 是否跳过真实微信支付 | production 必须 false；模拟支付下退款只改库、不退钱 |
| `DEVICE_MOCK`（无此键） | 派生值：`RUN_MODE=demo` 时为真 | 开舱/关舱/派发是否本地假装 | **没有独立环境变量**，由 `runtime.js → deviceMock` 派生；`.env.example` 无该键；历史文档中的 `DEVICE_MOCK=true` 属旧版描述 |
| `ALLOW_UNSAFE_PROD_PLATFORM` | 未设=false | 逃生阀：允许 pilot 连生产物流平台 | 需显式承担风险；启动摘要告警 |

| `BIND_HOST` | `0.0.0.0` | 监听地址 | 默认全网段可达（真机预览需要）；反向代理后设 `127.0.0.1`（`server.js` → `BIND_HOST`） |
| `PORT` | `3000` | 端口 | 三服务同端口（`server.js` → `PORT`） |

## 3. 启动与部署

### 3.1 命令行启动（首次建库 + 种子）

```bash
cd backend
npm install        # 首次（node_modules 未进仓库）
node server.js     # 或：根目录双击「启动服务器.bat」
```

- 首次启动自动建库并写入种子数据：`db.js → init`（建表/迁移）→ `seed`（1 个店铺「零栋铺子」+ 真实点位（川师成龙校区，与平台核对）+ 基础商品）；随后 `importStoreGoods`（`store_goods.json` 门店真实商品替换导入，幂等）与 `applySeedImages`（为无图商品回填同名 `/store-img/*` 种子图，不覆盖商家上传图）。
- 看到 `[lingdong-backend] listening on http://0.0.0.0:3000` 即成功，随后打印运行模式摘要（登录/支付/配送/设备控制/召唤配送各链路状态）。
- 验证：浏览器访问 `http://127.0.0.1:3000/api/goods/list` 返回 `{"code":0,...,"data":[...]}`。

### 3.2 根目录 bat 脚本

| 脚本 | 作用 |
|---|---|
| `启动服务器.bat` | 进入 backend 目录跑 `node server.js`；先用 `netstat` 探测 3000 端口，已监听则提示「后端已在运行」不重复启动 |
| `打开管理员网页.bat` | 只打开网页不启动后端；默认连 `127.0.0.1:3000`，同目录存在 `服务器地址.txt`（第一行 `IP:端口`）时改连远程；先 curl 连通性探测，连不上给排查提示 |
| `打开可视化大屏.bat` | 同上，打开 `/dashboard/` |

### 3.3 服务器访问（同一 3000 端口三 URL）

| 谁 | 地址 | 认证 |
|---|---|---|
| 管理员网页 | `http://<IP或域名>:3000/admin/` | 账号密码登录（无共享令牌；账号用 `backend/tools/admin_user.js` 管理） |
| 可视化大屏 | `http://<IP或域名>:3000/dashboard/` | 免登录只读；支持 `?demo=1` |
| 小程序 API | `http://<IP或域名>:3000/api/...` | 各接口鉴权 |
| 根路径 | `http://<IP或域名>:3000/` | 302 跳转到 `/admin/`（Express `res.redirect` 默认 302；`/admin/`、`/dashboard/` 目录请求的 301 来自 serve-static） |

> ⚠️ 末尾**必须带斜杠**（`/admin/`、`/dashboard/`），页面相对路径脚本才能正常加载（`server.js` 注释）。

### 3.4 防火墙 / 域名 / HTTPS

1. 服务器防火墙 / 云安全组**放行 3000 端口**（本地能开、外面打不开多为这一步，`README.md` §三 必要条件）。
2. 当前 `IP:3000` 直连即可用；上域名 / 443 时加一层 Nginx 反向代理，把 `/` 转发到 `http://127.0.0.1:3000`（管理员、大屏、API 同端口同源，全部跟着走）。此时建议 `BIND_HOST=127.0.0.1` + `TRUST_PROXY=1`（`README.md` §三 可选）。
3. 微信小程序连服务器 API **必须 HTTPS 域名**，且需在小程序后台配置 request 合法域名（`README.md` §三）。
4. 支付/平台回调需公网可达：`WXPAY_NOTIFY_URL` 与 `PLATFORM_CALLBACK_BASE` 配公网 https 地址；无公网时用 basicList 轮询兜底（详见 doc/07_配送平台对接.md「任务体系」）。

大屏主机装 Chrome / Edge 后，以管理员身份运行一次 `可视化大屏/deploy/安装开机自启.ps1`，注册登录自启计划任务，开机自动全屏打开大屏；看门狗脚本（`可视化大屏/deploy/看门狗.ps1`）同时守护后端与大屏进程（`README.md` §三）。

## 5. 管理员账号体系

### 5.1 背景与定位

管理员网页此前用「共享静态 ADMIN_TOKEN」鉴权——所有人同一把钥匙、无法区分操作者、也无法单独禁用某人。现改为**用户名 + 密码登录 → 签发随机 session token**（方案A）：`backend/services/adminAuth.js` 头注释。`/api/admin/*` 全部接口经 `adminGuard` 校验，能召唤/驻停机器人、开关舱门、清空活跃订单、读取出餐码（`domains/admin/routes.js` 路由清单）。

### 5.2 Session 机制

| 环节 | 实现 | 定位 |
|---|---|---|
| 密码哈希 | `adminAuth.js → hashPassword / verifyPassword` | Node 内置 `crypto.scrypt` 加盐哈希（16 字节随机盐，64 字节输出），存 `salt$hash`；校验用 `timingSafeEqual` 恒定时间比较，防时序侧信道 |
| 签发 | `adminAuth.js → issueSession` | 32 字节随机 hex token，写入 `admin_sessions` 表；`expires_at = datetime('now','localtime','+N days')`，默认 7 天（`ADMIN_SESSION_DAYS`），过期比较与鉴权同一时钟源 |
| 校验 | `domains/_shared.js → adminGuard` | 只认请求头 `x-admin-token`（已移除 `?token=` 查询串，避免令牌进访问日志/浏览器历史）；JOIN `admin_users` 且 `status=1` 才有效 |
| 吊销 | `adminAuth.js → revokeSession / revokeAllSessions` | 退出登录删单条；禁用账号 / 改密后吊销该账号全部 session，强制重新登录 |

登录接口 `POST /api/admin/login`（`domains/admin/routes.js`）：失败计数限流（`ADMIN_LOGIN_MAX=5` 次 / 10 分钟窗口，超限 429）；成功更新 `last_login_at`、签发 token 并落审计（`audit`）。配套接口：`/admin/me`（会话校验）、`/admin/logout`（吊销）、`/admin/password`（改密后吊销全部）。

### 5.3 tools/admin_user.js 用法（backend 目录下执行）

| 命令 | 说明 |
|---|---|
| `node tools/admin_user.js add --username admin [--password xxx] [--nickname 名称] [--gen]` | 创建账号；密码至少 8 位；`--gen` 自动生成 16 位强密码（去掉易混淆字符）并只打印一次 |
| `node tools/admin_user.js list` | 查看 id/用户名/昵称/状态/角色/创建/最后登录 |
| `node tools/admin_user.js disable --username admin` | 禁用（status=0），同时吊销该账号全部 session |
| `node tools/admin_user.js enable --username admin` | 启用 |
| `node tools/admin_user.js reset --username admin --password xxx [--gen]` | 重置密码并吊销全部 session，强制重新登录 |

### 5.4 启动守卫

`server.js` → 启动日志回调：`adminAuth.enabledCount(store)` 统计启用账号数；**非 demo 档若为 0 直接 `process.exit(1)` 拒绝启动**（提示运行 add 命令创建）；demo 档仅告警不阻断（`server.js` 注释：避免把机器人控制权交给整个校园网）。

## 6. WebSocket 实时推送

- 挂载：`server.js → push.attach(server, { validateToken })`，路径 `/ws`；实现为 Node 内置 `http.Server` 的 `upgrade` 事件 + 自实现 RFC6455 握手/帧编解码，**无第三方依赖**（`services/push.js` 头注释）。
- 方向：只做「服务端 → 客户端」单向广播；客户端仅需处理 ping/pong/close 保持连接健康，业务帧只接受订阅消息 `{type:'sub', topics:[...]}`（`push.js → attach` 内 onData）。
- 鉴权：upgrade 时校验 `Authorization: Bearer <token>`（兼容 `?token=`，便于排查）；`server.js → validateToken` 两路放行：① `admin_sessions` JOIN `admin_users`（管理员 session token，须未过期且 status=1）；② `users` 表 openid（普通登录 token）。
- 广播能力（`push.js`）：`broadcast`（全量广播，如新订单事件 `order_created` 触发商家端红点刷新）、`broadcastTopic`（按主题精准广播，如管理员实时地图只推 `admin/live`，不把高频位置刷给商家端/用户端）、`topicCount`（后台实时泵据订阅者数决定要不要费力抓取位置，零订阅自动跳过）。
- 资源上限（`push.js` 常量，防单连接顶爆单进程内存——该进程同时承担派车调度与平台回调接收）：

| 上限 | 值 | 说明 |
|---|---|---|
| `MAX_CLIENTS` | 200 | 并发连接上限，超出直接断开 |
| `MAX_FRAME_BYTES` | 64 KB | 单帧上限（业务帧仅几十字节的订阅消息，超限断开） |
| `MAX_BUFFER_BYTES` | 256 KB | 单连接接收缓冲上限，超限清理（防声明超大帧长持续发送把内存顶爆） |
| `IDLE_TIMEOUT_MS` | 10 分钟 | 空闲连接回收（半开连接不占驻 socket 与 clients 条目；客户端会自动重连） |

## 7. 构建产物（管理员网页分片构建）

`管理员网页/build.js` 把源码按数据域拆在 `js/parts/admin/*.js`（7 个 part）与 `js/parts/map/*.js`（5 个 part），运行时是**同一个闭包**——所有 part 拼进一个 IIFE，函数/变量跨文件引用与拆分前完全一致，行为不变。

- 拼接：`build.js → build()` 按 `TARGETS` 的 parts 清单（顺序即拼接顺序）把各小文件逐行拼回 `admin.js` 与 `admin-map.js`。
- 反向切分：`build.js → gen()`（`--gen` 参数）按 `CUTS`（每个输出文件各 part 的末行号边界，行号单调递增）从当前输出文件切回 parts，保证与输出逐字节等价。
- 约定：**只改 `js/parts/` 下的小文件，改完跑 `node build.js` 生效**；直接改了输出文件想重新拆一次时用 `--gen`。
- 为什么 parts 不能单独 `node --check`：每个 part 只是闭包的一段切片，会引用其它 part 里定义的函数/变量（如 `01-core.js` 定义的 `esc/log/toast/api/状态字典` 被后续 part 使用，`04-overview-ws.js` 等 part 顶部并无 require/声明），单独对某个 part 做语法检查必然报「未定义标识符」类错误；只有拼回完整输出文件后才能做整体语法检查与运行验证。
