## 二、待办清单

### P0 · 现场实测（唯一真正的阻塞项）

**为什么是阻塞项**：v2 所有时间参数（车速、每站等待、上货耗时）都是**模拟器估算值，不是实测值**。
「每趟 ≤15 分钟」这个约束直接由它们决定能装几站 —— 参数错 30%，结果就完全不同。

| # | 要测什么 | 怎么测 | 为什么关键 |
|---|---|---|---|
| 1 | **无人车真实平均车速** | 机器人上线后，用 `status_events` 里状态 60（去往取货点）→70（到达取货点）的时间差 ÷ 两点位距离。`status_events` 每 2.5 秒自动记录一次 | 直接决定一趟能跑几个点位 |
| 2 | **每站实际等待时长** | 状态 70 到达 → 用户实际取走（`picked_up_at`）的时间差，取多次的中位数 | 现在按 70 秒估算；提前提醒落地后预计能降到 40 秒左右 |
| 3 | **上货耗时** | 状态 30（到达上货点）→50（已上货） | 现在按 120 秒估算 |
| 4 | **提前提醒是否真的让人早下楼** | 对比启用前后的「站内等待时长」中位数 | 这是提前提醒唯一的价值来源 |

**填这里：**

```
实测日期：__________   测试批次：__________

① 平均车速        = ______ m/min   （原估计 60）
② 每站等待中位数  = ______ 秒      （原估计 70）
③ 上货耗时中位数  = ______ 秒      （原估计 120）
④ 启用提前提醒后每站等待 = ______ 秒
```

实测完成后：把 ① ② ③ 填进 `backend/.env`：

```ini
V2_SPEED_MPM=实际车速
V2_STOP_WAIT_SEC=实际每站等待
V2_LOADING_SEC=实际上货耗时
```

## 三、怎么开启 v2 / 怎么回滚

### 开启（三层，缺一不可）

```ini
# backend/.env
BATCH_V2_READY=true
BATCH_ALGO=v2
```

改完**必须重启后端**。启动日志会出现这一行才算成功：

```
[batch] BATCH_ALGO=v2 已生效：新组单算法（情况1/情况2 + 15分钟窗口 + 每趟≤15分钟）
```

若日志出现「已请求，但 BATCH_V2_READY 不是 true，本次运行仍走 legacy」= **没生效**，检查变量拼写。

### 回滚（三层保险，任选其一）

| 层级 | 方法 | 适用 |
|---|---|---|
| 🟢 环境变量 | `.env` 改成 `BATCH_ALGO=legacy`（或删掉这两行）+ 重启 | 日常，最快 |
| 🟡 代码 | `git checkout backup/batch-v2-before-20261005 -- backend/services/batch.js backend/domains/delivery/timers.js` | 代码改坏了 |
| 🔴 数据库 | 停后端 → 删 `lingdong.db` `-wal` `-shm` → 把 `lingdong.db.bak_before_batch_v2_20261005_215233` 复制成 `lingdong.db` → 重启 | 数据被改坏 |

> ⚠️ 数据库回滚**必须先停后端**。库是 WAL 模式，热删会丢数据。

## 四、关键参数表（全是估算值）

| 参数 | 默认 | 含义 | 是否有实测依据 |
|---|---|---|---|
| `V2_SPEED_MPM` | 60 | 车速（米/分钟） | ❌ 估算 |
| `V2_DETOUR` | 1.3 | 绕行系数（直线距离 ×1.3 = 实际路径） | ❌ 估算 |
| `V2_LOADING_SEC` | 120 | 上货耗时 | ❌ 估算 |
| `V2_STOP_SERVICE_SEC` | 30 | 每站停靠 + 开舱动作 | ❌ 估算 |
| `V2_STOP_WAIT_SEC` | 70 | 每站等用户取餐 | ❌ 估算 |
| `V2_PER_ORDER_OPEN_SEC` | 10 | 每多一单多花的开舱时间 | ❌ 估算 |
| `V2_MAX_TRIP_MIN` | 15 | 每趟行程上限 | ✅ 推导：承诺 30 分钟 = 攒单 15 + 行程 15 |
| `BATCH_MAX_ITEMS` | 12 | 单批件数上限 | ✅ 现有约束 |
| `BATCH_HOLD_MS` | 900000 | 攒单窗口（15 分钟） | ✅ 推导 |

| `BATCH_TOTAL_CARS` | 2 | 演示档的可用车数 | 真实环境走平台设备列表 |

## 五、端到端实测结果（2026-10-05，真实坐标）

24 单 / 9 个楼栋，2 台车：

| 指标 | v2 | legacy |
|---|---|---|
| 批次数 | 9 | 3 |
| 平均每批件数 | 3.7 | 11.0 |
| 平均站点数 | 2.6 | 7.3 |
| **平均行程** | **12.8 分钟** | **31.5 分钟** |
| **最长行程** | **14.9 分钟** | **34.6 分钟** |
| 超 15 分钟的批次 | 0 | **3 / 3** |
| 漏单 | 0 | 0 |

**结论**：legacy 严重违反 30 分钟承诺（最长 34.6 分钟，光路上就超了）；
v2 把行程压进 15 分钟内，代价是**车次变多**（9 趟 vs 3 趟）。

> 注意：这组数字验证的是**算法逻辑正确**，不是**参数正确** —— 参数仍是估算值。

## 七、已知问题与坑（接手必读）

### 1. 演示档下看不到真实的路线/站点 ⚠️

演示档（`RUN_MODE=demo`）里，订单在批次定型约 6 秒后会被 Mock 状态机**自动推进到「已送达」**。
此时 `route` 查询条件（订单状态 1/2）已无匹配 → 批次详情里的路线是空的。

**这是纯演示档现象，生产环境不存在。** 不要误判为 bug。

### 2. 演示档不隔离数据库

`RUN_MODE=demo` **不会**换数据库。要隔离必须同时给 `LINGDONG_DB=<临时库路径>`，
否则演示数据会写进真实库 `backend/data/lingdong.db`。

### 3. 全新数据库没有点位坐标

坐标只能靠平台 `landInfo` 同步。新库初始化会播一批 `pos=(0,0)` 的占位点位。
没有坐标时：行程距离恒为 0，ETA 退化成纯固定耗时 —— **v2 的行程约束会失效**。

已修：取值统一走 `batch.loadingPointOf()`，只认**有真实坐标**的点位。
（`domains/delivery/queries.js` 的 `loadingPointFirst` 有同样的隐患，影响地图渲染，暂未改动。）

### 4. 提前提醒依赖坐标

用户端横幅的「还有几站 / 约几分钟」在**没有坐标**的库上会算不准（距离项为 0）。
实车环境坐标齐全，正常。

### 5. 用户端没有推送通道

用户端**没有 WebSocket**（商家端有），订单状态靠追踪页**每 3 秒轮询**。
所以提前提醒做成了「后端算好 + 轮询读取」，**用户必须开着小程序才能看到**。
若要真正的微信服务通知，需要申请订阅消息模板 + 用户手动授权（见待办）。

## 九、附：模拟器结论（供参考，非实测）

离线模拟器在 `simulator/`（独立目录，不影响后端）。主要结论：

- **不限行程上限**：稳定期 37 趟 / 平均 4.7 站 / 超时 16~35 → **加上限明显更好**
- **最优上限**：随车速变化，60 m/min 时约 ≤15 分钟
- **午餐高峰**：2 台车即使最优参数也超 115 单以上 → 运力问题，非算法问题
- **每站等待上限**（阶梯）：60 秒 → 未取走 34.3%；120 秒 → 13.1%；180 秒 → 4.9%
- **提前提醒**（模拟）：超时 97 → 22，未取走 79 → 18，ETA 误差 P95 4.4 → 2.1 分钟

跑法：双击 `simulator/启动模拟器.bat`，或 `node simulator/simple.js`。
