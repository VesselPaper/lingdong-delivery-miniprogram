# 组单模拟器（simulator/）

离线仿真「订单到达 → 组单分批 → 排路线 → 无人车配送」，用**同一串订单流**对比不同分批算法。
你把你的规则（15 分钟窗口 + 情况1/情况2 分支）和现有实现（best-fit + 90 秒）放进同一个模型里跑，
差异就只来自算法本身，不再靠争论。

## 一、它在哪里、会不会动到现有项目

```
simulator/
  README.md              本文档
  simple.js              人话版：填几个数字 → 直接给「好 / 不好」
  简单版.bat             双击 = 人话版交互式
  run.js                 命令行入口（完整对比）
  启动模拟器.bat         双击 = 完整对比
  lib/config.js          默认值、场景预设、参数解析
  lib/rng.js             确定性随机数（同 seed 必得同订单流）
  lib/generate.js        订单流生成（到达率 / 楼栋分布 / 每单件数）
  lib/route.js           站点路线（与 backend/services/batch.js planRoute 同语义）
  lib/engine.js          仿真引擎（离散时间步 + 车队调度）
  lib/strategies.js      四种分批策略
  lib/report.js          指标统计 + 文本报告
```

## 一之二、只想看「好还是不好」→ 用人话版

`simple.js` 不发大表、不讲策略，只回答一个问题：**你这组设置跑下来，好还是不好？**

```bash
node simulator/simple.js                    # 交互式，问你 5 个数字（一路回车 = 默认值）
node simulator/simple.js 15 2 271 8 30      # 锁定分钟 车数 订单数 小时数 承诺分钟
```

也可以直接编辑 `simple.js` 顶部那个「设定」块里的数字（含判定门槛），改完重跑即可。
双击 `simulator/简单版.bat` 等于跑交互式。

它会告诉你：锁定时间 / 车数 / 订单量 / 一趟跑几个楼栋 / 一辆车跑几趟 / 全程多久 /
用户等多久 / 超时几单 / **结论 ✅好 ⚠️凑合 ❌不好**（附逐条对照），
外加「换几组订单流还成立吗」和「锁定时间该填多少」的扫描表。

**完全独立：**

- 零依赖 —— 只用 Node 内置模块，不需要 `npm install`
- 不 `require` `backend/` 下任何文件
- 不读写真实数据库（`backend/data/lingdong.db` 一个字节都不碰），订单全部现场生成
- 不改动任何既有文件 —— 删掉整个 `simulator/` 目录即可完全回退

参数默认值只是"抄"了真实系统的常量（容量 12、90 秒、15 分钟、30 分钟承诺），改的是副本，不是原代码。

## 二、怎么用

> **先确认你在哪个目录。** 下面命令按「**在项目根目录 `lingdong-delivery` 下执行**」写。
> 如果你已经 `cd simulator` 进去了，把所有 `simulator/run.js` 换成 `run.js` —— 否则会去找
> `simulator/simulator/run.js`，报 `Error: Cannot find module ...\simulator\simulator\run.js`。

也可以直接双击 `simulator/启动模拟器.bat`（不带参数跑默认场景；也可以带参数：`启动模拟器.bat --all-scenarios`）。

```bash
node simulator/run.js                          # 默认场景，四种策略同台对比
node simulator/run.js --all-scenarios          # 跑遍所有预设场景
node simulator/run.js --help                   # 全部参数

node simulator/run.js --scenario lunch         # 午高峰
node simulator/run.js --scenario rush          # 极端过载
node simulator/run.js --strategy theirs        # 只看你的规则
node simulator/run.js --json                   # 输出 JSON，便于画图/二次处理
```

验证你规则里的两个歧义点（默认值就是"按你原话最自然的读法"）：

```bash
node simulator/run.js --strategy theirs --timer window       # 情况2 = 滚动 15 分钟窗口（默认）
node simulator/run.js --strategy theirs --timer perOrder     # 情况2 = 按批计时
node simulator/run.js --strategy theirs --count openOnly     # 分支口径 = 只数未定型批次（默认）
node simulator/run.js --strategy theirs --count allPending   # 分支口径 = 未定型 + 待上货
node simulator/run.js --strategy theirs --carmode idle       # 车数 = 当前空闲车（默认 static = 车队总数）
```

做敏感性测试（**这是这个模拟器最有价值的用法**）：

```bash
node simulator/run.js --strategy theirs --window 3     # 换窗口长度
node simulator/run.js --strategy theirs --window 8
node simulator/run.js --strategy deadline --minwait 4  # 换"车驱动"等待时长
node simulator/run.js --scenario lunch --seed 33       # 换订单流
node simulator/run.js --coords                         # 打开楼栋坐标（规则3 生效）
```

## 三、参数

| 参数 | 默认 | 含义 |
|---|---|---|
| `--scenario` | `steady` | 预设场景：`steady` / `lunch` / `offpeak` / `lowdensity` / `rush` |
| `--all-scenarios` | — | 依次跑遍全部场景 |
| `--strategy` | 全部 | `current,theirs,adaptive,deadline` 任选 |
| `--hours` | 8 | 收单时长（小时）；之后继续仿真到全部送完（最多再 `--tail` 分钟） |
| `--rate` | 36 | 到达率（单/小时） |
| `--cars` | 2 | 无人车数量 |
| `--capacity` | 12 | 单批件数上限（= `BATCH_MAX_ITEMS`） |
| `--window` | 15 | 你规则里的固定窗口（分钟） |
| `--adaptlow` / `--adapthigh` | 3 / 12 | `adaptive` 策略低/高负载时的窗口 |
| `--promise` | 30 | 承诺送达 = 下单 + N 分钟（= 用户端 `asapEta`） |
| `--minwait` | 1.5 | `current` 的超时定型（90 秒）、`deadline` 的车驱动最小等待 |
| `--buffer` | 4 | `deadline` 策略的安全缓冲（分钟） |
| `--timer` | `window` | `theirs` 情况2 的读法 |
| `--count` | `openOnly` | `theirs` 分支口径 |
| `--carmode` | `static` | `theirs` 车数口径 |
| `--loading` / `--travel` / `--stop` | 120 / 90 / 60 | 上货、站间行驶、每站服务耗时（秒，无坐标时用） |
| `--speed` | 60 | 有坐标时的车速（米/分钟） |
| `--coords` | 关 | 启用楼栋坐标：路线走最近邻 + 单数加权，规则3 生效 |
| `--alpha` | 0.5 | `planRoute` 的单数权重 α |
| `--seed` | 20261001 | 随机种子 |
| `--tick` | 5 | 仿真步长（秒） |
| `--json` / `--quiet` | — | 输出 JSON / 静默 |

## 四、四种策略分别是什么

| 策略 | 放置（订单→批次） | 定型（发车） | 出处 |
|---|---|---|---|
| `current` | best-fit：装得下且最满的批次，**无楼栋维度** | 满 12 件 或 成立超 90 秒 | `backend/services/batch.js` + `delivery/timers.js` 现有实现 |
| `theirs` | 同楼栋（选最满）→ 就近楼栋 → 按时序填空位 | 满 12 件；情况1 按 15 分钟计时；情况2 滚动窗口锁定 | **你给的规则** |
| `adaptive` | 与 `theirs` 完全相同 | 满 12 件 或 到自适应窗口（低负载 3 分、高负载 12 分） | 对照用：只把"固定 15 分钟"换成随负载滑动 |
| `deadline` | 与 `theirs` 完全相同 | 满 12 件 或 到最晚发车时刻 或 车驱动 | 对照用：把固定窗口换成 `min(承诺送达) − 行程 − 缓冲` |

### 你规则里没写、由我补上的假设（标 ★，都可改）

1. **★ 放不下就新建批次** —— 你的规则没写，但不写会把订单丢掉。
2. **★ 什么时候发车** —— 你的规则只写了"计时"，没写计时到点之后怎样。这里按最自然读法：**计时到点即定型发车，装满 12 件必发**。`--window` 就是那个计时长度。
3. **★ 规则3 需要坐标** —— 楼栋间距要用 `x/y` 算，而真实库里 10 个点位坐标**全是 (0,0)**，规则3 实际不生效。要用它得先 `POST /api/merchant/landmarks/sync` 同步真实坐标。
4. **★ 分支不判抖动** —— `情况1 ↔ 情况2` 每个 tick 都重新判一次，没有滞回。规则里也没写临界值该往哪边归。
5. **★ 派车与定型解耦** —— 定型不等于有车。定型后要排队等空闲车（对齐真实系统 `pickAvailableRobot` / `isRobotBusy` 的门禁）。可用 `--lockneedsCar` 改成"没车不许定型"。
6. **★ 无坐标时的路线** —— 退化成"单数多的先送"，和 `planRoute` 的退化分支一致（当前真实系统就是走这条）。

## 五、指标定义

| 指标 | 含义 |
|---|---|
| 趟数（批次数） | 一共发了多少趟 —— 直接对应车的行驶成本 |
| 载货率 | 总件数 ÷ (趟数 × 12) —— 每趟装得多满 |
| 总停靠次数 / 平均停靠/趟 | 开关舱门的次数 —— 你关心的"取货点"成本 |
| 单楼栋批次占比 | 一趟只服务一个楼栋的比例 —— **同楼栋最大化的直接度量** |
| 平均等待 / 中位数 / P95 / 最长 | 下单 → 送达的时长 |
| 超时单数 / 超时率 | 送达时刻晚于"下单 + 30 分钟"的单数 |
| 实际−承诺 | 平均而言比承诺早/晚多少（负 = 比承诺早，说明承诺偏保守） |
| 等待标准差 | 到达时间的稳定程度，越小越可预期 |
| 车辆利用率 | 车在跑的时间 ÷ (车数 × 仿真时长) —— **超过 ~85% 就说明系统贴着崩溃边缘** |
| 未送达 | 仿真结束时还没送完的单数（正常应为 0） |

`run.js` 每次都会跑一遍**不变量校验**：批次件数 ≤ 容量、件数合计守恒、送达不早于下单、订单不丢。校验不过直接报错退出，不给你看可疑的数字。

## 六、建模假设与局限（请先读这段再信数字）

1. **楼栋坐标是虚构的示例值**（`lib/config.js` 里的 `LANDMARKS`，单位米）。真实坐标同步下来之前，`--coords` 模式下的绝对数字只能看**机制和趋势**，不能当结论。
2. **行程耗时是常量**（默认每站 90 秒 + 每站服务 60 秒 + 上货 120 秒）。真实值请用一趟真实配送的日志校准；这组常量直接决定"载货率低是否会拖垮车队"，是最敏感的旋钮。
3. **没有建模**：电梯/门禁等待、用户取餐延迟、商家出餐延迟、退货、订单取消、车故障、平台限流、电量。
4. **订单流是离散化泊松过程**（每个 tick 以 `rate × tick` 的概率来一单），楼栋按权重独立抽。
5. **承诺时间是固定的 +30 分钟**，不随系统状态动态调整（与当前产品一致）。
6. 一单一单送 / 召唤多单配送这两种模式对组单结果无影响，未建模。

## 七、实测结论（seed 20261001，2 台车，无坐标）

### 常态 36 单/时（8 小时，271 单 / 389 件）

| 指标 | current | theirs | adaptive | deadline |
|---|---|---|---|---|
| 趟数 | 136 | **37** | 55 | 110 |
| 载货率 | 23.8% | **87.6%** | 58.9% | 29.5% |
| 平均停靠/趟 | 1.8 | 4.8 | 3.6 | 2.1 |
| 单楼栋批次占比 | **42.6%** | 0.0% | 9.1% | 35.5% |
| 平均等待 | 9.4 分 | 13.6 分 | 11.5 分 | **7.3 分** |
| 等待 P95 | 15.8 分 | 25.2 分 | 19.7 分 | **12.7 分** |
| 超时单数 | 0 | 1 | 0 | 0 |
| 车辆利用率 | **88.9%** | 52.3% | 61.0% | 81.2% |

换 5 个种子复跑：`current` 平均等待 11.1~23.5 分、超时 0~56 单；`theirs` 平均等待 14.0~14.7 分、超时 0~3 单。

**读法**：现有实现把车用到 89%，处在"随时崩"的边缘，所以换个种子就偶尔崩出几十单超时；你的规则把利用率降到 52%，换来的是稳定，代价是低峰时每人多等约 4 分钟。

### 午高峰（第 2~3 小时到达率 ×3，339 单）

| 指标 | current | theirs | adaptive | deadline |
|---|---|---|---|---|
| 趟数 | 145 | **45** | 58 | 93 |
| 平均等待 | 46.7 分 | 17.7 分 | 16.8 分 | 18.8 分 |
| 超时单数 | **237（70%）** | 35 | 37 | 89 |

5 个种子下 `current` 超时 227~289 单，`theirs` 2~88 单 —— 差距稳定存在。

**读法**：高峰时现有实现**必然崩**（70% 超时），根因不是策略细节，而是载货率只有 24% 导致车队吞吐量只有需求的 1/3。这时你的"攒满一车再发"是唯一出路。

### 低峰 12 单/时（76 单）

窗口长度敏感性（`theirs`）：

| 窗口 | 1 分 | 3 分 | 8 分 | 15 分 |
|---|---|---|---|---|
| 趟数 | 62 | 52 | 33 | 23 |
| 平均等待 | 5.0 分 | 6.8 分 | 10.5 分 | **16.1 分** |
| 平均停靠/趟 | 1.2 | 1.3 | 2.0 | 2.7 |

**读法**：低峰时 15 分钟窗口是**纯亏** —— 车本来就闲着，白让用户多等 11 分钟，而且每趟停靠数还更多（攒的单越多，12 件里必然掺进更多楼栋）。

### 高峰窗口长度敏感性（`lunch`）

| 窗口 | 1 分 | 3 分 | 8 分 | 15 分 |
|---|---|---|---|---|
| 趟数 | 172 | 101 | 56 | 45 |
| 平均等待 | 55.7 分 | 22.4 分 | 16.4 分 | 17.7 分 |
| 超时单数 | 235 | 117 | **34** | 35 |

**读法**：高峰确实要长窗口，但**8 分钟已经吃到全部收益，15 分钟没有额外好处** —— 拐点在 8 分钟左右。

### 结论

1. **你的方向是对的**：`current` 载货率 24%、利用率 89%，贴着崩溃边缘；高峰必崩。攒批提高载货率是唯一出路，这点数据完全支持。
2. **但"固定 15 分钟"这个数字不对**：低峰纯亏（多等 11 分钟），高峰 8 分钟就已到顶。窗口应当随负载动，不是常数。
3. **"同楼栋最大化"没有兑现**：`theirs` 的单楼栋批次占比是 **0%**，每趟停靠 4.8 个点，比现有实现的 1.8 个还多。因为窗口一长，12 件装进来必然跨更多楼栋。真正减少总停靠次数的是"攒满一车"，不是"同楼栋优先"。
4. **情况1/情况2 分支基本是死代码**：按你原话的口径（未定型批次数 vs 车队总数），`情况2` 触发率 **0.0%**。只有把口径改成"未定型+待上货 vs 当前空闲车"才会触发 16%。分支条件里没算在途/待上货的车，也没算空闲车，所以它判的永远偏乐观。
5. **规则3 在当前数据下是空转**：真实坐标全是 (0,0)。即使喂上虚构坐标复跑，`theirs` 的趟数/停靠数与无坐标时**一模一样**（37 趟 / 178 停靠）—— 因为候选批次通常只有一个，没有"选更近"的余地。
6. **过载时无解**：`rush` 场景（120 单/时、2 台车）四种策略平均等待 144~198 分钟、超时 864~878 单。加车比改算法有用。
7. **推荐形态**：`deadline`（满 12 件 / 到最晚发车时刻 / 车有空且已等够）在常态下平均等待 7.3 分、P95 12.7 分、超时 0，全面优于固定窗口；`--minwait 4` 时在高峰把超时从 35 单压到 27 单。它只有一个发车判据，没有分支，也不需要在低峰/高峰之间切参数。

## 八、下一步怎么校准

想让数字变成可信的决策依据，按优先级做三件事：

1. **量一趟真实配送**：上货多久、站间多久、每站停多久 → 填 `--loading / --travel / --stop`（或 `--speed` + 真实坐标）。这是最敏感的一组参数。
2. **同步楼栋真实坐标**：`POST /api/merchant/landmarks/sync`，再把结果填回 `lib/config.js` 的 `LANDMARKS`。之后 `--coords` 才有意义，规则3 也才可评。
3. **统计真实订单流**：一天的订单数、时段分布、楼栋分布、每单件数 → 填 `--rate` / `peaks` / `landmarkWeights` / `itemsDist`。

校准完之后，用 `--all-scenarios` 出一张表，再决定窗口/发车判据的参数。要加新策略（例如"窗口自适应 + 破段保超时"），在 `lib/strategies.js` 里加一个工厂函数并登记到 `FACTORIES` 即可，其余不用动。
