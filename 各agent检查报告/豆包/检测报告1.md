# 检测报告 1：真实业务合理性检查

> 检查对象：送餐无人车微信小程序（用户端 + 商家端 + Node 后端 + robox 开放物流平台对接）
> 检查时间：2026-09-06
> 检查范围：README.md、交接文档.md、真实上线所需功能书.md、doc/01~07、backend 全部源码（server.js / db.js / services/*）
> 检查方法：以「模拟开关全部关闭、真实业务全量启用」（真实微信登录 / 真实支付 / 真实退款 / 真实扫码 / 真实机器人配送）为假设前提，逐链路审查业务模型、资金流、状态机、数据一致性、权限与安全。
> 结论：**业务闭环设计完整，但存在 6 项高危问题、9 项中危问题，均集中在「模拟→真实」切换点，直接决定能否商用。**

---

## 0. 结论摘要

| 级别 | 数量 | 一句话概括 |
| --- | --- | --- |
| 🔴 高危 | 6 | 身份与资金链路在真实环境下存在冒充、伪造、资金不一致风险 |
| 🟠 中危 | 9 | 状态机语义、库存/销量口径、批次与组单策略在真实业务下失真 |
| 🟡 低危/建议 | 10 | 体验细节、数据口径、合规与运营补强项 |

最核心的三条判断：
1. **"钱"与"身份"一旦接通，现有鉴权与退款模型撑不住**——商家身份可自选、token 即 openid 明文、退款只改本地状态。
2. **"订单状态"与"物理现实"存在偏差**——机器人"到达即结算销量"、"接单即置配送中"、"开舱即完成"，在真实取餐失败、用户不取餐等场景下账实不符。
3. **一车多单的组单参数（90s 派车）与容量口径（按件数）与真实运营矛盾**——几乎无法实现"一车多单"的成本价值。

## 1. 🔴 高危问题（上线前必须修复）

### H1 商家身份可自选，无审核——任何人可成为商家并控制真实机器人
- **位置**：`server.js` 登录接口 `const roleVal = role === 'merchant' ? 'merchant' : 'student'`
- **现象**：`role` 由客户端传入，任意微信用户登录时传 `role=merchant` 即获得商家权限，可操作全部 `/api/merchant/*`，包括**给真实机器人开舱门、派发配送、同意退款**。
- **真实业务影响**：学生可冒充商家发起配送、同意自己的退款、把批次绑定到任意机器人，资金与设备安全失控。
- **建议**：商家账号需线下白名单/审批制（如商家表绑定 openid 或邀请码）；登录接口对 merchant 角色做服务端校验，禁止客户端自选。

### H2 token 即 openid 明文，无过期、无会话管理
- **位置**：`server.js` 登录返回 `token: user.openid`；`auth` 中间件直接用 `Authorization` 头里的 token 查 users 表
- **现象**：微信 openid（真实身份标识）直接作为长期有效 token 传输并存储在前端 storage；无过期时间、无撤销机制、无设备绑定。
- **真实业务影响**：openid 出现在日志/数据库/请求头任一泄露点，即等于账号永久被盗；用户换设备、退出登录均无法真正吊销。
- **建议**：服务端生成随机 session token（带过期与续期），建 session 表关联 openid；登录接口不返回 openid 明文。

### H3 平台回调接口无鉴权，可伪造配送状态
- **位置**：`server.js` `/api/platform/callback/delivery`、`/api/platform/check-order`（均无鉴权、无签名校验）
- **现象**：任何能访问到该 URL 的人可直接 POST 一个 `taskId + taskStatus=70/80` 把订单置为已送达/已完成。
- **真实业务影响**：伪造"已送达"诱导用户取餐失败纠纷；伪造"已取消"导致订单作废、库存回补；伪造"任务完成"使批次提前完成。
- **建议**：回调加签名校验（HMAC 或平台 token 头），并核对回调中 deviceSn/任务归属；公网部署后至少做来源 IP/凭据校验。

### H4 取消/退款不联动平台任务，机器人仍会继续配送
- **位置**：`server.js applyOrderCancelled()`（只改本地 `delivery_tasks.task_status=110`，无任何平台调用）；`platform.js` 无任务取消/关闭接口
- **现象**：用户免费窗口内取消、商家同意取消申请、异常退款时，平台侧任务未主动取消。文档自述"回调未配 → 取消/退款强制关平台任务机制失效"。
- **真实业务影响**：机器人照样去上货、去配送已取消订单 → 货损、空驶、用户纠纷；若平台把货送到无人认领点位，批次卡死。
- **建议**：实现并调用平台任务取消/关闭接口（或通过 check-order forceCloseTask 在配置回调后依赖设备端执行，需真机验证）；取消流程加"先关平台任务、再改本地状态"的顺序与重试。

### H5 测试接口在真实模式下无条件暴露，可一键造假
- **位置**：`server.js` `/api/merchant/device/batch/mock-dispatch`（无 PLATFORM_MOCK 判断）、`/api/merchant/delivery/test-complete`（无条件可用）
- **现象**：真实模式下商家仍可调用 mock-dispatch 把批次伪造为"配送中→10 秒后送达"，test-complete 可把任意订单伪造为已送达/已完成。
- **真实业务影响**：商家可不下发真实配送直接收钱；操作失误（点错按钮）会造成订单假完成、用户取不到餐。
- **建议**：两个接口加 `process.env.PLATFORM_MOCK === 'true'` 守卫或直接按功能书删除；上线前用开关强制禁用并回归验证。

### H6 支付回调不校验金额一致性；真实退款未实现且部分退款与库存回补矛盾
- **位置**：`server.js` `/api/pay/notify`（仅取 `out_trade_no` + `trade_state`，不比对回调金额）；`wxpay.js decryptNotify`（未验证微信签名头）；`server.js` 售后 `approve`（amount 仅校验 ≥0，无上限、无原路退回）；`goodsStats.restoreStock`（按订单全部数量回补）
- **现象**：
  1. 回调只按订单号置已支付，不核对 `amount.total` 与订单 `total_amount` 是否一致；
  2. 未校验微信签名头（Wechatpay-Signature/Timestamp/Nonce/Serial）；
  3. "同意退款"只把订单置 7，不调微信退款接口；商家可填任意金额（可超实付）；
  4. **部分退款**时 `restoreStock` 仍按整单数量回补库存（已售商品被回补，账实不符）。
- **真实业务影响**：金额不一致回调被错误确认收款；退款不到账用户投诉；部分退款导致库存虚增、财务对不上。
- **建议**：回调校验金额+签名；退款实现微信原路退回（先退款成功再改状态），amount 上限=实付金额；按退款比例/退货状态回补库存。

## 2. 🟠 中危问题（真实业务下功能失真）

### M1 未支付订单无超时关单，库存被无限占用
- **位置**：`server.js /api/order/create` 下单即扣库存；订单 status=0 无任何超时扫描
- **现象**：用户下单不支付，库存一直占用；恶意用户可批量下单锁死商品库存，真实商家无法出货。
- **建议**：待支付订单超时（如 15~30 分钟）自动置取消并回补库存；支付页提示剩余时间。

### M2 下单流程非事务，异常时订单与库存不一致
- **位置**：`server.js /api/order/create`（INSERT orders → 循环扣库存，无事务包裹）
- **现象**：扣库存中途异常（磁盘/约束错误），订单已存在而库存未扣，或反之。
- **建议**：用 SQLite 事务（BEGIN/COMMIT/ROLLBACK）包裹「建单+扣库存+清购物车」。

### M3 机器人"到达取餐点"即结算销量，用户尚未取餐
- **位置**：`platform.js applyStatus`：`if (orderStatus === 3 || orderStatus === 4) settleSales`
- **现象**：任务 70 到达 → 订单 3 已送达 → 立即 `goods.sales += 数量` 并置 `goods_settled=1`。此时用户可能不取餐、取餐失败或退款，销量不可回滚、库存不回补。
- **真实业务影响**：销量虚高（列表按销量排序，商家被误导）；未取餐退款后库存不恢复，商品实际还能卖但系统显示已售。
- **建议**：销量结算时机改为"确认取餐/任务 80 完成"（用户真正拿到餐），或与退款路径联动回滚。

### M4 自动派车窗口 90 秒，一车多单名存实亡
- **位置**：`batch.js BATCH_WAIT_MS = 90 * 1000`；`server.js` 自动派车扫描
- **现象**：自动接单模式下批次成立 90 秒即自动派车。真实校园下单分散，90 秒内几乎不可能凑满 12 单/12 件。
- **真实业务影响**：绝大多数批次 1~2 单即发车 → 一车一单、空驶率高，一车多单的摊薄成本价值完全丢失；商家手动派车可缓解但违背自动化的初衷。
- **建议**：组单窗口改为分钟级（如高峰 3 分钟 / 平峰 10 分钟）或按单量触发（≥3 单才发车）；容量上限与窗口做成可运营配置。

### M5 购物车结算后全量清空，未选中的商品也被删除
- **位置**：`server.js /api/order/create`：`DELETE FROM cart WHERE user_id=?`
- **现象**：用户购物车勾选部分商品结算，下单后**整个购物车**被清空，未勾选商品丢失。
- **建议**：只删除本次下单的 cart id 列表（前端传 id 或后端按 goods_id 删）。

### M6 "预约送达时间"只有 UI，无后端支撑
- **位置**：`用户端/pages/order/confirm.js`（指定时间选择、30 分钟一档）；`db.js orders` 表无任何送达时间字段；下单接口无对应参数
- **现象**：用户选"2 小时后送达"，订单立即组单、按 90s 窗口派车配送，完全无视预约时间。
- **真实业务影响**：功能是"假"的；用户按预约时间到点位，餐早已到或还没到，产生纠纷。
- **建议**：要么移除预约时间 UI，要么后端加 `expect_arrive_at` 字段并在派车/组单时按时间排序。

### M7 商家扫码绑定设备无校验，扫错机器人会错绑批次
- **位置**：`server.js /api/merchant/device/scan`：按 deviceSn 找不到待上货批次时，**直接取最早待上货批次并改写 device_sn**
- **现象**：商家扫到任意一台机器人的码（或输错编号），会把整个批次绑定到该设备并尝试开舱。
- **真实业务影响**：把货装进错误的车、开错舱门、控制权冲突（平台 DLV_CTRL_0007 设备正在被使用）。
- **建议**：扫码必须校验"该设备空闲/在附近/与该批次派车设备一致"；不匹配则报错而非静默换批次。

### M8 订单状态 2"配送中"语义失真——接单即置配送中
- **位置**：`batch.js addOrderToBatch`：接单并入批次即 `status=2`（配送中），此时未派车、未上货
- **现象**：用户端"配送中"tab 会看到一批尚未派车、尚未上货的订单；状态机里 2 既表示"组单中/待上货"又表示"配送中"。
- **真实业务影响**：用户以为餐在路上，实际商家还没装车；投诉与沟通成本高。
- **建议**：状态机拆分（如 2=已接单组单中、3=配送中、4=已送达……）或统一用批次状态+stage_text 表达，保证用户端展示口径一致。

### M9 批次详情混入已摘除/已取消订单，计数与列表不一致
- **位置**：`batch.js getBatchDetail`：`SELECT * FROM orders WHERE batch_id=?` 无状态过滤；`removeOrderFromBatch` 不清理订单的 batch_id
- **现象**：订单取消/异常重配摘除后仍出现在旧批次详情列表；total_orders 动态统计含已取消单，与 total_orders 字段口径打架。
- **真实业务影响**：商家上货时看到已取消订单的货，误装；批次完成判断被干扰。
- **建议**：getBatchDetail 过滤 `status IN (2,3,4)`（与 maybeCompleteBatch 口径一致）。

## 3. 🟡 低危 / 建议项

| # | 问题 | 位置 | 建议 |
| --- | --- | --- | --- |
| L1 | 取餐码 4 位纯数字，无同批次碰撞检查（约 0.7% 碰撞率/批） | `server.js` 取餐码生成 | 生成时校验本批次/本设备唯一，或扩到 5~6 位 |
| L2 | 取餐页 40s 自动关舱，一车多单 12 份餐找餐时间紧张 | 取餐页倒计时 | 按单量延长窗口或允许用户主动延时 |
| L3 | 已送达(3)订单无"不取餐超时"处理，机器人驻留点位阻塞批次 | 状态机/批次 | 增加超时回收（退回上货点/标记异常）并通知商家 |
| L4 | 收餐手机号在下单时写入 users.profile，覆盖用户设置资料 | `confirm.js` 调 `PUT /api/user/profile` | 下单收餐人信息不应写进账号资料，与地址绑定即可 |
| L5 | 金额用浮点累加（`g.price*quantity`），应全程用分（整数） | `server.js /api/order/create` | 金额计算改为整数分，入库分转元 |
| L6 | 演示账号（demo_*）数据未清理；切换真实登录后老用户 openid 变化、历史订单断裂 | 登录接口/DB | 上线前迁移映射或清理演示数据 |
| L7 | 生产 config 未配置：双端 `config.js` prod 仍为 `http://localhost:3000/api`，真机需 HTTPS+白名单 | 双端 utils/config.js | 上线前配置正式域名并验证合法域名 |
| L8 | 单门店模型：shops 固定 id=1，多商家/多店铺场景不支持 | 数据库设计 | 若未来多商家，shops 按商家 openid 隔离 |
| L9 | 批次容量按"件数"计（12 件），真实仓容应按体积/重量/餐盒规格 | batch.js BATCH_MAX_ITEMS | 引入商品体积/重量系数，容量=Σ占用 |
| L10 | 平台点位/货舱参数未经真机验证：stockType=1 中舱、priority 递减排程、同设备多任务 | platform.js | 按交接文档待办完成真机验收后再商用 |

## 4. 模拟→真实切换检查清单（代码层面）

| 开关/代码 | 当前状态 | 上线前动作 |
| --- | --- | --- |
| `PAY_MOCK=true` | 存在 | 删除开关；接通微信支付商户 |
| 演示登录（demo_ 哈希） | 默认启用 | 取消注释启用 code2session，配置 WX_APPID/WX_SECRET |
| 真实退款 | 未实现（仅本地标记） | 实现微信退款接口，先退款成功再改订单状态 |
| `mock-dispatch` / `test-complete` | 真实模式可用 | 加 MOCK 守卫或删除（H5） |
| 取餐开/关舱 `test:true` 兜底 | 存在 | 无真实任务时禁止本地完成 |
| `PLATFORM_CALLBACK_BASE` | 为空 | 配置公网 HTTPS 回调地址（云服务器/cloudflared） |
| 回调鉴权 | 无 | 加签名/IP 校验（H3） |
| 商家身份 | 自选 | 白名单审批（H1） |

## 5. 优先级建议

1. **第一批（资金与身份安全，商用前提）**：H1 商家审核、H2 token 会话化、H6 支付金额校验+真实退款、H3 回调鉴权。
2. **第二批（配送真实闭环）**：H4 任务取消联动、H5 测试接口封禁、M7 扫码校验，配合真机验证"一车多单多地点配送顺序"。
3. **第三批（业务口径与体验）**：M1 超时关单、M3 销量结算时机、M4 组单窗口、M8 状态语义、M6 预约时间（二选一），以及 L 类低危项。

> 备注：本报告基于静态代码审查与文档核对，未对真实机器人/真实支付做端到端验证；"真机多地点配送顺序、平台对同设备多任务支持、仓容与取餐策略"等平台侧行为需按交接文档第 7 节待办完成实机验收后方可下结论。
