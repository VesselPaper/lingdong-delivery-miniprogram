# 检测报告 1：真实业务合理性检查

> 检查对象：送餐无人车微信小程序（用户端 + 商家端 + Node 后端 + robox 开放物流平台）
> 检查时间：2026-09-06
> 检查范围：README、交接文档 1/2、真实上线所需功能书、doc/01~07、backend（server.js / db.js / services/*）、双端下单/上货关键页
> 检查前提：**模拟开关全部关闭，真实微信登录 / 真实支付 / 真实退款 / 真实扫码 / 真实机器人配送全部启用**，按校园商用试点审查业务模型、资金流、状态机、数据一致性、权限与设备安全。
> 方法：文档对照 + 源码静态审查（未做真机/真实支付端到端）。
> 结论：**业务闭环在演示层是完整的，但按真实商用启用后，身份、资金、收餐人、自动接单、上货开关、库存回补均存在会直接出事的断点。建议上线前先修高危项，再做真机验收。**

---

## 0. 结论摘要

| 级别 | 数量 | 一句话概括 |
| --- | --- | --- |
| 高危 | 8 | 钱、身份、收餐人、自动接单、测试后门在真实模式下不可用或可被滥用 |
| 中危 | 11 | 状态机/组单/库存/路径/仓容与真实运营口径不一致 |
| 低危/建议 | 10 | 部署、合规、体验与数据口径补强 |

最核心的三条判断：

1. **接通真实支付后，自动接单会失效，取消/售后也不会把钱退回去。** 支付回调里用的仍是「待支付」内存对象；取消与同意退款只改本地状态。
2. **用户在确认页填的收餐人/手机号不会写入订单。** 订单联系人取的是下单前的用户资料，而资料更新发生在建单之后；平台开舱校验用的是订单手机号，真实取餐可能对不上。
3. **商家端上货页 `DEVICE_MOCK = true` 写死，真实模式下仍走 10 秒模拟送达。** 后端即使连正式平台，商家点「立即配送」也不会真的开舱/派发。

## 1. 高危（上线前必须修）

### H1 真实支付回调不会触发自动接单

- **位置**：`backend/server.js` `POST /api/pay/notify`；对比 `POST /api/order/pay` 的 `PAY_MOCK` 分支
- **现象**：Mock 支付会先把订单改成 status=1，再重新查出订单调用 `maybeAutoAccept`。真实回调则是：

```js
if (order && order.status === 0) {
  store.prepare("UPDATE orders SET status=1 ...").run(order.id)
  maybeAutoAccept(store, order)  // 此处 order.status 仍是 0
}
```

`maybeAutoAccept` 入口条件是 `order.status === 1`，因此**真实微信支付成功后永远不会自动接单并入批次**，订单停在「待接单」。
- **真实业务影响**：店铺已开自动接单，高峰期商家以为系统会组车，实际所有已付款订单堆积；餐做好了没人派车。
- **建议**：回调更新库后必须 `SELECT` 最新订单再调用 `maybeAutoAccept`；支付接口与回调共用同一套「已支付 → 自动接单」函数。

### H2 确认页收餐人未写入订单，平台开舱可能校验失败

- **位置**：用户端 `pages/order/confirm.js` `submit()`；`server.js` `/api/order/create`
- **现象**：确认页校验了姓名、手机号，但建单请求只传 `landmark_id / landmark_name / remark / items`。后端写入的是 `req.user.nickname`、`req.user.phone`。资料更新 `PUT /api/user/profile` 发生在**建单之后**，且是 fire-and-forget。
- **真实业务影响**：
  - 替同学代点、改收餐手机号，订单上仍是旧昵称/旧号；
  - 平台 `unloadingVerify` 使用 `order.contact_phone` + 取餐码，手机号对不上则开不了舱；
  - 商家贴标、电话联系取餐人都是错的。
- **建议**：下单接口必收 `contact_name`、`contact_phone`（后端再校验手机号），写入 `orders`；不要用账号昵称顶替收餐人；资料页与下单联系人分离。

### H3 已付款取消/同意退款不走微信原路退回；库存回补也非幂等

- **位置**：`applyOrderCancelled`；`POST /api/merchant/refund/handle`；`POST /api/merchant/order/exception/refund`；`goodsStats.restoreStock`；`wxpay.js`（无退款 API）
- **现象**：
  1. 免费窗口内取消已支付订单：只把订单置 5，不调微信退款；
  2. 商家同意退款/异常退款：只改本地 status=7，金额可改且无上限校验（可大于实付）；
  3. `restoreStock` 注释写「幂等」，但**回补后不打标**。用户取消会回补一次，平台回调 110/150 再走 `applyStatus` 又回补一次 → **库存虚增**。
- **真实业务影响**：用户钱没到账会投诉；商家账实不符；部分退款仍按整单回补（已结算则完全不回补，已送达退款后库存也不回来）。
- **建议**：先调微信退款成功再改订单；金额上限=实付分；`restoreStock` 增加 `stock_restored` 或与 `goods_settled` 对称标记；部分退款按行处理。

### H4 登录仍是演示模式；商家角色客户端自选；token 即 openid

- **位置**：`POST /api/auth/login`；`auth()`；`merchantGuard`
- **现象**：
  1. `code2session` 整段注释，即使配了 `WX_APPID/WX_SECRET` 也不会启用。`wx.login` 的 code 一次性，每次登录 `demo_ + sha1(code)` 都是**新用户**，历史订单全部断裂。
  2. 首次注册 `role` 由客户端传入，`role=merchant` 即商家，可开舱、派车、同意退款。
  3. `token: user.openid`，鉴权用 Authorization 直接查 users.openid，无过期、无吊销。注释写「openid 的哈希」，实现是明文。
- **真实业务影响**：正式环境若忘了取消注释，每个学生每次打开都是新账号；任意学生可冒充商家控制真车；openid 泄露即永久盗号。
- **建议**：用环境开关启用 code2session（不要靠注释）；商家白名单/邀请码，禁止自选角色；随机 session token + 过期；登录响应不回传 openid。

### H5 平台回调与 check-order 无鉴权；退款单不会强制关任务

- **位置**：`/api/platform/callback/delivery`、`/api/platform/callback/exception`、`/api/platform/check-order`
- **现象**：三个接口公开，无签名、无 token、无来源校验。任意人 POST `taskStatus=70/80/110` 即可把订单改成已送达/已完成/已取消。`handleCheckOrder` **只对 status=5 返回 forceCloseTask**，status=7（已退款）当正常单，机器人继续送。
- **真实业务影响**：伪造送达/取消；已退款订单机器人仍去上货；回调 URL 一旦公网暴露即可被打。
- **建议**：按平台文档做签名/IP 校验；check-order 对 5 和 7（及明确作废态）都返回关任务；取消/退款主动调平台关任务，不能只靠回调未配时的轮询。

### H6 测试后门在真实模式仍可用；商家端上货写死模拟

- **位置**：`POST /api/merchant/device/batch/mock-dispatch`（无 `PLATFORM_MOCK` 守卫）；`POST /api/merchant/delivery/test-complete`；`商家端/pages/device/batchDetail.js` `DEVICE_MOCK = true`；取餐 `pickup-open/close` 无真实任务时 `test:true` 本地完成
- **现象**：真实配送模式下，商家仍可一键把批次假送达；上货详情页永远走 mock-dispatch + 10 秒到达，**不会调用** `/merchant/device/batch/open-bin|close-bin|dispatch`。
- **真实业务影响**：商用后误点即假完成、用户取不到餐；或以为已接真机器人，实际从未开舱派发。
- **建议**：后端测试接口仅 `PLATFORM_MOCK=true` 可进，生产直接 404；`DEVICE_MOCK` 改为跟后端环境，禁止前端写死 true 上线。

### H7 支付回调不核金额、不验微信签名头

- **位置**：`/api/pay/notify`；`wxpay.decryptNotify`
- **现象**：只解密 resource，看 `trade_state` 与 `out_trade_no`，不比对 `amount.total` 与订单 `total_amount`；不校验 `Wechatpay-Signature / Timestamp / Nonce / Serial`。技术方案写「已校验 out_trade_no 与订单状态」，金额一致性未做。
- **真实业务影响**：异常/被改金额的通知仍会把订单标已支付并进入履约（若再叠加 H1 修完后的自动接单，会真的派车）。
- **建议**：验签 + 金额（分）全等 + 仅 status=0 幂等确认；失败返回 FAIL 让微信重试。

### H8 取消/异常重配只改本地任务状态，机器人可能继续跑

- **位置**：`applyOrderCancelled`；`exception/retry`；`platform.js` 无任务取消 API；交接文档亦写回调未配则强制关任务失效
- **现象**：本地 `delivery_tasks.task_status=110`，不调平台关闭。`exception/retry` 把同批次未完成任务全部标 110 再并入新批次，旧平台任务仍在。
- **真实业务影响**：已取消订单仍被装车配送；异常重配后一车两套任务、控制权冲突（如 DLV_CTRL_0007）。
- **建议**：先关平台任务成功再改本地；失败入重试队列并阻断该单派车。

## 2. 中危（真实业务下功能失真）

### M1 未支付订单无超时关单；扣库存不校验购买数量

- **位置**：`/api/order/create`
- **现象**：下单即 `stock -= quantity`，但只拒绝 `stock <= 0`，**买 99 件而库存 3 仍成功**（`MAX(0, stock-?)` 把库存打到 0）。无待支付超时扫描。建单、扣库存、清购物车无事务。
- **真实业务影响**：恶意占库存；并发超卖；中途失败订单与库存不一致。
- **建议**：`quantity > stock` 拒绝；15~30 分钟关未支付单并回补；`BEGIN` 包裹建单链路。

### M2 购物车结算后整表清空

- **位置**：`DELETE FROM cart WHERE user_id=?`
- **现象**：只结算勾选商品时，未勾选行一并删除。
- **建议**：只删本次 `goods_id` / cart id。

### M3 「预约送达时间」只有 UI

- **位置**：`用户端/pages/order/confirm.js`（asap / 30 分钟档）；`orders` 表无期望送达字段；组单按支付先后 + 90s 窗口
- **现象**：用户选「2 小时后」仍立即组单派车。商品详情免责声明还把该时间说成「平均理想值」。
- **建议**：去掉选择器，或后端存 `expect_arrive_at` 并按时间窗组单。

### M4 自动派车 90 秒，一车多单很难成立

- **位置**：`batch.js` `BATCH_WAIT_MS = 90s`；自动接单开启即到期派车
- **现象**：校内下单分散，90 秒几乎凑不满 12 件。默认自动接单开启时，成本优势（一车多单）名存实亡。
- **建议**：窗口改为可配置的分钟级，或「满 N 件 / 最长等待」双条件；高峰/平峰两套。

### M5 接单即订单 status=2「配送中」

- **位置**：`addOrderToBatch`；用户端配送中 tab / 进度条
- **现象**：组单中、待上货、在途共用 2。用户以为车已出发，商家可能还没装车。
- **建议**：拆「已接单/待上货」与「配送中」，或用户端只用批次状态展示。

### M6 到达即结算销量；未取餐不回滚

- **位置**：`platform.applyStatus` 任务 70 → 订单 3 → `settleSales`
- **现象**：用户未取、取失败、事后退款时，`goods_settled=1` 导致不回补库存，销量虚高。
- **建议**：在确认取餐 / 任务 80 再结算；退款路径回滚销量。

### M7 扫码绑定会静默改绑批次设备

- **位置**：`POST /api/merchant/device/scan`
- **现象**：真实模式按 deviceSn 找不到批次时，取**任意最早待上货批次**并改写 `device_sn`，再 `grantControl`。
- **真实业务影响**：扫错车、货装错仓、抢正在执行任务的机器人。
- **建议**：设备必须与派车时的 SN 一致，否则报错；禁止静默换绑。

### M8 批次详情把订单状态当成批次状态文案

- **位置**：`batch.js` `getBatchDetail`：`status_text: statusText(o.status)`，而 `statusText` 是批次枚举（0 组单中 / 1 待上货 / 2 配送中 / 3 已完成 / 4 异常）
- **现象**：订单 1 待接单显示成「待上货」；订单 3 已送达显示成「已完成」；订单 5 已取消无对应文案。
- **真实业务影响**：商家上货时把已取消/已送达单当有效货，装错或漏装。
- **建议**：订单用 `ORDER_STATUS`；列表过滤有效单 `status IN (2,3,4)`；取消后清理或标记 `batch_id` 展示口径。

### M9 路径规划用欧氏距离，没用校园路网

- **位置**：`batch.planRoute` 最近邻；监控地图已有 `mapInfo` graph
- **现象**：规划直线距离最短，忽略不可通行区、楼宇绕行。平台是否按 `priority` 执行仍待真机验证（交接文档已标待办）。
- **建议**：在 graph 上做最短路；真机验证多地点顺序，不行则 `preUnloadingTime` / 联合任务。

### M10 单仓多人取餐的物理模型风险

- **位置**：PRD「一个仓多个人拿」；`pickup-open` 开舱即 `markOrderPicked`
- **现象**：若硬件是单货舱，任一取餐码开舱后整仓暴露，取餐码只能防「系统层拿错」不能防「伸手拿别人的」。开舱即标记已取走，40s 关舱前若没拿到餐，系统已认为完成。
- **建议**：与越凡确认舱格是否按任务隔离；不能隔离则运营上同车尽量同点位，或开舱不立即完成、关舱/确认后再置已取。

### M11 双端正式发布与支付 AppID 模型未设计

- **位置**：用户端/商家端 `project.config.json` 目前同一 `appid`；后端只有一套 `WX_APPID` 做登录和 JSAPI 支付
- **现象**：微信不允许两个小程序共用一个 AppID。拆成两个 AppID 后 openid 不互通，商家登录的 openid 无法作为用户支付 payer。
- **建议**：明确「一个小程序两角色」还是「两个小程序」；若拆端，支付必须用**用户端 AppID + 用户 openid**，商家端只用第二套登录。

## 3. 低危 / 建议

| # | 问题 | 位置 | 建议 |
| --- | --- | --- | --- |
| L1 | 取餐码 4 位数字，无批次内唯一约束 | 建单 `pickupCode` | 冲突重试；扩到 6 位 |
| L2 | 全仓库无 `wx.scanCode` | 双端 | 上线必须接真机码，并约定屏上二维码字段 |
| L3 | 已送达无取餐超时，车会堵在点位 | 状态机 | 超时召回/异常并通知商家 |
| L4 | 金额浮点累加 | 建单 `g.price * quantity` | 全程分（整数） |
| L5 | 商家今日 GMV 用 UTC 日期，且含已退款 | `merchant/stats` `toISOString().slice(0,10)` 且 `status NOT IN (0,5)` | 用 `localtime`；排除 5/7 |
| L6 | 列表无分页 | 订单/商品/批次 | 量大必加 |
| L7 | SQLite 单进程、无备份 | 后端选型 | 试点可暂用；商用要备份/考虑迁移；多实例会重复自动派车 |
| L8 | prod `baseUrl` 仍是 localhost | 双端 `config.js` | 正式 HTTPS 域名 + 合法域名 |
| L9 | 到货通知 R2 未做 | PRD / 技术方案 | 订阅消息，否则用户不知道车到了 |
| L10 | 售后可重复提交；协议/资质占位 | `/api/refund/apply` | 一单一条处理中售后；隐私协议与食品安全条款按主体填写 |

`.env.example` 仍写 `BATCH_MAX_ORDERS`，代码容量已改为 `BATCH_MAX_ITEMS`（按件），配置文档会误导运营。

## 5. 优先级建议

1. **资金与履约能否转起来**：H1 自动接单、H2 收餐人、H3 退款与库存幂等、H7 支付验签金额。
2. **别让测试开关和身份把真车打穿**：H4 登录/商家审核、H5 回调鉴权、H6 测试接口与 DEVICE_MOCK、H8 关平台任务。
3. **运营口径**：M1 超时关单与库存数量、M4 组单窗口、M5/M8 状态文案、M3 预约时间二选一、M9/M10 真机路径与舱格。

## 6. 与文档承诺的偏差（摘录）

| 文档说法 | 代码实际 |
| --- | --- |
| 营业+自动接单 → 支付即并入批次 | 仅 Mock 支付路径成立；真实 `/api/pay/notify` 不成立（H1） |
| 下单联系人来自地址/确认页 | 订单写的是用户表昵称/手机，且写在改资料之前（H2） |
| 取消/售后闭环 | 状态机有，资金无；check-order 不管已退款（H3/H5） |
| 正式启用登录见注释 | 必须改代码，配环境变量不够（H4） |
| 一车多单摊薄成本 | 90s 自动派车下很难多单（M4） |
| 收货完成才计销量 | 任务到达（70）已结算（M6） |
| 安全：支付回调已校验 | 未验签、未核金额（H7） |
