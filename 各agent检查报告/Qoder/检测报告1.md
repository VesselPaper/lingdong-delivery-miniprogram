## 0. 总体结论

**业务建模（一车多单、批次状态机、取消分级、库存/销量分离结算）设计得相当扎实，文档质量也在同类课程/试点项目里属于上乘。但当前代码距离"真实业务可用"有一道结构性鸿沟：钱、身份、机器人三条主线全部是模拟的，而模拟层与真实层没有任何隔离开关——它们混在同一份代码、同一个 .env、同一个进程里。**

最危险的一点不是"某个功能没做"，而是**当前仓库的实际配置组合**：

| 开关 | 当前值（backend/.env 实测） | 含义 |
| --- | --- | --- |
| `WX_APPID` / `WX_SECRET` | **未配置** | 登录走演示模式，`openid = demo_ + sha1(客户端传入的 code)` |
| `PAY_MOCK` | **true** | 支付不产生任何资金流，点一下就"已支付" |
| `PLATFORM_MOCK` | **false** | 配送走真实平台 |
| `PLATFORM_BASE` | **https://robox.eventec.cn**（正式环境，非 test-robox） | 会真实调度真机 |
| `DEVICE_MOCK`（商家端 `batchDetail.js:10`） | **true（硬编码）** | 开舱/关舱/派发全部本地假装成功 |

即：**无身份校验 + 无真实收款 + 直连生产物流平台 + 前端假装已上货已送达**。

在这个组合下，任何一个能访问到后端的人（后端跑在开发者笔记本上、`cors()` 全开、无限流）都可以：把自己注册成商家 → 0 元下单 → 触发对生产 robox 平台的 `queue/create` → **真实机器人被调度到上货点等待**；而商家端点"开始配送"时走的是 `mock-dispatch`，只在本地把任务改成"已上货"、10 秒后把订单改成"已送达"，**从未调用平台的 `loading/confirm`**。机器人会一直停在上货点直到平台侧超时（92 等待上货超时 / 120 上货流程挂起），而用户手机上显示"已送达，请取餐"。

这不是假设，是当前默认配置下的必然行为。

**结论：可以校内演示，不可以真实经营。** 下文按严重度列出 46 项问题，其中 P0 级 6 项在修复前必须禁止接入任何真实用户与真实设备。

## 1. P0 阻断级问题（修复前禁止真实运营）

### P0-1 任何人都能自助成为商家 —— 全站最高权限越权

**证据**

- `backend/server.js:70-105` 登录接口从请求体直接取角色：
  ```js
  const { code, role = 'student', nickname = '' } = req.body || {}
  ...
  const roleVal = role === 'merchant' ? 'merchant' : 'student'
  ```
  新用户注册时 `role` 完全由客户端决定，服务端没有任何白名单、邀请码、手机号绑定、独立主体校验或人工审批。
- `商家端/pages/user/login.js` 就是这么用的：`request.post(api.login, { code, role: 'merchant', nickname: '零栋铺子' })`。
- `backend/server.js:703-708` `merchantGuard` 只校验 `req.user.role === 'merchant'`，即"客户端说自己是什么就是什么"。

**真实业务后果**

任意一个装了这个小程序的学生（甚至只用 curl 打后端 HTTP 接口的人）都能获得完整商家权限，可以：

- 改任意商品价格/库存、下架全部商品（`PUT /api/merchant/goods`、`/goods/stock`）
- 接单、派车、控制真实机器人舱门（`/api/merchant/device/*`、`/batch/dispatch`）—— 意味着**可以远程开舱偷餐**
- 审批自己的退款申请、把任意订单标记为已完成（`/api/merchant/refund/handle`、`/api/merchant/delivery/test-complete`）
- 批量导出**全校顾客的姓名 + 手机号**（`GET /api/merchant/orders` 全量返回，无分页无脱敏）→ 直接触碰《个人信息保护法》
- 删除/篡改活动、切换店铺营业状态（全店停摆）

`真实上线所需功能书.md` 完全没有识别这一项，只提到"演示登录需换真实 code2session"。换成真实 code2session **也不能解决本问题**：真实 openid 只证明"这是一个微信用户"，不证明"这是零栋铺子的老板"。

**建议**：商家身份必须由服务端授予。最小方案是 `merchants` 白名单表（openid 或手机号）+ 管理端一次性授权；或商家端使用独立 AppID 并在后端做 AppID→role 映射；再加操作审计日志。

### P0-2 `DEVICE_MOCK = true` 硬编码：真机被真实调度，前端却假装已上货已送达

**证据**

- `商家端/pages/device/batchDetail.js:10` → `const DEVICE_MOCK = true`（写死在源码，不是配置）
- 同文件 `143-176` `dispatchAll()`：`DEVICE_MOCK` 为真时调用 `api.batchMockDispatch`，真实分支 `api.batchDispatchAll` 被跳过
- 同文件 `79-95` `openBin()`、`98-140` `closeBin()`：真实分支 `batchOpenBin` / `batchCloseBin` 同样被跳过，只做 `setTimeout` 假装成功
- `backend/server.js:1009-1033` `/api/merchant/device/batch/mock-dispatch`：纯本地把 `delivery_tasks.task_status` 改成 50，再 `setTimeout(MOCK_ARRIVE_MS=10s)` 把批次内全部订单改成 `status=3 已送达` 并结算销量，**完全不调用开放物流平台**
- 而 `backend/.env` 里 `PLATFORM_MOCK=false`，批次派车 `doDispatchBatch`(`server.js:930-952`) 会真实调用 `platform.createTasksForBatch` → `queue/create` 打到生产 robox

**真实业务后果**

派车时真机任务已经真实创建，机器人会真的开去上货点等装货。但商家端的"开舱/关舱/开始配送"三个按钮全在本地空转，`loading/verify`、`drawerCtrl`、`loading/confirm` 一次都没发。结果：

1. 机器人停在上货点无人确认装货 → 平台侧超时挂起
2. 用户端 10 秒后收到"已送达，请取餐" → 走到楼栋口发现根本没有车
3. 订单被本地置为 3、销量被结算、批次被推进 → 本地状态与物理世界彻底脱钩
4. 由于任务状态再也不会被平台回调更新（本地已被 mock 改成 70），超时扫描也发现不了

**这是当前配置下的默认行为，不是边界情况。** `真实上线所需功能书.md §2.5` 列出的待移除测试辅助里**没有包含 `mock-dispatch` 和 `DEVICE_MOCK`**，即这份上线清单本身漏掉了最危险的一项。

**建议**：`DEVICE_MOCK` 必须由后端下发的运行模式决定（例如 `/api/shop/status` 返回 `device_mock` 字段），禁止前端硬编码；`mock-dispatch` 接口在非演示模式下直接 404；上线清单补入这两项。

**证据**

- `用户端/pages/order/confirm.js` `submit()` 的请求体只有四个字段：

  ```js
  request.post(api.orderCreate, {
    landmark_id: String(selectedPoint.id),

    items: items.map((it) => ({ goods_id: it.goods_id, quantity: it.quantity }))
  ```

  页面上用户填的 `contactName` / `contactPhone`（`confirm.js` 有 `/^1\d{10}$/` 校验）、选的 `selectedAddress`（含 `detail` 楼栋房间号）**一个都没传**。
- 后端 `server.js:275` 也没有从 body 取这两个字段，`server.js:292` 用的是用户表里的旧值：

- 而更新用户资料是在下单**之后**、fire-and-forget：`confirm.js` `request.put(api.updateProfile, {...}).catch(()=>{})`

**真实业务后果**

1. **新用户首单的手机号必定为空**（`users.phone` 默认 NULL）→ `platform.js:337` 创建任务时

**建议**：`order/create` 请求体加入 `contact_name` / `contact_phone` / `address_id`，后端做手机号正则校验（`doc/03 §7` 声称有，实际没有）并落库；把 `updateProfile` 移到下单之前或直接删除。

### P0-4 取消/退款不取消平台任务；`forceCloseTask` 漏判"已退款"

**证据**

- 全仓库检索确认：**没有任何一处调用平台的任务取消/关闭接口**（`deliveryTask/cancel`、`taskCancel`、`closeTask` 均无匹配）

  ```js
  store.prepare("UPDATE delivery_tasks SET task_status=110, status_text='订单取消' ...").run(...)
  ```

  平台侧任务对此一无所知，机器人继续按原计划取货、送货、在该点位等待
- 唯一的兜底是设备端主动查询的 `checkBizOrderStatusUrl`，即 `server.js:1210-1225` `handleCheckOrder`：

  **只判断 5 已取消，不判断 7 已退款**。而"商家同意退款"(`server.js:574`) 与"配送异常退款"(`server.js:863`) 都是把订单置 **7**。

**真实业务后果**

**建议**：接入平台任务取消接口，在 `applyOrderCancelled` 与所有退款分支中真实下发；`handleCheckOrder` 的强制关闭条件改为 `status IN (5,7)`；取消已上货订单时走人工介入流程（餐已装车无法召回）。

### P0-6 支付回调未校验金额、商户号与平台证书签名

**证据** `server.js:339-355`：

```js
const info = wxpay.decryptNotify(body.resource)
if (info.trade_state === 'SUCCESS' && info.out_trade_no) {
  const order = store.prepare('SELECT * FROM orders WHERE order_no=?').get(info.out_trade_no)
  if (order && order.status === 0) { /* 直接置为已支付 */ }
}
```

缺失的校验：

1. **不比对金额**：未检查 `info.amount.total === Math.round(order.total_amount*100)`。微信支付官方接入指引明确要求校验金额一致
2. **不校验 `Wechatpay-Signature` / `Wechatpay-Serial` 请求头**，未用平台证书验签（当前仅靠 APIv3 密钥解密提供事实上的完整性，不符合官方规范，也无法防御证书轮换场景）
3. **不校验 `info.mchid` / `info.appid`** 是否为本商户
4. **无幂等记录表**：靠 `order.status === 0` 兜底，但退款后订单变 7，若微信重发同一笔支付通知，逻辑上无法区分
5. 失败分支返回 HTTP 200 + `{code:'FAIL'}`（`server.js:351`）与 HTTP 400/500 混用，微信重试语义不清晰

**建议**：按微信支付 V3 官方 Node 接入规范补齐验签 + 金额 + 商户号三重校验，并落一张 `pay_notifications` 幂等表。

## 2. P1 严重问题（真实运营必然高频触发）

### P1-1 单舱多单没有物理隔离，"每单独立取餐码"不构成安全边界

**这是整个"一车多单"产品模型最根本的现实矛盾。**

**真实业务后果**：批次里任意一个订单到达"已送达"后，该用户点"打开舱门"，**整个舱就开了，同舱 12 单的餐全部暴露**。取餐码只能防"自己输错"，防不了"顺手把别人的也拿走"。第一批用户取餐后，后面的人大概率拿到空舱或错餐。

**建议**（三选一，需与越凡确认硬件能力）：
1. 确认机器人是否有多个独立格口；若有，`stockType`/`stockPos` 必须按单分配（当前 `platform.js:649` 写死 `stockPos:'pos_1'`）
2. 若确为单舱，改变运营模型：**一趟只送一个点位**，或按点位分批（同点位多单同车），到点后由该点位的所有用户共同取餐，接受"同点位互信"
3. 加装取餐柜/人工值守，无人车只负责点到点运输

这一项不解决，一车多单在真实场景就是"集体丢餐"。

### P1-3 "配送异常重新配送"会摧毁整批次的任务状态同步

`server.js:833-848` `/api/merchant/order/exception/retry`：

```js
if (order.batch_id) {
  store.prepare("UPDATE delivery_tasks SET task_status=110, status_text='异常重配，任务作废'
                 WHERE batch_id=? AND task_status < 80").run(order.batch_id)
  ...
}
```

条件写的是 **`WHERE batch_id=?`**，不是 `WHERE order_id=?`。商家为**一单**点"重新配送"，同批次**其余 11 单**正在途中的任务全部被本地标记为 110 已取消。

随后 `platform.js:513` 轮询兜底：

```js
if (!t || t.task_status >= 80 || (t.task_status >= 90 && t.task_status !== 120)) return
```

task_status=110 → 直接 return，**这些任务永远不会再与平台同步**。而平台侧机器人还在正常跑这些单。

**后果**：一次误操作（或一次真实的单车故障）就让整批 12 单在系统里"失联"：商家看不到进度、用户端进度条冻结、批次永远无法完成、销量永不结算。

**建议**：把条件改为 `WHERE order_id=?`；作废平台任务必须调用平台接口而非仅改本地字段。

### P1-5 库存超卖：校验非原子，且 `MAX(0,…)` 把超卖痕迹抹掉

`server.js:270-303` `/api/order/create`：

```js
if (Number(g.stock) <= 0) throw new Error('「'+g.name+'」已售罄')   // 只判断"是否 > 0"
...
store.prepare('UPDATE goods SET stock=MAX(0,stock-?) WHERE id=?').run(quantity, goods.id)
```

两个问题：

1. **只判断 `stock <= 0`，不判断 `stock >= quantity`**。库存剩 1 份时，两个用户各下 5 份都能通过校验，`MAX(0,1-5)=0`，两单都成立 → 实际超卖 9 份，且数据库显示库存 0，**事后无法发现超卖了多少**。
2. **`quantity` 完全不校验**：
   - 传 `-5` → `total += price * (-5)` 得到负数金额；`stock = MAX(0, stock+5)` → **库存反增**；`Math.round(total*100)` 为负，微信支付会报错，但 `PAY_MOCK=true` 下直接通过
   - 传 `0.5`、`1e9`、`'abc'`（→ NaN）均无拦截，NaN 会污染 `total` 与 `stock`

**后果**：真实运营中高峰期必然超卖 → 商家做不出餐 → 批量客诉退款（而退款又是假的，见 P0-5）。负数量是一个可被脚本利用的数据污染入口。

**建议**：`quantity` 强制 `Number.isInteger(q) && q > 0 && q <= 50`；库存校验改为条件更新并检查影响行数：
```js
const r = db.prepare('UPDATE goods SET stock=stock-? WHERE id=? AND stock>=?').run(q, id, q)
if (r.changes === 0) throw new Error('库存不足')
```
整个下单流程包在一个事务里（见 P2-1，当前全仓库零事务）。

### P1-7 派车存在并发竞争 → 重复创建平台任务、重复调度真机

`server.js:930-952` `doDispatchBatch`：

```js
const b = ...get(batchId)
if (Number(b.status) !== 0) throw new Error('该批次已派车')   // ← 读检查
const route = batch.planRoute(store, orders)
let sn = deviceSn || b.device_sn || ''
if (!sn && PLATFORM_MOCK !== 'true') {
  const r = await platform.pickAvailableRobot()      // ← await，事件循环让出
  ...
}
store.prepare("UPDATE delivery_batches SET ... status=1 ...")
await platform.createTasksForBatch(store, b, orders, route)   // ← 再次 await，内部逐单 await queue/create
```

在"读检查"与"写 status=1"之间存在 `await`，Node 事件循环会让出。而触发派车的入口有**三个且互相不知情**：

1. `server.js:954` 商家手动点"派车配送"
2. `server.js:1425-1446` 每 15 秒的自动派车 `setInterval`
3. 商家在网络慢时重复点击（`batchDetail.js:144` 只挡了 `phase==='dispatched'`，而 phase 是请求成功后才更新的）

**后果**：两个调用同时通过 `status===0` 检查 → 同一批次生成**两套 `delivery_tasks`** → 对生产平台发出 **24 次 `queue/create`** → `orders.delivery_task_id` 被后写的那套覆盖，前一套任务成为无人认领的孤儿任务，真实机器人可能真的跑两趟。批次 `total_orders` 也会被 `addOrderToBatch` 之外的路径搞乱。

同类竞争还存在于：`pickup-open`（两次并发都通过 `status===3` 检查 → 两次开舱 + 两次 `markOrderPicked`）、`refund/handle`（无订单状态检查，见 P2-9）。

**建议**：所有"读-判断-await-写"的状态机迁移改为条件更新抢占：
```js
const r = db.prepare('UPDATE delivery_batches SET status=1, dispatched_at=... WHERE id=? AND status=0').run(id)
if (r.changes === 0) throw new Error('该批次已派车')   // 抢不到就退出，再做后续 await
```
并把状态写入提前到所有 await 之前。

`batch.js:61-71` `getOrCreateOpenBatch`：

### P1-10 扫码识别机器人时会认错车，货上到错误的机器人上

`server.js:1316-1333` `/api/merchant/device/scan` 真实模式分支：

```js
batchRow = db.prepare('SELECT * FROM delivery_batches WHERE status=1 AND device_sn=? ...').get(deviceSn)
```

### P1-11 平台 HTTP 调用无超时 → 一个挂起的请求能拖死整个后端

`platform.js:69-97` `requestPlatform` 用原生 `http/https.request`，**没有设置任何 timeout**（无 `req.setTimeout`、无 `AbortController`、无 `Promise.race`）。

被它阻塞的调用链：

- `server.js:1381-1390` 真实模式轮询：`setInterval` 内 `for...await` 串行同步每一个未完成任务。任一请求挂起 → 该 interval 回调永不结束 → 任务状态永久停止同步
- `server.js:1160-1163` `/api/merchant/delivery/monitor`：`for...await getDevicePosition` 串行，商家端每 5 秒轮询
- `server.js:596` `/api/delivery/track`：用户端每 3 秒轮询
- `platform.js:222-229` `getMapOverview`：同样串行 for-await

叠加 `node:sqlite` 的 **DatabaseSync 是完全同步、阻塞事件循环**的（见 P2-1），一次平台超时 + 大量同步 SQL 就能让整个单进程后端无响应。

**建议**：所有平台调用统一加 5-10s 超时 + 有限重试 + 熔断；轮询改为并发受限的批处理（`Promise.allSettled` + 并发上限）；`getDevicePosition` 按 `deviceSn` 而非 `taskId` 缓存（见 P2-4）。

- 检索确认：`backend/` 中**没有任何 `BEGIN` / `COMMIT` / `ROLLBACK` / `db.exec('BEGIN')`**
- 多步写入全部裸奔：
  - 下单：`INSERT orders` → N × `INSERT order_items` → N × `UPDATE goods.stock` → `DELETE cart`（`server.js:289-301`）。第 2 件商品插入失败 → 订单已存在、库存只扣了第 1 件、购物车未清、客户端收到 500
  - 派车：`UPDATE batches` → N × `INSERT delivery_tasks` + `UPDATE orders` + N × 平台 `queue/create`（`server.js:944-949`）。中途失败 → 部分订单有任务、部分没有，批次已是"待上货"
  - 退款：`UPDATE refunds` + `UPDATE orders` + `restoreStock`（`server.js:571-575`）
- `db.js:2` 使用 `node:sqlite` 的 `DatabaseSync`：该模块在 Node 22.5 引入时需 `--experimental-sqlite`，至今 Stability 仍为 1.1（Active development）。**同步 API 意味着每一条 SQL 都阻塞事件循环**，与 P1-11 的无超时平台调用叠加，单进程后端在几十并发下即会明显卡顿
- `db.js:196-203` `migrate()` 每次启动都执行两条**相关子查询的全表 UPDATE** 回填 `daily_seq`（`WHERE date(b2.created_at)=date(...)`，无索引）→ O(n²)。订单量到几万条后每次重启都要卡数十秒
- 无数据库备份机制、无 schema 版本号表、无迁移回滚

**建议**：所有多步写入包事务（`node:sqlite` 支持 `db.exec('BEGIN')`）；`daily_seq` 回填加 `WHERE daily_seq IS NULL` 的索引或改为一次性脚本；制定每日 SQLite 文件备份 + WAL checkpoint 策略；评估迁移到 MySQL/PostgreSQL（`doc/03 §2` 自己写了"后续可平滑迁移 MySQL"，但没有迁移方案）。

### P2-3 列表接口全部无分页，且存在严重 N+1

- `/api/order/list`(`server.js:357-365`)：`ORDER BY id DESC`，无 LIMIT
- `/api/merchant/orders`(`server.js:755-799`)：无 LIMIT，且**每一行**执行 `getItems` + `getBatch` + `landmarkNameOf`（后者内部再查一次 landmarks）= 3-4 条 SQL。1000 单 → 单次请求 3000+ 条同步 SQL + 全量 JSON
- `/api/merchant/orders/exception`(`server.js:877`)：同样无 LIMIT + 每行 3 条 SQL
- `/api/refund/list`、`/api/merchant/refunds`、`/api/merchant/cancel-requests`、`/api/address/list`、`/api/goods/list`：均无 LIMIT

**后果**：用户端"我的订单"页、商家端"任务页"随数据增长线性变慢，一个月后（按日均 200 单 = 6000 单）商家端每次进入任务页触发 2 万+ 条同步 SQL，页面白屏。

### P2-4 位置缓存按 taskId 而非 deviceSn，且两个 Map 永不清理

- `platform.js:536` `const posCache = new Map() // taskId -> {ts,pos}`，`platform.js:543` 3 秒缓存
- 一个批次 12 个任务共用同一台机器人 → **12 个独立缓存条目 → 每 3 秒对平台发 12 次完全相同的 `iotGatewayProxy` 请求**。再乘以并发用户数（每人 3 秒轮询一次 track）
- `posCache` 与 `platform.js:41` `mockTasks` 都是模块级 Map，**没有任何淘汰逻辑** → 长期运行内存单调增长（任务永不删除）

**建议**：缓存键改为 `deviceSn`；加 LRU 上限或定期清理已完成任务的条目；`mockTasks` 在任务终态时 `delete`。

### P2-5 `daily_seq` 用 `COUNT(*)+1` 生成，可重复

- `server.js:288-292`：`SELECT COUNT(*) FROM orders WHERE date(created_at)=date('now','localtime')` 然后 `+1`
- `batch.js:67-69`：批次序号同样逻辑

"读计数 → +1 → 写入"不是原子操作。虽然 `order/create` 处理器是纯同步的（当前不会被事件循环打断），但：

1. 一旦按 P1-7 的建议引入事务或改为多进程（PM2 cluster）/多实例，**立刻产生重号**
2. 用 `COUNT(*)` 而非 `MAX(daily_seq)+1`，任何订单删除都会导致后续序号整体错位

而商家端与用户端的**主要可视标识就是这个序号**（`doc/01_PRD §6`：卡面标题为「批次 N / 订单 N」，完整编号只在详情页弱化展示）。重号 = 商家按"订单 7"配餐时配错单 = 直接错餐。

**建议**：改为单条原子 SQL `INSERT ... SELECT IFNULL(MAX(daily_seq),0)+1 FROM orders WHERE date(created_at)=date('now','localtime')`，并对 `(date(created_at), daily_seq)` 加唯一约束。

### P2-6 金额全链路使用浮点数

- `db.js:49` `goods.price REAL`、`db.js:75` `orders.total_amount REAL`
- `server.js:282` `total += g.price * Number(it.quantity)`（浮点累加）
- `server.js:292` `.run(..., total.toFixed(2), ...)` —— 把**字符串**绑定到 REAL 列，依赖 SQLite 类型亲和性隐式转换
- `server.js:330` `amountFen: Math.round(Number(row.total_amount) * 100)`

`0.1 + 0.2 !== 0.3` 的经典问题在真实收款上是硬风险：`10.9 * 3 = 32.699999999999996`，本例 `Math.round` 侥幸得到 3270，但价格与数量组合足够多时必然出现某组合少收/多收 1 分。而微信支付金额以分为单位、必须与实际收款一致，差异会导致对账不平。

**建议**：全链路改为**整数分**存储与计算（`price_fen INTEGER`），展示层再除 100。这是电商系统的基础要求。

### P2-7 无全局错误中间件，业务 `throw` 变成裸 HTML 500

- 检索确认 `server.js` 中**没有** `app.use((err, req, res, next) => ...)`
- `server.js:280-281` `/api/order/create` 内部用 `throw new Error('商品不存在')` / `throw new Error('「xxx」已售罄，请更换商品')`，**该处理器没有 try/catch**

Express 4 会捕获同步 throw 并交给默认错误处理器 → 返回 **HTML 格式的 500**（开发模式含完整堆栈）。而 `用户端/utils/request.js` 只解析 `res.data.msg`，HTML 响应下走到 `'请求失败'` 兜底。

**后果**：
1. 用户下单时商品刚好售罄 → 看到"请求失败"，而不是"「招牌鸭脖」已售罄，请更换商品"。精心写的错误文案一个字都到不了用户面前
2. 开发模式下堆栈直接返回给客户端，泄露内部路径与代码结构

**建议**：加全局错误中间件统一输出 `{code, msg}`；`order/create` 包 try/catch 把业务错误映射为 400；生产环境 `NODE_ENV=production` 屏蔽堆栈。

### P2-8 `landmark_id` 不校验存在性 → 订单可指向不存在的点位

`server.js:292` 直接落库 `landmark_id || ''`，不查 `landmarks` 表。

后果链：`batch.planRoute`(`batch.js:151-195`) 找不到该 landmark → `lm=null`、坐标为 0 → 路线规划退化；`platform.js:282` `unloading` 为 `undefined` → `platform.js:318` 触发重新同步，同步后仍找不到 → `updateTask(store, taskId, '待配置平台点位，任务未下发')` **但 `task_status` 保持 0、订单保持 status=2** → 15 分钟后被超时扫描标为配送异常。整个过程用户已付款、商家已备餐。

**建议**：`order/create` 校验 `landmark_id` 必须存在于 `landmarks` 且 `type='deliverPoint'` 且 `platform_landmark_id != ''`，否则直接拒单。

### P2-9 `restoreStock` 非幂等 → 库存可被重复回补

`backend/services/goodsStats.js:22-31`：


`settleSales` 会置 `goods_settled=1`（幂等），但 `restoreStock` **不置任何标记**，注释却写着"（幂等，已结算不退回）"。

### P2-10 商家当日统计存在时区错误

`server.js:732-736`：


而 `created_at` 全部由 `datetime('now','localtime')` 写入（北京时间）。UTC 与北京时间差 8 小时：

商家早上出摊看工作台，"今日订单 0 / 今日营收 ¥0"，而实际上凌晨已经有单。早餐/夜宵场景直接受影响。

### P2-13 "送达时间"是纯装饰 UI：采集了、展示了、从不提交、不参与任何排程

### P2-16 整批开舱/关舱被实现为"逐任务串行调用"，真机语义存疑

- `platform.js:373-386` `verifyBatchLoading`：`for` 循环对批次内每个 `task_status<50` 的任务依次调用 `loadingVerify(..., { autoOpen: true })`
- `platform.js:389-403` `confirmBatchLoading`：同样对每个任务依次调用 `loadingConfirm`

**风险**：
1. `autoOpen:true` 连续调用 12 次 → 真机舱门可能反复开合，或第 2 次起报"舱门已开"
2. `loading/confirm` 语义是"确认上货并开始配送"（`platform.js:657` 注释）。**第 1 次 confirm 就可能让机器人出发**，而商家还在往舱里放第 2-12 份餐 → 舱门在装货途中关闭并驶离
3. 串行 12 次 HTTP（且无超时，P1-11）→ 一次"开始配送"点击可能等待数十秒

`doc/03 §1.1 第 7 条` 只说了"每单一个 queue/create 任务"，没有论证平台的整批上货语义。`真实上线所需功能书.md §2.4` 提到需真机验证配送顺序，但没提这个更前置的问题。

**建议**：与越凡确认是否存在批次级/多任务级的 `loading/verify`、`loading/confirm`（`unloadingVerify` 已经支持 `taskIdList` 数组，说明平台有多任务语义，上货侧大概率也有）。若有，改为一次调用传全部 taskId。

### P2-17 停靠顺序仅靠 `priority` 提示，超过 10 站后完全失效，且平台是否遵守未验证

   ```js
   const isLoading = (p) => /上货|商铺|店铺|铺子/.test(p.landmarkName || '')
   ```
   一旦平台侧把"商铺上货"改名（如改成"零栋取货点"" Loading Point"），**系统里就不再有 loadingPoint** → `platform.js:274` 查不到 → 全部任务"待配置平台点位，任务未下发" → 全店瘫痪
3. `platform.js:146` 同步成功后无条件删除所有 `platform_landmark_id` 为空的点位：
   ```js
   removed = db.prepare("DELETE FROM landmarks WHERE platform_landmark_id='' OR platform_landmark_id IS NULL").run().changes
   ```
   而 `addresses.landmark_id`、`orders.landmark_id` 都是**无外键约束**的裸引用（`db.js` 建表语句中没有任何 `FOREIGN KEY`）。删掉点位后，历史订单与用户地址的 `landmark_id` 变成悬空引用 → `batch.landmarkNameOf`(`batch.js:41-47`) 回退到 `'未知点位'`

**建议**：上货点应由平台 `type=loadingPoint` 查询获得而非名称猜测；`building` 应可配置；删除点位改为软删除（`status` 字段），并检查引用。

### P2-19 登录令牌就是 openid 明文，永久有效、不可吊销

- `server.js:104` `ok(res, { token: user.openid, user })` —— token 直接等于 openid
- `server.js:49-56` `auth` 中间件就是 `SELECT * FROM users WHERE openid=?`
- `doc/03 §7` 声称"token=openid（真实 openid 不可预测）"

问题：

1. **当前是演示模式**：`server.js:78` `openid = 'demo_' + sha1(code).slice(0,24)`，`code` 由客户端任意提供 → openid **完全可预测、可伪造**。任何人可以自己算出任意 openid 并冒充该用户（包括已存在的商家账号）
2. 即使换成真实 openid：openid 是**永久不变的标识符**，不是令牌。泄露即永久失去该账号（无法吊销、无法过期、无法强制下线）
3. `server.js:107` `GET /api/user/profile` 把包含 openid 的**整行用户记录**返回给前端；`用户端/pages/user/login.js:15` 存进 `wx.setStorageSync('userInfo')` → openid 在客户端明文落盘
4. 无登录态过期、无设备绑定、无异地登录检测、无登出即失效（`退出登录` 只清本地 storage，服务端 token 仍然有效）

**建议**：签发 JWT 或随机 session id（存服务端、可吊销、有有效期），openid 只做内部主键，绝不出现在任何响应体中。

### P2-20 缺少生产级基础设施：限流、安全头、日志、进程守护、监控

- `server.js:44` `app.use(cors())` —— 全开，任意来源可跨域调用全部接口
- 无 `helmet`（缺 CSP、X-Content-Type-Options、HSTS 等安全头）
- **无任何限流**：登录、下单、支付、退款、机器人控制接口全部可被脚本高频调用。`/api/merchant/device/batch/open-bin` 无限流 = 可被刷爆真机舱门
- `server.js:45` `express.json({ limit: '8mb' })` + `server.js:1036-1047` base64 图片上传 + `fs.writeFileSync` 同步写盘 → 单个请求可让事件循环阻塞数百毫秒，8MB × 并发即可打满内存与磁盘
- 无请求日志（morgan/pino）、无错误上报（Sentry）、无健康检查端点、无 metrics
- `backend/package.json` 只有 `start: node server.js`，**无 PM2/systemd 配置、无 `engines` 字段声明 Node 版本**（`node:sqlite` 要求 Node ≥22.5，实际建议 ≥23.4 才免 flag）
- 上传图片无尺寸/大小/内容类型校验（只校验扩展名 `server.js:1040`），无魔数校验，无过期清理 → 磁盘无限增长
- `用户端/app.js` 无 `onError` / `onUnhandledRejection` 全局兜底，无 `wx.getUpdateManager()`（发布后用户可能长期运行旧版本）

### P2-21 定时状态迁移全部依赖进程内存，重启即丢

后端有 3 处 `setInterval`/`setTimeout` 驱动业务状态：

- `server.js:1020` mock 送达的 `setTimeout`（纯内存，重启即丢，见 P1-4）
- `server.js:1381` 平台状态轮询
- `server.js:1415` 超时未接单扫描
- `server.js:1425` 批次自动派车扫描

后三者每次 tick 都从数据库重新求值，重启可自愈。但**没有任何分布式锁**：一旦按 `真实上线所需功能书.md §2.6` 用 PM2 cluster 或多实例部署，这些 interval 会在每个实例上各跑一份 → 自动派车竞争（P1-7 加剧）、超时扫描重复标记、平台轮询请求量翻倍。

**建议**：定时任务抽到独立 worker 进程，或用数据库行锁/分布式锁保证单实例执行。

### P2-22 用户端 401 处理与商家端不一致，且会堆满页面栈

- `用户端/utils/request.js`：401 时 `wx.removeStorageSync('token')` + **`wx.navigateTo({url:'/pages/user/login'})`**
- `商家端/utils/request.js`：401 时清 token + userInfo + **`wx.reLaunch`**

用户端用 `navigateTo`：页面栈上限 10 层，每次 401 都压一层登录页；且不清 `userInfo`，导致返回后页面仍显示旧用户信息。并发请求同时 401（例如首页并行发 3 个请求）会**一次性压入 3 个登录页**。

**建议**：两端统一为 `reLaunch`，并加"正在跳转登录"的去重标志。

## 4. P3 轻微问题

### P3-1 追踪页轮询无 onHide 清理、无重入保护

`用户端/pages/delivery/track.js:26` `onLoad` 里 `this.timer = setInterval(() => this.load(true), 3000)`，但只有 `onUnload` 清理，**没有 `onHide`**。用户从追踪页 `navigateTo` 进取餐页（`track.js:simulatePickup`）时追踪页仍在栈中、仍在每 3 秒请求 `/api/delivery/track`（该接口内部会同步调用平台位置接口）。`load()` 也没有 `if (this.loading) return` 的重入保护，平台响应慢于 3 秒时请求会无限堆积。

对比 `商家端/pages/device/batchDetail.js:35-36` 就正确实现了 `onHide` + `onUnload` 双清理。

### P3-2 死代码与未使用导出

- `platform.js:237-255` `createQueueTask`（单订单建任务）已被批次版 `createTasksForBatch` 取代，仍导出
- `platform.js:406-466` `realDispatch`（单任务真实派车）同样已被 `realDispatchBatch` 取代，两份代码 90% 重复，改一处忘另一处的风险很高
- `server.js:635-646` `/api/delivery/confirm`（带取餐码校验的确认取餐）**取餐页从不调用**，实际走的是不校验取餐码的 `pickup-open`（见 P1-1）。也就是说：唯一做了取餐码校验的接口是个死接口
- `server.js:386-388` `/api/user/order/mark-read` 是空实现（`ok(res)` 直接返回），保留"兼容"
- `server.js:1250` 留了一行注释"已由下方批次版取代"但没有删除对应实现
- `backend/test_batch_flow.js` 是冒烟脚本，但 `package.json` 没有 `test` script，无法纳入 CI

### P3-3 商品编辑接口无字段校验，部分更新会写坏数据

`server.js:1084-1094` `PUT /api/merchant/goods` 用全量覆盖式 UPDATE，但：

- `name` 不校验非空（`POST` 版本 `server.js:1078` 有校验，`PUT` 没有）→ 可把商品名改成 `undefined`/NULL
- `price` 无校验 → `Number('abc')` = NaN 写入 REAL 列；负价格可通过 → 用户下单得到负金额（叠加 P1-5 的负数量问题）
- `status` 缺省强制为 1（`server.js:1092` `status !== undefined ? Number(status) : 1`）→ 想只改价格却把下架商品重新上架
- `category` 缺省为 `'其他'` → 未传分类会静默改写分类

### P3-4 取餐码空间过小且无防爆破

`server.js:286` `const pickupCode = String(Math.floor(1000 + Math.random() * 9000))` —— 4 位数字，仅 9000 种可能，且 `Math.random()` 非密码学安全。

- 同批次 12 单要求码各不相同（`doc/01_PRD §1.1 第 4 条`），但**代码没有任何去重逻辑**，纯靠概率（12 单在 9000 空间中碰撞概率约 0.7%，即大约每 140 个批次出现一次同车重码）。一旦重码，"防拿错"设计当场失效
- `/api/delivery/confirm` 对取餐码错误无次数限制、无锁定 → 可枚举（虽然它当前是死接口，见 P3-2）
- 机器人屏幕上如果显示取餐码，旁人可直接读取

**建议**：改用 `crypto.randomInt`，扩展到 6 位，并在批次内做唯一性校验（重试生成）。

### P3-5 前端与后端的售罄/歇业拦截依赖前端，绕过成本低

- `confirm.js:submit()` 的 `shopClosed` 拦截、`cart.js:73-77` 的售罄拦截都在前端
- 后端有兜底（`server.js:272` 歇业、`server.js:281` 售罄），这点做得对
- 但 `server.js:271-274` 的歇业检查在处理器**最前面**，而商品校验在 `map` 里 throw（P2-7 变成 HTML 500）→ 歇业提示能正常到达用户，售罄提示不能。同一个处理器里两种错误处理路径不一致
